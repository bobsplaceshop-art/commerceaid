## Worked on

### The Daraja portal: the missing product

Every STK push returned HTTP 404 with the body
`{"errorCode":"404.001.03","errorMessage":"Invalid
Access Token"}`. The message names the wrong
cause. The token was valid: the OAuth handshake
succeeded, the token was 28 characters of
printable ASCII, the Authorization header was
correctly formatted.

The actual cause: the Daraja developer app did
not have the "Lipa Na M-Pesa Sandbox" product
enabled. Daraja returns 404.001.03 for a missing
product subscription, not just for a bad token.
The error code is the same for both.

The fix was in the portal: enable the product on
the app. No code change.

### The transaction type / shortcode mismatch

After the product was enabled, the STK push
returned HTTP 400 "Bad Request - Invalid
TransactionType". The settings row held
`CustomerBuyGoodsOnline` paired with shortcode
`174379`. That shortcode is a Paybill; the paired
transaction type must be `CustomerPayBillOnline`.
Buy Goods (Till) shortcodes use
`CustomerBuyGoodsOnline`.

The two values move together. A Paybill shortcode
requires the PayBill transaction type. A Till
shortcode requires the BuyGoods transaction type.
The admin form offers both options without
validating the pair.

Fixed in Settings > Payments: changed the
transaction type to `CustomerPayBillOnline`. No
code change.

### The M-Pesa phone field

The provider reads `$context['customer_phone']`.
Nothing supplied it. The original design pulled
the phone from the shipping address — wrong,
because the payer can differ from the shipping
recipient (gift orders, third-party payments).

A new field on the payment step appears only when
M-Pesa is selected. Its value travels through the
checkout state and into the provider context as
`customer_phone`. The shipping address is
untouched.

### The order currency hardcode

`CheckoutService::placeOrder()` wrote the literal
`'EUR'` as the order's `currency_code`. The
store's `default_currency_id` was never read. The
setup wizard's Currency tab stored the value; the
checkout flow ignored it. M-Pesa is KES-only; the
provider's gate refused every order.

`StoreRepository::currencyCodeForStore(int $storeId)`
was added. It joins `commerce_stores` to
`core_currencies` and returns the code. Falls back
to `'EUR'` if the store has no currency set.

`CheckoutService::placeOrder()` reads the value
through that method.

Committed as `9b27bef` — `fix(checkout): order
currency reads the store's setting`.

### The inventory reservation not released on failure

`placeOrder()` reserves stock inside its
transaction (`reserved += qty`). When the charge
failed (the four issues above), the order stayed
`unpaid`, the reservation stayed held, and the
customer saw the product as out of stock on retry.
Five stuck orders accumulated in one test session.

`CheckoutController::cancelFailedOrder()` releases
each line's reservation and cancels the order on
any charge failure. The order becomes terminal;
the customer retries with a new order.

The five existing stuck orders were cleaned up
manually with two SQL statements: one to release
each order's reservation, one to cancel each
order.

This bug is not M-Pesa-specific. Every provider's
failed charge would have hit the same path. Any
future provider inherits the fix.

### The token trim (defensive)

`MpesaProvider::token()` now trims the access
token before caching it. The Daraja OAuth
response was clean in testing — the diagnostic
showed 28 characters of printable ASCII with no
trailing byte. The trim is insurance against a
future response that carries whitespace. A token
with trailing whitespace produces the same
misleading 404.001.04 error the portal product
check produces.

## The diagnostic method

When the STK push failed with 404 and the token
looked valid, the diagnostic was a byte-level log
line:

    Logger::info('mpesa.stkpush.debug', [
        'token_len'       => strlen($token),
        'token_hex_first' => bin2hex(substr($token, 0, 8)),
        'token_hex_last'  => bin2hex(substr($token, -8)),
        'header_len'      => strlen('Authorization: Bearer ' . $token),
    ]);

The output was:

    {"token_len":28,
     "token_hex_first":"414e673263596d34",
     "token_hex_last":"6e51616633695678",
     "header_len":50}

Decoding: the token is `ANg2cYm4...nQaf3iVx` — 28
printable ASCII characters, no `0a`, no `0d`, no
`efbbbf`. The token is clean.

That result pointed the search away from the
token and toward the Daraja portal. The
diagnostic was removed after the fix.

The method generalizes: when an API says a
credential is invalid but the credential looks
valid, log its byte shape. A BOM, a trailing
newline, or a stray control character shows up in
the hex and nothing else.

## The waiting page timeout

The polling script stops after 5 minutes
(`MAX_POLL_MS = 5 * 60 * 1000`). If the order has
not flipped to `paid` by then, the status message
changes to "Still waiting. If you did not receive
the prompt, use the link below to try another
method." The customer must click the cancel link
to retry. No automatic redirect.

The sandbox callback arrived 26 seconds after the
push. Real M-Pesa pushes usually complete in
15-60 seconds. Five minutes is generous.

An order whose customer never enters the PIN
stays `unpaid` with its inventory reserved. The
`bin/cleanup-mpesa-requests.php` cron deletes
stale pending rows after 24 hours. A future cron
should cancel abandoned unpaid orders and release
their reservations. Logged in the ROADMAP's
abandoned-checkout recovery entry.

## Decisions made

**The M-Pesa phone is a payment-step field, not a
shipping-address field.**

The payer can differ from the shipping recipient.
Gift orders and third-party payments are common.
The payment phone is transient; it is used for the
STK push and never written to the order's shipping
data. The industry pattern (Flutterwave, Odoo,
WooCommerce mobile money plugins) collects the
phone on the payment step.

**The M-Pesa phone field is only shown when M-Pesa
is selected.**

The payment step already had this pattern for the
purchase-order number. The M-Pesa phone field
follows the same shape: hidden by default,
revealed by the payment method radio. A
progressive-enhancement script does the toggling.
If the script fails to load, the field stays
hidden and the server validates — the customer
gets a clear error and returns to the payment
step.

**The caller context on `PaymentChargeService::charge()`.**

The signature changed from `charge(Order $order)`
to `charge(Order $order, array $context = [])`.
The caller supplies keys the provider needs beyond
the order itself. Today that is
`customer_phone`. A future provider that needs a
different caller value uses the same parameter.
The default is an empty array, so no existing
caller breaks.

**The failed-charge cleanup cancels the order.**

The order is terminal after a charge failure. The
customer retries with a new order. The
alternative — keep the order `unpaid` for retry
— would leave it in the admin queue indefinitely
and would need its own reservation cleanup on the
retry path. Cancelling is simpler and produces
the same customer outcome.

**The waiting page does not auto-redirect on
timeout.**

A customer who has been staring at "Waiting for
confirmation..." for five minutes has either
abandoned or is having phone trouble. Either way,
the customer should choose the next step. The
cancel link is visible. Auto-redirecting would
lose the page if the callback arrived at the
5-minute mark.

**The diagnostic uses `bin2hex`, not `var_dump`.**

`var_dump` of a string with a trailing newline
shows a `\n` in the output that is easy to miss
in a log. The hex representation is unambiguous:
`0a`, `0d`, `efbbbf` are the exact bytes to
look for. The method generalizes to any
credential-related failure.

## New patterns for REMEMBER.md

**A provider error message names the wrong
cause when the app is not subscribed to the
product.**

Daraja returned 404.001.03 "Invalid Access
Token" for two different conditions: an expired
or malformed token, and an app that does not
have the called product enabled. The message
names the token; the cause was the product
subscription. The fix was in the portal, not
in the code.

The general lesson: when a provider's error
message names a specific cause but the cause
looks valid, check the provider's product
subscription or account state before debugging
the message. The message is a hint, not a
diagnosis.

Where we hit it: the M-Pesa STK push flow. Every
push returned "Invalid Access Token" for two
hours. The token was valid. The Daraja app did
not have Lipa Na M-Pesa Sandbox enabled.

**A settings value that looks plausible in
isolation can be wrong for the paired value.**

`CustomerBuyGoodsOnline` is a valid Daraja
transaction type. `174379` is a valid Paybill
shortcode. Together they are invalid. Daraja
rejected the pair with "Bad Request - Invalid
TransactionType".

The settings form offers both transaction types
without validating that the selected type
matches the shortcode's product. A future
improvement: the Settings tab validates the pair
on save and warns the merchant.

The general lesson: when two settings values
must move together, validate the pair, not each
value alone.

Where we hit it: the M-Pesa settings. The stored
transaction type was the Buy Goods value; the
shortcode was a Paybill.

**A credential byte diagnostic catches the
invisible failures.**

`var_dump` of a string with a trailing newline
shows a `\n` that is easy to miss. `bin2hex`
shows `0a` unambiguously. When a credential
fails but looks correct, log its hex shape.

Where we hit it: the M-Pesa token. The
diagnostic proved the token was clean, which
redirected the investigation to the Daraja
portal.

## Post-close - Abandoned checkout recovery

The M-Pesa sub-stage closed with the session
file above. The same day continued into the
abandoned-checkout recovery. Two commits.

### The gap

The M-Pesa test session surfaced the gap. Five
orders accumulated in an hour, each holding its
inventory reservation after a failed charge. The
`cancelFailedOrder()` fix (shipped in `581e802`)
handles the charge-failure path. It does not
handle the abandonment path: a customer who
places an order and never completes payment.

The abandoned-checkout cron found eighteen such
orders on its first real run. Nine from the day
the checkout was first built (2026-09-28), nine
from the Stripe and PayPal test mornings
(2026-10-15). They had been sitting `unpaid` for
weeks. Each held its reserved stock.

### OrderCancellationService

`app/Commerce/Services/OrderCancellationService.php`.
One public method: `cancel(Order, reason)`.
Releases each line's inventory reservation,
marks any pending `commerce_mpesa_requests` row
for the order as failed, and writes the order's
terminal state (`status = 'cancelled'`,
`payment_status = 'failed'`).

`CheckoutController::cancelFailedOrder()` is now
a thin wrapper around the service. The cron
calls the same service. One implementation, two
entry points.

### The cron

`bin/cancel-abandoned-orders.php`. Same shape as
`bin/cleanup-mpesa-requests.php`. Iterates every
store, finds abandoned orders via
`OrderRepository::findAbandoned(int $minutes)`,
and cancels each through the service.

Flags: `--store=`, `--minutes=`, `--dry-run`.

The threshold is the store setting
`general.orders.abandoned_after_minutes`
(default 60). The `--minutes` flag overrides it
for testing.

### The setting

`StoreSettingDefinitions` gains
`general.orders.abandoned_after_minutes`, an
int default 60, in the general group. Editable
from Store Settings.

### The waiting-page timeout

Dropped from 5 minutes to 3 minutes. Real STK
pushes complete in 15-60 seconds. A customer who
has not entered their PIN in three minutes is
usually not going to.

### The twenty-four-hour view

Three thresholds now work together:

  - 3 minutes:  the waiting page stops polling
                and offers "try another method"
  - 60 minutes: the abandoned-order cron cancels
                unpaid orders and releases stock
  - 24 hours:   the M-Pesa cleanup cron deletes
                stale pending requests

A customer who abandons at any point is handled.
The stock returns. The admin queue stays clean.

### The anchor-overwrite bug

The `findAbandoned()` patch's anchor was
`public function countByStatusGroups(): array`.
The insert placed the new method before that
line. The anchor's docblock sat above the line
and was not part of the anchor, so it survived.
But the anchor itself, once replaced, lost the
docblock that was attached to it. PHPStan
flagged `countByStatusGroups()` on the next
`composer check`.

Fixed with one docblock restoration. The method
was unchanged.

The lesson: an anchor that names a method
signature should include the method's docblock.
The docblock is part of the method's identity
for a patch. Pattern 23 (cascade check before
every patch) already names this; the specific
case is worth noting.
