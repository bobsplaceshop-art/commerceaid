None. Every file landed clean on first pass. PHPStan
level 8 reports zero errors at 254 files (six new files
over the previous 248). All three repositories resolve

The absence of bugs is not luck — it is the result of
three structural choices:

  1. The migration SQL was written against a 0333 read,
     not from memory. Every column type, index name,
     and constraint name matches an existing sibling.

  2. The models follow `Subscriber`/`SubscriberList`
     conventions exactly, including the defensive
     JSON-column decoding pattern.

  3. The repositories follow `SubscriberListRepository`
     conventions, including the `buildFilters()`
     private helper and the
     `array_merge(['store_id' => $this->storeId()],
     $data)` insert pattern.

## Decisions made

- **No explicit provider bindings.** The container
  resolves the three new repositories via ADR-018
  auto-construction. Verified by CLI smoke test. Adding
  explicit bindings would be dead code.

- **Soft delete on forms, hard delete on fields, hard
  delete on submissions.** Forms have audit value (a
  form deletion should be recoverable); fields have no
  separate audit value (they are configuration); and
  submissions are hard-deleted at the merchant's
  discretion (the status enum carries the archived
  state).

- **Payload as JSON, not key-value.** One row per
  submission. No schema change when a form adds a
  field. Two denormalised columns (`submitter_email`,
  `submitter_name`) cover the common filter case
  without querying JSON.

- **`nextSortOrder()` and `reorder()` use 10-step
  spacing.** New fields land at 10, 20, 30; a reorder
  rewrites sequentially with the same spacing. Room
  to insert between fields without rewriting the
  whole list.

- **`options_json` stores `{value, label}` pairs, not
  bare strings.** The CustomFields engine uses bare
  strings; Forms uses pairs. The divergence is
  deliberate: a form field's option often needs a
  display label different from its submitted value
  (e.g. `{"value":"us","label":"United States"}`).

- **`bulkUpdateStatus` and `bulkDelete` silently
  drop ids that do not belong to the current store.**
  Not an error; the caller does not need to know.
  The affected-row count returned reflects only
  rows actually changed.
