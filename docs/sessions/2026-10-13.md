- **The Forms 500 investigation.** The 500 that
  started the pipeline work turned out to be a
  WSL-to-Windows staleness issue. Every layer was
  individually proven correct:

  - The service works from CLI. `submit()` returns
    ok:true, creates a row.
  - The controller reaches the service. Three
    file_put_contents diagnostics confirmed it.
  - The service returns successfully from HTTP too.
    The [3] diagnostic wrote `{"ok":true,...}`.
  - The view renders. A later browser test produced
    the success panel without error.

  The failure was never reproducible after a full
  Apache restart. The pipeline now makes any future
  failure visible in one request instead of requiring
  the four-hour diagnostic chain this session ran.

  The service received the honeypot value and

## Bugs found

1. **Logger silently dropped entries.** Logger::log()
   returned early when logDir() returned null. The
   fallback to error_log() the docblock promised
   never fired. Every 500 since 2026-10-11 13:32 had
   been lost. Fixed in commit 1.

2. **is_writable() lies on the WSL/Windows bridge.**
   PHP's is_writable() reads the file attribute bit,
   not the ACL. It returns false on directories
   file_put_contents() can write to. A diagnostic
   proved storage/logs is writable by an actual write
   while is_writable() returns false. Fixed by
   removing the preflight from logDir() and trusting
   the write's return value.

3. **The custom error handler swallows logger
   warnings.** App::registerErrorHandling() converts
   every warning into an ErrorException. A warning
   from the fallback error_log() call would be
   re-thrown, caught by renderException()'s
   try/catch, and swallowed. Fixed by detaching the
   handler around the write chain with
   set_error_handler/restore_error_handler in a
   finally block.

4. **Conditional value input was free text.** Fixed
   by the wrapper + sync in commit 41bf5a3.

5. **`nul` file from Windows `curl -o NUL`.**
   Windows created a literal file named `nul` when
   the curl output was redirected to NUL. Removed
   with `rm -f nul`.

None of these were the Forms 500. That bug was
proven to be environment staleness. Documented as
part of the arc.

## Decisions made

- **Build the pipeline before fixing the 500.** The
  500 was blocking for two sessions. Building the
  pipeline took a session but made the 500
  diagnosable in one request. The decision paid for
  itself the moment the four favicon 404s appeared
  in the overlay.

- **The write itself is the authoritative permission
  check.** is_writable() is a preflight with a
  different answer on this environment. Removing it
  was the correct fix, not loosening it further.

- **Detach the error handler around the write.** The
  logger must not be able to trigger the exception
  pipeline it feeds. Silencing errors during the
  write chain is the correct boundary.

- **Read the log file for the debug endpoint, do not
  keep a rolling in-memory buffer.** The file is the
  source of truth. Reading the tail is fast enough
  for a dev endpoint. No new state to maintain.

- **Only return lines with a request_id.** CLI lines
  and static test lines are excluded. The endpoint
  serves HTTP debugging only.

## New patterns for REMEMBER.md

**Candidate: PHP's is_writable() is unreliable on
the WSL/Windows bridge.**

The file attribute bit and the ACL are two different
checks. is_writable() consults the first.
file_put_contents() consults the second. On a
Windows path created through WSL, the two can
disagree. The rule: never gate a write on
is_writable(). Attempt the write and inspect the
return value.

**Candidate: the custom error handler can swallow
the logger.**

If App::registerErrorHandling() converts warnings
into ErrorExceptions, any warning from the logger's
own write path becomes another exception. If
renderException() wraps the logger call in
try/catch, the second exception is swallowed and
the first never lands. The fix: detach the handler
around the logger's writes.

Both patterns are the shape PHPStan and the
prevenger cannot detect - they are runtime
environment interactions. They belong in
docs/REMEMBER.md.
