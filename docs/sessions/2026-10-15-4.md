## Worked on

### The four bugs that blocked PayPal

The round trip surfaced four distinct bugs. Each
was diagnosed from the log and the DB.

**Bug 1 — PayPal's capture endpoint rejected the
empty request body.**

The first captures returned HTTP 400 with
`Request is not well-formed, syntactically
incorrect, or violates schema.`

PayPalProvider::capture() sent an empty PHP array
`[]` as the payload. `json_encode([])` produces
`"[]"` (a JSON array). PayPal's capture endpoint
requires a JSON object `"{}"` even when there are
no capture overrides.

Fixed by sending `new \stdClass()`, which encodes
to `"{}"`. HttpClient::postJson() gained the
`array|\stdClass` union type so the new call
passes PHPStan.

After the fix the capture returned HTTP 201 with
the full capture object. The order went paid with
a `2KB...` capture id in `payment_reference`.

**Bug 2 — the tunnel SSL handshake failed.**

PayPal's event log showed the webhook delivery
attempts with:

    "reason_phrase": "not an SSL/TLS record;
     nested exception is
     io.netty.handler.ssl.NotSslRecordException"

Two attempts, `FAIL_SOFT` then `FAIL_HARD`. PayPal
could not complete a TLS handshake with the
tunnel URL.

External reachability was confirmed with
allorigins.win: `server: cloudflare`, `cf-ray`
header present, and the body was the expected
`{"error": "Empty body."}` from
`WebhookController::handle()`. The tunnel was
reachable from outside the network.

The failure was on the tunnel's edge state at the
moment PayPal attempted delivery. A cloudflared
restart cleared it. No code change.

**Bug 3 — Request::header() did a case-sensitive
lookup.**

Webhook signature verification was failing with
`webhook.signature-invalid` from `ip: ::1`. The
log showed no `POST /v1/notifications/verify-webhook-signature`
line — the code returned before that call.

A temporary diagnostic in `WebhookController::handle()`
and `PayPalProvider::verifyWebhook()` confirmed:

  - `$_SERVER` had every PayPal header:
    `HTTP_PAYPAL_TRANSMISSION_ID`,
    `HTTP_PAYPAL_TRANSMISSION_TIME`, and the rest.
  - The headers array the controller passed to
    `verifyWebhook()` was **empty**.

The producer (`Request::extractHeaders()`) title-cases
header names. `HTTP_PAYPAL_TRANSMISSION_ID` became
`Paypal-Transmission-Id`. The consumer
(`WebhookController::lowercasedHeaders()`) asked for
`PayPal-Transmission-Id` — with a capital `P` in
both syllables of the brand.

`Request::header()` did `$this->headers[$name] ?? $default`
— an exact string match. Every lookup returned
null.

Fixed by adding a case-insensitive fallback to
`Request::header()`. Header names are
case-insensitive per RFC 7230 section 3.2.

**Bug 4 — PayPal events recorded an empty
event_type.**

The webhook events table rows for PayPal had an
empty `event_type` column. `WebhookController::handle()`
read `$event['type']`. Stripe uses `type`. PayPal
uses `event_type`.

Fixed by reading `$event['type'] ?? $event['event_type'] ?? ''`.

## Decisions made

**The capture body is a JSON object, not a JSON
array.** PayPal's API requires it. The difference
between `[]` and `{}` in PHP is one class name.
That is the entire fix.

**Header names are case-insensitive.**
`Request::header()` now respects that. The fix
applies to every caller in the codebase, not just
the webhook path. Any prior latent case mismatch
silently starts working.

**The Stripe smoke case constructs a Request object
directly with its own headers array.** That is why
the case-sensitivity bug did not surface in the
smoke harness. A future smoke case should exercise
`Request::capture()` (or `extractHeaders()`) against
a synthetic `$_SERVER` array with a brand-
capitalised header, and assert that `header()`
returns the value. Logged as a follow-up.

**The tunnel is a development convenience, not a
production dependency.** Production hosting has a
real domain and a real certificate. Webhook
delivery works there without the tunnel. The
tunnel's occasional SSL edge-state failures are a
dev-environment concern.

## New patterns for REMEMBER.md

**A case-sensitive lookup against a
producer-generated key is a silent-failure class.**

The producer emitted `Paypal-Transmission-Id`. The
consumer asked for `PayPal-Transmission-Id`. Both
are valid strings. Neither is technically wrong.
But the exact-match lookup made them incompatible,
and nothing warned. The controller logged
`webhook.signature-invalid` — a message that
suggests a signature problem, not a key-case
problem. The actual defect took a temporary
diagnostic to name.

The lesson: when a producer builds keys
programmatically and a consumer hardcodes the same
keys, the two must be normalised to a shared form.
Case-folding, lowercasing, or a canonical
comparison. Never exact match on
programmatically-generated keys.

**A payload type that depends on encoding (`[]` vs
`{}`) is a silent-failure class.**

PHP's `[]` and `new \stdClass()` are both "empty".
They serialize differently: `[]` → `"[]"` (JSON
array), `new \stdClass()` → `"{}"` (JSON object).
Some APIs accept either. PayPal does not. The
error message is generic
(`MALFORMED_REQUEST_JSON`) and does not name the
empty-vs-empty distinction.

The lesson: when sending an empty payload to an
external API, check whether it wants a JSON array
or a JSON object. PHP does not distinguish. JSON
does. The type annotation on the transport method
(`postJson(array $payload)`) hides the difference.
