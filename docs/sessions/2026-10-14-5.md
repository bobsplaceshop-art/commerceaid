## Worked on

- **StripeProvider implements PaymentProvider.**
  Charge uses Stripe Checkout (the hosted redirect
  page). Refund uses POST /v1/refunds with the
  order's PaymentIntent id. Webhook verification
  reads the Stripe-Signature header and validates
  HMAC-SHA256 over "{timestamp}.{raw_body}" with a
  5-minute timestamp tolerance.

  One design decision the plan did not anticipate:
  the charge flow sets both `metadata[order_id]` on
  the Checkout Session AND
  `payment_intent_data[metadata][order_id]`. Stripe
  does not propagate session metadata to the
  PaymentIntent it creates. Without the second
  metadata path, the webhook handler's
  orderIdFromObject() would return 0 on every
  payment_intent.succeeded event, and the order
  would never be marked paid.

- **ChargeResult value object.** Four factories:
  redirected, charged, offline, failed. Symmetric
  to RefundResult from Session 2.

- **PaymentChargeService.** The charge wrapper.
  Called by CheckoutController::place() after the
  order is placed. Resolves the provider, calls
  charge(), returns a ChargeResult.

- **WebhookController.** The codebase's first
  webhook receiver. Reads the raw body, resolves
  the provider, verifies the signature, records
  the event in commerce_webhook_events with an
  idempotency key, calls handleWebhook(), and
  returns 204.

  Status codes: 200/204 on accept (whether or not
  the handler acted), 400 on signature failure or
  malformed payload.

- **WebhookEventRepository.** record(),
  existsByProviderEvent(), findById(),
  backfillOrderId(), markProcessed(). The unique
  key on (provider_key, event_id) is the
  idempotency guard at the database level.

- **StripeReturnController.** The customer-facing
  return handler. Reads ?order= and ?session_id=,
  verifies the Checkout Session against Stripe's
  API, writes the paid state when the webhook has
  not arrived, and redirects to the confirmation
  page.

- **Two webhook routes and one return route.**
  POST /webhooks/stripe and POST /webhooks/paypal
  in routes/commerce.php. GET /checkout/stripe/return
  in routes/storefront.php. All under the 'store'
  middleware. No CSRF on the webhooks - the
  signature is the security boundary.

- **CheckoutService payment-key validation is
  registry-driven.** The $allowed list was
  ['cod','bank_transfer','purchase_order']. It
  now accepts any key that resolves through
  PaymentProviderRegistry, plus the three offline
  keys. A forged POST of payment_method=stripe
  fails on a store that has not enabled Stripe.

- **CheckoutController::place() dispatches the
  charge.** Three branches: redirected (send to
  Stripe), offline (proceed to confirmation),
  failed (flash error, back to confirm).

- **App::loadRoutes() skips Session->start() on
  CLI.** session_name() throws after any byte
  reaches STDOUT on this PHP build. Every CLI tool
  that echoes progress before App::boot() would
  crash without the guard. The smoke harness, the
  seed workers, and the retry cron all benefit.

- **Two smoke cases.**
  - bin/smoke-cases/refund.php: path 2 switched
    from stripe to paypal. The stripe class now
    resolves; the registry-miss branch needs a key
    whose class does not exist yet.
  - bin/smoke-cases/stripe-webhook.php: signs a
    payment_intent.succeeded payload with the same
    HMAC-SHA256 scheme verifyWebhook() uses,
    dispatches through WebhookController::stripe(),
    and asserts the order is paid, the event row is
    recorded, and a second delivery is idempotent.
  - _fixtures.php::createOrder gains a
    $paymentStatus parameter. The payment_reference
    is only set when the provider is real and the
    order is paid.

## Bugs found

### The double-patch class

Three times in this session, a patch added the
same thing a prior patch had already added.

  1. The WebhookController use statement was
     inserted twice in CommerceServiceProvider.
     PHPStan caught it: "Cannot use ... as
     WebhookController because the name is already
     in use."

  2. The WebhookController singleton binding was
     added twice in the same file. PHPStan did not
     flag it - singleton() silently overwrites.
     A grep of the file showed both bindings.

  3. The 6 occurrences of ->status() in the webhook
     case were miscounted as 5 in the first patch
     attempt. The count guard aborted on the
     difference. The second attempt used the
     correct count.

The pattern: every patch was written from a
fragment read, not the whole file. When two
patches touched the same region without either
reading the current bytes first, the second added
what the first had already put there.

The fix that ended it: after every patch, grep -c
the intended unique token to confirm exactly one.
If the count is 2, the patch matched a block that
already existed.

### The Stripe metadata propagation bug

The charge flow set metadata[order_id] on the
Checkout Session. The webhook handler read
metadata.order_id from the PaymentIntent. Stripe
does not propagate session metadata to the
PaymentIntent. Every payment_intent.succeeded
would arrive with empty metadata, orderIdFromObject
would return 0, and the order would never be
marked paid. The webhook would silently succeed
with handled: false and leave the row unprocessed.

Fixed by setting payment_intent_data[metadata][order_id]
in addition to metadata[order_id]. The webhook now
reads the order id from the PaymentIntent's own
metadata.

### The ADR-018 empty-container trap

Resolving WebhookController through
$container->get(WebhookController::class) hits an
ADR-018 limit. build() reflects the constructor,
sees `Container $container`, and calls
$container->get(Container::class). That builds a
fresh empty Container rather than the real one.
Subsequent $this->container->get(...) calls inside
the controller run against the empty container and
re-enter build() for every dependency, eventually
hitting Database's untyped $config parameter.

Fixed by binding WebhookController explicitly:
$c->singleton(WebhookController::class, fn() => new WebhookController($c)).
The closure receives the real container.

The pattern: any class whose constructor takes
Container itself must be bound explicitly. The
codebase already does this for PaymentProviderRegistry.

### The fixture's paid-state assumption

The Stripe webhook case failed with:

  assertion 1: payment_reference is pi_smoke_a9092252,
  expected pi_test_29f0e34c537573c3

The fixture's createOrder set payment_status = 'paid'
unconditionally. The webhook handler's idempotency
guard reads:

  if ($order->paymentStatus === 'paid') { return; }

So the handler returned early with handled: true,
never wrote the PaymentIntent id, and the assertion
caught the mismatch.

The fix is in the fixture, not the handler. The
handler is correct: an already-paid order should
not be re-written. The fixture gained a
$paymentStatus parameter with a default of 'paid'.
The webhook case passes 'unpaid'.

The test failure was doing its job. It caught the
fixture's wrong assumption.

### The session_name CLI crash

The harness stopped after the seeders with no
summary and no error text. The app log showed:

  session_name(): Session name cannot be changed
  after headers have already been sent
  ... App.php(307) ... Session->start()
  ... App.php(99)  ... App->loadRoutes()
  ... App.php(78)  ... App->bootstrap()
  ... bin/smoke.php(221) ... App::boot()

App::loadRoutes() called Session->start()
unconditionally. On CLI, PHP CLI's headers_sent()
check returns true once any byte has been written
to the STDOUT stream - even bytes inside an
ob_start() buffer on this build. The harness's
ob_start() did not prevent it.

Fixed by guarding Session->start() with a
PHP_SAPI !== 'cli' check inside loadRoutes().
Sessions are an HTTP concern; a CLI process has
no cookies and no headers.

The fix removes the crash for every CLI tool in
the codebase: the smoke harness, bin/send-emails,
bin/retry-refunds.

## Decisions made

- **Checkout over PaymentIntent.** The plan
  described both Stripe Checkout (the hosted
  redirect) and PaymentIntents (Stripe Elements)
  in the same flow. Those are two different Stripe
  APIs. The charge uses Checkout - it matches the
  redirect_url return shape the interface's
  charge() docblock specifies, and it requires no
  client-side JS.

- **payment_failed does not transition the order.**
  The plan's state table says payment_failed →
  mark failed. The handler records the event and
  returns handled: true without writing the order
  state. The order stays 'unpaid' so the customer
  can retry with a different card. A 'failed'
  order cannot be retried against the same order
  number.

- **Any class whose constructor takes Container
  must be bound explicitly.** ADR-018 auto-
  construction builds a fresh empty Container
  rather than the real one. PaymentProviderRegistry
  already followed this pattern; WebhookController
  joins it.

- **The webhook idempotency is at the row level.**
  The unique key on (provider_key, event_id)
  enforces one row per event. The controller
  checks existsByProviderEvent() before calling
  the handler. A re-delivered webhook is a no-op
  at the controller.

- **StripeReturnController verifies the session.**
  When the customer lands on the return URL, the
  controller reads the Checkout Session from
  Stripe's API and writes the paid state if the
  webhook has not arrived yet. Both paths are
  idempotent against each other.

- **The CLI session guard is a codebase-wide fix.**
  Not a workaround in the harness. The guard lives
  in App::loadRoutes(); every CLI tool benefits.

## New patterns for REMEMBER.md

**A patch that adds a discrete piece of code
must verify the count after.** After adding a
use statement, a binding, or any single-instance
construct, grep -c the token to confirm exactly
one. If the count is 2, a previous patch already
added it, and the current patch duplicated it.
The check takes one second. It prevents the
three-duplicate problem this session had.

**ADR-018 auto-construction has a Container
parameter trap.** A class whose constructor
takes Container itself will be built with a
fresh empty container, not the real one.
Subsequent $this->container->get() calls inside
the class re-enter build() for every dependency
and eventually fail on the first class with an
untyped parameter. Every such class needs an
explicit binding: $c->singleton(Class::class,
fn() => new Class($c)).

**The CLI SAPI does not respect ob_start() for
session_name().** PHP CLI's headers_sent()
returns true once any byte reaches STDOUT,
including bytes in an active output buffer.
App::loadRoutes() must guard Session->start()
with PHP_SAPI !== 'cli'.

## Plan amendment

The plan's Session 3 section named both Stripe
Checkout and PaymentIntent in the flow. They are
two different APIs. The charge uses Checkout.

The plan's state transition table says
payment_intent.payment_failed → mark failed. The
handler does not transition the order. The order
stays 'unpaid' for retry.

Both are recorded in the plan's Post-session
updates section.
