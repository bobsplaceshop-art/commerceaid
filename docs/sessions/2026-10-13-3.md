  Orders, customers, inventory, reviews, forms

  `ra-hide-sm` usage was inert.

- **The Logs hub.** One sidebar entry replaces two.
  Four tabs in one screen: Overview, Activity Log,
  System Logs, Audit Trail. A sub-nav rail mirrors
  the Setup hub's. `LogController` merges the logic
  from the two retired controllers.

  The three data streams are distinct:
    - `core_activities` — business timeline, human
      sentences, written by `ActivityLogger::log()`.
    - `storage/logs/app.log` — developer log, written
      by `Logger`.
    - `core_audit_logs` — raw HTTP audit, written
      automatically by the middleware.

  The merchant reads the Activity Log. The developer
  reads the other three. The tab labels reflect the
  audience.

- **Store-aware logging.** Every log row now records
  which store the action happened in. Both tables had
  a `store_id` column from migration 0101 but neither
  writer populated it. The middleware and the
  ActivityLogger now read the store context and write
  the column.

  New interface: `Platform\Context\StoreContextInterface`.
  Platform cannot import Commerce's `StoreContext`
  class. The interface declares the two methods
  Platform needs (`idOrNull()`, `has()`), and Commerce
  implements it. Container binds the interface to the
  existing singleton.

  Migration 0338 backfills 868 existing audit rows to
  the only store on record.

- **Two pipeline refinements from the morning.**
  Unmatched routes no longer log (the browser's
  favicon request and every extension's source-map
  request were writing hundreds of useless
  `Page not found` lines). The admin layouts gained a
  `<link rel="icon">` so the browser stops requesting
  `/favicon.ico` at all.

- **A cascade check miss on the migration.** The first
  attempt (0337) tried to add a `store_id` column
  that already existed. Migration 0101 had added it
  to both tables months earlier. The cascade check
  read only the migrations that created the tables,
  not the ones that altered them later. 0337 was
  deleted; 0338 ships the backfill only.

## Bugs found

1. **`data-responsive` was on the table, not the
   wrapper.** The wrapper is the element with
   `overflow-x: auto`; the attribute must be on it.
   Six files had no wrapper at all. One file used
   Bootstrap's `.table-responsive`. All 35 admin
   tables now sit inside a
   `.ra-table-responsive-wrap[data-responsive]`.

2. **`ra-hide-sm` was inert on 22 tables.** Only the
   inventory table had a rule that actually hid the
   column. The general rule at 899px landed with the
   card treatment.

3. **Extension 404s filled the log.** Every Chrome
   extension that injects a stylesheet link produced
   a `Page not found` line at exception level on
   every page load. Hundreds of rows, no signal.
   Fixed by the unmatched-route filter.

4. **The favicon 404 fired on every admin page.** No
   `<link rel="icon">` in the admin layouts. The
   browser defaulted to `/favicon.ico`. Fixed by the
   layout link plus the unmatched-route filter.

5. **Migration 0337 duplicated an existing column.**
   Migration 0101 had already added `store_id` to
   both log tables. The cascade check read the
   creating migrations only. See the pattern below.

6. **`git mv` on untracked files silently fails.**
   The two settings views were uncommitted when the
   move command ran. Plain `mv` was correct. The
   files landed in the second commit instead of the
   first.

7. **The first Logs hub commit's message lied.** It
   named `activity.php` and `audit.php` as moved
   files. The diff contained only four of the six.
   The two remaining views landed in commit 2. Noted
   in commit 2's message.

## Decisions made

- **The Logs hub is one screen, four tabs.** Not
  four sidebar items. The sub-nav rail pattern from
  Setup is general — the class names are historical
  but the shape is reusable. Adding a fifth log type
  later is one `TAB_META` entry and one view file.

- **Three data streams, three tabs.** `core_activities`
  (merchant timeline), `app.log` (developer log), and
  `core_audit_logs` (raw HTTP audit) are not merged.
  Each has an audience. The Overview tab counts all
  three; the detail tabs show one each.

- **Store-aware logging via a Platform interface, not
  a Commerce import.** `Platform\Context\StoreContextInterface`
  is the boundary. Commerce implements it. The
  container binds it. Platform never imports Commerce.

- **`ActivityLogger::log()` gained an optional
  parameter.** Not a required one. Zero cascade to the
  eleven call sites across three consumer services.

- **The migration was split.** 0337 (add the column)
  was deleted. 0338 (backfill the data) ships. The
  column already existed.

- **The Audit Trail and System Logs stay
  developer-facing.** The merchant reads the Activity
  Log. The other two tabs are for support and
  engineering.

## New patterns for REMEMBER.md

**The cascade check has four directions.**

Downstream (who calls this), upstream (what this
depends on and what is already true in the
environment), siblings (what else is like this),
perpendicular (what is the current state of the
object being changed).

Most misses are in directions 2 and 4. They do not
show up in a grep for the symbol being changed. They
require reading the schema, the config, or the
current state of a resource.

Where we hit it: migration 0337 tried to add a
`store_id` column that migration 0101 had already
added. The downstream check (grep for the table
name) found only the migrations that created the
tables. The upstream/perpendicular check would have
run `DESCRIBE core_audit_logs` and seen the column.
Ten seconds saved.

Rule going forward: **a change to the database is a
change to an existing part of the project.** Read
the current schema before writing a migration.

**`git mv` requires the file to be tracked.**

Both the settings views were uncommitted when the
move ran. `git mv` returned "not under version
control" and the file stayed put. Plain `mv` was
correct. The tell: after a `git mv`, `git status`
shows a rename (`R`) unless the source was
untracked.

Rule: before `git mv`, check `git status` for the
source. `??` means untracked — use `mv`, then
`git add` the destination.

## Session in the larger arc

The Logs hub is the piece of the pipeline that was
missing. The morning built the pipeline — three-tier
logger, request IDs, structured exceptions, the debug
endpoint. This session built the surface that the
merchant and the developer actually read.

Two audiences, one screen, four tabs. Same shape the
Setup hub uses for its own sub-sections. Reusable.

The store-aware logging closes a gap that would have
become harder to close later. Every row in both log
tables was silently unattributed. The middleware had
the store context all along. Now it uses it.

Migration 0101 is the reason this was possible
without a schema change. It anticipated the
multi-store future five months ago. The writers just
never caught up. This session closed the loop.

The session was long. The arc is coherent: the same
"make it work at every width, make every row carry
its context" thread runs from the card treatments
through to the store column. Each piece is small.
Together they are the difference between an admin
panel that works on desktop and one that works
everywhere the merchant uses it.
