## Worked on

- **The grand total was overcharging every German order.**
  The six-step pricing sequence computed
  `grandTotal = taxableBase + taxTotal + shippingTotal`
  unconditionally. That formula is correct for exclusive
  pricing (US-style). It double-counts for inclusive pricing
  (German PAngV). A cart of 8,100 gross at 19% inclusive
  produced 9,393.28 - the customer was being shown a total
  19% above the displayed price. Fixed by having TaxService
  return `inclusive_total` and `exclusive_total` alongside the
  overall total, and by changing the grand total formula to
  add only the exclusive portion on top of the taxable base.

- **Migration 0326 was never committed.** It added
  `commerce_products.tax_rate_override_percent` and had been
  applied to the dev database during the previous session, but
  the file was sitting untracked in the working tree. Committed
  it as `1987fbe` so a fresh clone would not fail on 0327
  (which requires the column 0326 creates).

- **Per-product tax rate override with an explicit
  inclusive/exclusive flag.** Migration 0327 adds
  `tax_rate_override_inclusive` (TINYINT(1) NULL). Three
  states: NULL = inherit from the class rate, 0 = exclusive,
  1 = inclusive. Admin Pricing tab gained a three-state select
  below the percent override field. `TaxService` reads the
  flag with three-state precedence. The storefront PAngV note
  is now computed by a new `tax_note()` helper that reads the
  tax_classes array and produces "inkl." or "zzgl." (or both,
  for a mixed cart) - replacing the hardcoded "inkl." string
  that reported inclusive wording even when the total was
  exclusive.

- **Admin form hints were almost invisible on the dark theme.**
  `.ra-content .form-text` bound to `--ra-muted`, which on the
  dark theme resolves to `#94a3b8` - medium grey on the navy
  card surface. Contrast ratio ~2.9:1. New `--ra-text-soft`
  theme variable: `#cbd5e1` dark (contrast ~8.4:1), `#5b6675`
  light (contrast ~6.1:1). `.form-text` now binds to it. Labels
  keep their existing `--ra-text` binding. The visual hierarchy
  is preserved.

- **The product editor rendered a cream panel on the dark
  theme.** Twelve admin views and two `main.css` rules
  reference `--ra-card-bg` and `--ra-fg`. Neither variable was
  defined anywhere. Every reference fell through to a hardcoded
  light-theme fallback (`#ffffff`, `#0f172a`), so the product
  editor's tab content was cream. Fixed by adding the two
  aliases to all three theme blocks, bound to their canonical
  equivalents (`--ra-surface`, `--ra-text`).

## Bugs found

1. **Inclusive tax double-counted in the grand total.** The
   formula was written for exclusive pricing. German stores
   were overcharged 19% on every order that reached the
   payment step. The cart page hid the bug (empty country
   code, no tax resolved). The checkout payment step exposed
   it (address known, rate resolved). Fixed in `00d6e81`.
   Documented as Pattern 32, third manifestation.

2. **Migration 0326 was never committed.** Untracked file
   sitting in the working tree. If a fresh install ran 0327
   without 0326, the ALTER would fail on the `AFTER
   tax_rate_override_percent` clause. Fixed in `1987fbe`.

3. **The override had no inclusive/exclusive choice.** Migration
   0326's override inherited `is_inclusive` from the class
   rate. When the class had no rate for the destination, the
   flag fell to `false`, forcing exclusive pricing on a store
   whose convention is inclusive. Fixed in `464ed45`.

4. **The PAngV note lied.** Both `confirm.php` and
   `payment.php` built the "inkl. X% MwSt." string by hand
   from the tax_classes array, hardcoding the "inkl." word
   regardless of the regime. A customer saw "inkl. 7% MwSt."
   under a total that had just added 7% on top. Fixed in the
   same commit as the override.

5. **Form hints failed WCAG AA on the dark theme.**
   `.form-text` used `--ra-muted` at `#94a3b8` on the navy
   card. ~2.9:1 contrast ratio. Fixed by the new
   `--ra-text-soft` variable at `#cbd5e1`. Different commit;
   different concern.

6. **Twelve admin views referenced undefined CSS variables.**
   `--ra-card-bg` and `--ra-fg` were never defined in any
   theme block. Fallbacks `#ffffff` and `#0f172a` were light
   theme values. The product editor's cream tab panel on dark
   theme was the visible symptom. Fixed in `a5bdf74`.

7. **PHPStan caught a dead null check in TaxService.**
   After the outer `if ($override !== null)` guard, the inner
   ternary `$product !== null ? ... : null` was always true
   on the left branch. The outer guard already proved
   `$product` was non-null. Removed the redundant check.
   Caught at commit time before the code shipped.

## Decisions made

- **Per-line model, not binary regime.** Every cart line
  contributes to the grand total according to its own tax
  class's `is_inclusive` flag. A cart with mixed regimes
  (some inclusive, some exclusive) computes correctly. No
  refusal. This is the industry pattern (Avalara, Magento,
  WooCommerce all handle per-line tax regimes).

- **Three-state flag, not a boolean checkbox.**
  `tax_rate_override_inclusive` is NULL / 0 / 1, matching
  the three states the merchant actually needs: "inherit from
  the class", "explicitly inclusive", "explicitly exclusive".
  A checkbox would lose the "inherit" default.

- **Product-level only, not variant-level.** The current
  schema has `tax_class_id` at the product level. A variant
  override column without moving `tax_class_id` to the same
  grain would create two tax-resolution inputs at different
  granularities. If variant-level tax is ever needed, it is
  a bigger migration. Deferred.

- **Alias variables as a compatibility shim.**
  `--ra-card-bg` and `--ra-fg` were never defined, but twelve
  views reference them. Defining the aliases in the theme
  blocks fixes every view without touching a single view file.
  A future hygiene pass will replace the aliases with
  `--ra-surface` and `--ra-text` across all views. That pass
  is not urgent; the aliases work correctly now.

- **Plan doc updated by append, not rewrite.** The 008K.5
  plan's formula was wrong for inclusive pricing. The plan is
  the historical record of what was intended. The Post-session
  update section preserves the original body and records what
  was found. Same pattern as the 008G.4a.2 plan's Session 3
  Close Summary.

- **Python-heredoc protocol, not awk.** A session 3 patch
  attempt with awk failed because the heredoc contained
  `fn ($r) =>` and the shell parsed the `(`. Python with a
  heredoc handles every case cleanly. Use it as the default
  for any patch that touches PHP.

- **Split per-block anchors for CSS variable patches.** A
  single anchor tried to match two light-theme blocks, but
  one is inside `@media` and has 8-space indentation while
  the other has 4-space. The count check rejected it. Split
  into one anchor per block. Cleaner failure mode, clearer
  intent.

## Session in the larger arc

008K.5 was the last sub-stage of 008K. The admin surface
completion that motivated the whole stage - Orders,
Customers, Users, Roles, Coupons - is now complete. The
platform has merchant-facing surfaces for everything the
customer-facing half already had.

The pricing engine shipped as one coherent stage because
coupons, tax, and shipping all compute into the same totals
formula. The coupling principle from the roadmap said ship
them together or rewrite. They shipped together, and the
browser test caught what a static analysis pass could not:
the formula was correct for one pricing regime and wrong
for another.

Pattern 32 gained a third manifestation. The pattern now
covers three distinct failure classes:

  - key shape drift between producers
  - a WHERE clause that enforces an invariant the
    schema does not
  - a formula written for one regime applied to another

All three are the same underlying failure: a consumer
assumes a contract the producer does not enforce. The
pattern is now the codified response to that class of bug.
