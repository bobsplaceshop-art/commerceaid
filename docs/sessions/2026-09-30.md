## Decisions made

- **Bound on write, not on read.** Trim to 50 after every
  upsert. Two queries per product page load. Documented
  as Decision 1 in the plan.
- **No bot, prefetch, or crawler filter.** Every product
  detail page load records a view. Documented as Decision
  2.
- **The 24h dedup window emerges from the schema's UNIQUE
  key, not from code.** Documented as Decision 3.
- **The guest session array is ordered, not a set.**
  Re-viewing moves a product to the front, mirroring what
  the DB does with viewed_at. This differs from the
  wishlist session shape.
- **`record()` swallows all exceptions.** A broken
  recorder cannot break the product page. The call site
  therefore needs no try/catch. Cleaner contract than the
  wishlist service, which lets exceptions through.
- **Reused `.sf-wishlist-grid` CSS for the recent page.**
  The class name is historical; the shape is a generic
  account-page product grid. A future refactor (when 008G.3
  wants the same grid) will rename it. Documented as a
  comment inside recent.php.

under Planned Stages.

The message center is a different shape from the last two
sub-stages. Not a CRUD list. It reads from
`core_notifications` (already exists from Platform) and
presents them in tabs:

  - System Message    - platform announcements
  - Order Updates     - order status transitions
  - Promotions        - opt-in marketing

New ground vs the wishlist and recent builds:

  - Reads an existing shared table (core_notifications),
    not a new commerce_* table.
  - Has an unread count that feeds the account sidebar
    (the sidebar already renders a `badge` field on nav
    items - the wishlist and recent pages never used it).
  - Mark-as-read, bulk mark-all-read. First write action
    on a Platform-owned table from a Commerce controller.
  - Preferences page feeds into NotificationRuleService
    (Platform). This is the first cross-layer integration
    in the storefront build.

Read `docs/stages/008g.3_message-center-plan.md` (to be
written) before touching anything. The 008G.3 stage is
where the Commerce/Platform boundary gets tested for the
first time in a storefront-facing context.
