## Worked on

- **Store-scoped branding: the concept.** The
  store's name lives in `commerce_stores.name`.
  The merchant edits it in Setup > Business. Before
  this session, several surfaces read
  `config('branding.product_name')` directly, and
  several hardcoded the literal string. A rename
  did not propagate.

- **Two new helpers in `app/Helpers/functions.php`.**

  `brand_name(?Store $store = null): string`
    1. `$store->name`
    2. `config('branding.product_name')`
    3. `'Store'`

  `brand_short(?Store $store = null): string`
    1. `$store->pwaShortName`
    2. `config('branding.product_short')`
    3. `brand_name($store)`

  Pure functions. Store resolution is the caller's
  job. Every branded surface passes the resolved
  store, or `null` where no store is in scope (the
  login page, some error paths).

- **`AdminController::render()` now injects `$store`.**
  The admin base class had no store in scope — every
  admin view fell back to config. It now resolves
  the store once per request (mirroring
  `StorefrontController::resolveStore()`, which is
  private to its own class) and passes it into the
  layout data.

- **Every branded view calls the helper.** Layouts,
  partials, error pages, the storefront home hero,
  the sidebar brand card, the campaign preview
  header. Config stays as the fallback.

- **Email templates use the store name.**
  `AdminUserController` and `AuthController` pass
  `brand_name(...)` into `app_name` and the subject
  lines. The invitation and password-reset templates
  fall back to `brand_name(null)` instead of a
  hardcoded string. `password-reset.php` carried a
  "Recruit Aid" leftover from the framework import;
  now fixed.

- **The failure that motivated the error-page
  hardening.** The first append of the two helper
  functions to `functions.php` did not land. The
  heredoc wrote nothing. The next fourteen files
  were edited to call `brand_name()`. The site
  500-ed on every page that rendered a layout —
  including the error pages, which could not render
  because they also called the missing function.
  Two error references (`ERR-b9abf2`, `ERR-50e013`)
  and a chain of "Call to undefined function
  brand_name()" log lines named the exact file and
  line of every failure.

  The diagnosis was the log, not a guess. `grep
  'function brand_name' app/Helpers/functions.php`
  returned nothing. The second append landed, with
  inline verification (`wc -l`, `grep`, and a
  `php -r` autoload check) before any other file
  was touched.

- **`App::renderException()` now sets `$brandName`
  for the error views.** Guarded by
  `function_exists('brand_name')` so a bootstrap
  failure that has not yet loaded the helpers
  cannot make the error page itself fail. The
  four error views (`403.php`, `404.php`,
  `500.php`, `offline.php`) read `$brandName` with
  an `htmlspecialchars(..., ENT_QUOTES, 'UTF-8')`
  guard. `htmlspecialchars` is a PHP builtin; it
  cannot be missing even in the worst case.

## Decisions made

- **The store is the source of truth.** `commerce_stores.name`
  is what the merchant edits. Config is the fallback
  for contexts without a resolved store.

- **The helpers take a `?Store` argument.** They do
  not resolve the store themselves. That keeps them
  pure and testable. Store resolution lives with the
  caller.

- **`AdminController::resolveStore()` is a copy of
  `StorefrontController::resolveStore()`, not a
  shared trait.** Two base classes, no common parent,
  nine lines each. Extracting a trait would add
  indirection for two call sites.

- **The error views use `htmlspecialchars` directly,
  not `e()`.** `e()` is defined in `functions.php` —
  the same file whose absence we are guarding
  against. `htmlspecialchars` is a PHP builtin.

- **The config file is the fallback, not the
  source.** It carries the correct name for the
  contexts without a store, but it is not what the
  merchant edits day to day.

- **Three hardcoded strings remain.** Listed in the
  commit message as known follow-ups. Not fixed in
  this commit to keep the diff coherent and to give
  a clean reset position.

## New patterns for REMEMBER.md

**A `cat >>` heredoc that writes nothing can leave
no trace.** The first append of the helpers to
`functions.php` produced no output, no error, and no
file change. `tail` of the file returned the same
content it had before the append. Because I read the
same bytes twice and treated the second read as
confirmation of a change that never happened, the
failure propagated to fourteen downstream files.

The rule: after every heredoc write, `grep` for a
string the heredoc introduces. An empty grep is a
stop sign, not a green light. Not a check that the
file exists — a check that the new content is in the
file.

**The error page is the last line of defense, and it
must not be able to fail.** A bootstrap failure that
unloads the helpers also makes the error page
unrenderable if the error page calls the missing
function. Guard every helper call inside an error
path with `function_exists` or use PHP builtins
(`htmlspecialchars`, `strlen`) that cannot be
missing.

**WSL `curl` to `localhost:8084` returns `000`; the
browser works.** This is the WSL-to-Windows loopback
behavior. `curl` from WSL does not reliably reach a
Windows-hosted Apache on `localhost`. The fix: run
`curl` from Laragon Terminal. Or test in the browser,
which is the actual runtime being verified anyway.
