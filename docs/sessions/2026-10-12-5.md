## Worked on

- **Wave 1 — check-theme.php.** Reads every `--ra-X:`
  definition from `public/assets/css/*.css` and every
  `var(--ra-X)` reference from the CSS files plus every
  `.php` view under `resources/views/`. Reports orphans
  (references with no definition) and unused definitions
  (definitions with no reference). Both fail the check.

- **Wave 1 found two orphans.** `--ra-surface-alt` was
  referenced by `.ra-tab-count` with no definition. The
  fallback fired on every theme. Replaced with
  `--ra-surface-3`, which is defined in all three theme
  blocks. `--ra-cream` was referenced by
  `.ra-variant-slot-thumb` with no definition. The
  hardcoded fallback `#f4f5f7` rendered wrong on dark
  theme. Also replaced with `--ra-surface-3`. Neither
  bug was caught by four manual audits the same day. The
  parser caught both. Committed at `8f0eddf`.

- **Wave 2 — check-css.php.** Parses every inline
  `<style>` block in the views and every `.css` file
  under `public/assets/css/`. Validates brace balance,
  declaration shape (property colon value semicolon), and
  no `@media` blocks in view inline styles.

- **Wave 2 found nine structural issues.** Five were
  inline `@media` blocks in admin edit views - the
  sticky action bar copies. Four were missing semicolons
  that turned out to be false positives (multi-line
  declarations where the terminator was on the next
  line). The parser was fixed to skip bare-property
  lines. Then the five inline `@media` findings forced
  the sticky bar consolidation: six views carried
  identical inline copies of `.ra-sticky-actions`,
  `.ra-sticky-actions-inner`, `.ra-sticky-spacer`, and
  `.ra-btn-sm`, each with its own `@media` block. All
  moved to `main.css` (now `main-v2.css`). Committed at
  `688d0f9`.

- **Wave 3 — check-html.php.** Four structural rules
  plus one warning. Nested `<form>`, modal partial
  included inside a parent form, unescaped JSON in a
  `data-*` attribute, unbalanced `data-*` attribute
  quotes. Warning: `<table>` missing `data-responsive`.
  Committed at `8a73b00`.

- **Wave 3 found zero real bugs.** The nested-form
  class is dormant; every modal include is currently
  placed as a sibling of any page form. The data-*
  escaping pattern is correct across all 273 instances.
  The checker exists to catch the next violation, not
  the last one.

- **Wave 4 — the aggregator and composer wiring.**
  `bin/check.php` runs the three checkers as
  subprocesses, captures output, prints a summary.
  `composer.json` gains a `prevenger` script and extends
  `check` to run it. Committed at `039f06c` and
  `b3d6409`.

## Bugs found

### Real bugs fixed

1. **Two orphan theme variables.** `--ra-surface-alt` and
   `--ra-cream`. Both referenced, neither defined. Both
   silently fell back to a hardcoded colour. One worked
   by accident on light theme, the other rendered the
   wrong colour on dark theme. Fixed at `8f0eddf`.

2. **Five duplicate inline `@media` blocks.** The sticky
   action bar CSS was copied into six admin edit views.
   Each copy carried its own `@media (max-width: 900px)`
   block. The rule was correct in principle but wrong in
   placement. Consolidated into `main-v2.css`. Fixed at
   `688d0f9`.

### False positives, fixed in the checkers themselves

3. **check-css.php multi-line declaration.** The parser
   read the line ending in `background:` as a declaration
   and reported the missing semicolon. The semicolon was
   on the next line. Fixed by adding a bare-property
   check to the parser.

4. **check-html.php docblock reading.** The docblock
   inside `products/edit.php` mentioned `<form>` in
   prose. The parser counted it as a real form open. Two
   errors and a cascading modal-depth error resulted.
   Fixed by adding `strip_php_regions()` to blank every
   PHP region before scanning for tags.

### Process bug, cost three hours

5. **Literal `?>` inside a `//` comment closed the PHP
   block.** The first write of `check-html.php` had four
   comment lines documenting the data-* escaping
   pattern with literal short-echo examples. PHP closed
   the block at the first `?>`, and the rest of the file
   became HTML output. `php -l` reported "Unclosed '{'
   on line 249... on line 467" - a line far from the
   actual problem. Three failed fix attempts before the
   correct diagnosis. Documented as Pattern 39 in
   `docs/REMEMBER.md`.

## Decisions made

- **The prevenger is a set of reporters, not a fixer.**
  Every checker prints findings and exits non-zero. None
  modifies a file. Fixes are applied by hand in a
  separate patch. Same shape as PHPStan.

- **Hard errors vs warnings.** Structural bugs (nested
  forms, broken CSS, orphan variables) are hard errors
  and fail the check. Missing `data-responsive` on
  `<table>` is a warning because no consumer reads the
  attribute yet. It flips to a hard error when Stage 014
  Session 1 ships the breakpoint system.

- **No deferrals.** The `@media` findings from check-css
  were originally going to be warnings until Stage 014
  Session 3 landed the sticky bar consolidation. That
  deferral was rejected. The consolidation happened in
  the same session as the check. Stage 014 Session 3
  becomes a verification pass, not a fix pass.

- **One aggregator, not three composer entries.** Adding
  a fourth checker is one line in `bin/check.php`, not
  two edits in `composer.json`. The aggregator is the
  prevenger's single entry point.

- **Warnings pass through the aggregator unfiltered.**
  The 36 `<table>` warnings print in full inside
  `composer check`. A future `--quiet-warnings` flag on
  `bin/check.php` can suppress them if they become
  noise. Not today.

- **Python with heredoc for all patches.** The awk
  attempt during the earlier product-page bug arc failed
  on shell parsing of `fn ($r) =>`. Python is the
  codebase's default patching tool now.

- **Two-step patch for the check-html.php fix, not one
  big patch.** The first attempt combined helper
  insertion and shadow-replacement in one script and
  failed on an anchor mismatch. The working approach was
  two separate commands, each verified before the next.
  Extends Pattern 20.

## New patterns for REMEMBER.md

**Pattern 39 - Literal `?>` inside a PHP comment closes
the PHP block.**

Documented in full in `docs/REMEMBER.md`. The specific
tell: `php -l` reports an unclosed block far from the
actual problem. The detection: `grep -n '?>' <file>`.
The fix: describe the pattern in prose, never use the
literal short-echo characters in a comment.

## What the prevenger catches today

Three layers of structural discipline, running on every
`composer check`:

  Theme contract:
    - Definition without reference (unused).
    - Reference without definition (orphan).
    - Reports the count of each.

  CSS structural integrity:
    - Unmatched braces.
    - Declaration missing terminating semicolon.
    - `@media` blocks in view inline styles.

  HTML structural integrity:
    - Nested `<form>` elements.
    - Modal partials included inside a parent form.
    - Unescaped JSON in `data-*` attributes.
    - Unbalanced `data-*` attribute quotes.
    - Warning: `<table>` missing `data-responsive`.

## Session in the larger arc

The prevenger closed the structural-tooling gap. Before
this session, the build had PHPStan for type errors and
`bin/lint.php` for syntax. Neither could catch an orphan
CSS variable, a broken brace, or a nested form. The
prevenger extends the PHPStan pattern to structural
integrity.

The four-wave shape is intentional. Wave 1 wrote the
theme contract checker and fixed the bugs it found.
Wave 2 did the same for CSS. Wave 3 for HTML. Wave 4
wired it all together. Each wave was a self-contained
commit; each wave's checker exists because the previous
wave proved the pattern worked.

The bugs the prevenger caught in Wave 1 (two orphan
variables) and the bugs the sticky bar consolidation
fixed in Wave 2 (five duplicate inline blocks) were both
real. Four manual audits the same day missed them. The
parser did not.
