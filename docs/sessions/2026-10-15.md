- **The admin config tab.** Settings > Payments
  now renders a provider list above the credential
  fields:

    - One row per provider. The provider key
      renders as muted code. The label comes from
      the provider instance, not a second catalog.
    - An enabled toggle per row. Writes
      `commerce_store_payment_methods` via
      `PaymentMethodRepository::set($key, bool, int)`.
      The `save()` method reads the toggle from the
      POST (`payments__{key}__enabled`) and writes
      each provider in registry order.
    - A Test connection button per row.

  The credential fields below the provider list
  were already rendered by the generic settings
  form - the four `payments.stripe.*` and four
  `payments.paypal.*` keys are declared in
  `StoreSettingDefinitions::DEFINITIONS` under
  `GROUP_PAYMENTS`. No new definitions were needed.

- **The button no longer lies.** The Test
  connection button was originally wired to
  `isConfigured()`, a local check that only
  confirmed the settings rows were populated and
  the provider class resolved. That is not a
  connection test. Calling it one is misleading -
  especially yesterday, when the tunnel was down
  and a "looks configured" flash would have
  asserted success on a broken connection.

  The button now makes a real outbound API call:

    - Stripe: `GET https://api.stripe.com/v1/balance`
      with the stored secret key. A 200 means the
      key is valid, the account is active, and the
      API is reachable. 401 = wrong or revoked key.
      402/403 = suspended or restricted. Network
      failure reported distinctly.

    - PayPal: the OAuth token handshake that every
      subsequent PayPal API call already requires.
      A 200 with an access_token means the client
      id and secret are valid for the configured
      mode. The token itself is never echoed.

  Both calls are read-only. No charges, no orders,
  no side effects. The response body is not echoed;
  only a merchant-readable summary.

- **The interface gained one method.**

    PaymentProvider::testConnection(): array{ok, message}

  Both providers implement it. Future providers
  must implement it too - that is the point of
  putting it on the interface rather than calling
  provider-specific methods from the controller.

  A separate `isConfigured()` check still runs
  first. It short-circuits the flow when the
  credentials are blank, with a message that names
  the missing fields. The network call only runs
  when there is something to test.

- **Registry gained `labels()`.**

    PaymentProviderRegistry::labels(): array<string,string>

  Returns the human label for every provider whose
  class exists, keyed by provider_key. The
  Settings tab uses it to render one row per
  provider. The label comes from the provider
  instance, not a second catalog.

- **Setup > Payments becomes a hand-off.**
  `SetupController::showPayments()` now redirects
  to `/commerce/ca-admin/settings?tab=payments`.
  The Setup sub-nav keeps its tab as a link into
  the real config. `TAB_META['payments']['real']`
  flips to `true` so the "SOON" badge is gone.

  `availablePaymentProviders()` - the static
  six-provider catalog that fed the stub - is
  removed. PHPStan flagged it as dead after the
  redirect replaced its only caller. Deletion was
  correct: no other site referenced it.

**`availablePaymentProviders()` became dead code** the
moment `showPayments()` started redirecting. Its only
caller was the stub render. PHPStan level 8 flagged it
as `method.unused` on the first `composer check` after
the redirect landed. Deleted in the same commit.

`api.stripe.com` from the Apache process on the first

## Decisions made

- **The Test connection button makes a real API call.**
  The alternative was to rename the button to
  something weaker like "Verify credentials" and keep
  the local-only check. Rejected - the button exists
  to answer the question the merchant actually has
  ("does the key on file work"), and a name that
  promises a connection test but does not test the
  connection is worse than no button.

- **`testConnection()` belongs on the interface.** Each
  provider knows its own "cheapest authenticated
  call" - Stripe uses `/v1/balance`, PayPal uses the
  OAuth handshake. The controller does not need to
  know which call. One method per provider, one
  caller in the controller.

- **Both calls are read-only.** No side effects.
  Testing the connection must never create an order,
  charge a card, or leave state behind. A merchant
  who clicks the button twenty times gets the same
  answer twenty times, with no residue.

- **The interface method returns a message, not just
  a boolean.** The flash needs to explain *why* a
  test failed - 401, unreachable, wrong mode. A
  boolean forces the controller to build the message,
  which means provider-specific knowledge leaks out
  of the provider. The provider knows best what its
  own error means.

- **Config lives in Settings, not Setup.** The Setup
  wizard is for first-run. Once the merchant is past
  the wizard, they configure in Settings. Two
  surfaces with different purposes. The Setup
  Payments tab points at the Settings surface rather
  than duplicating it.

- **The `.ra-paytab-*` class prefix, not
  `.ra-payment-*`.** A family of `.ra-payment-*`
  classes already exists in `main-v2.css` (the Setup
  stub view used them). The new classes get a
  distinct prefix so the two families do not
  collide or invite confusion when someone greps.

- **No `@media` block in the CSS.** The provider row
  uses `flex-wrap: wrap` so the key code and the
  test button stack naturally at narrow widths. A
  media query would work but `check-responsive.php`
  rule 1 flags inline `@media` blocks in views -
  and the block lives in the view's inline `<style>`.
  `flex-wrap` handles narrow widths without
  violating the rule.

## New patterns for REMEMBER.md

None this session. Two small observations, neither
worth a pattern:

- **Interface method additions are additive at the
  type level, but a required implementation.** Every
  concrete class implementing the interface must be
  updated in the same commit. This session updated
  both `StripeProvider` and `PayPalProvider`. If a
  third provider existed, it would break the build
  until it also implemented `testConnection()`.
  That is the correct outcome - the compiler enforces
  the contract.

- **PHPStan's `method.unused` is a real signal after
  a redirect replaces a caller.** The instinct when
  a method becomes unused is to consider whether it
  might be needed later. The correct answer here was
  to delete. Dead code accumulates. The only thing
  that ever calls it is a future grep wondering why
  it is there.
