## Bugs found

Two real bugs, both fixed.

1. **FileValidator rejected WebP.**

   The ALLOWED allowlist had no 'webp' entry. Uploading
   a WebP (which the pipeline itself produces) returned
   422 "contents do not match extension". The pipeline
   could not accept its own output. Fixed by adding
   `'webp' => ['image/webp']` to the allowlist.

   This bug had been latent since 008G.4a shipped.

2. **Featured and New arrival toggles always read as off.**

   The inline $val / $valBool closures in
   products/edit.php used $product->$key with the
   caller's snake_case key. The Product model uses
   camelCase. $product->is_featured returned null.
   $valBool returned false regardless of the DB value.

   Exactly Pattern 15 in docs/REMEMBER.md. The
   EditView::valClosure / valBoolClosure helpers exist
   to prevent this. The product editor had not been
   migrated. Fixed by swapping the two inline closures
   to EditView calls.

   Also deferred: five other admin views still use the
   inline closures (attributes, brands, categories,
   customer_groups x2). Migration to EditView is a
   hygiene pass.

3. **Sequencing regression: helpers not on disk when
   the consumer landed.**

   First File 15 attempt anchored on a function name
   that was not present. The patch script's
   sys.exit(1) fired; the helper was not written. The
   card partial was changed anyway (File 16). Every
   product card on the storefront silently vanished -
   view_partial() caught the resulting fatal and
   returned an empty string.

   Caught by the operator's browser test and the app
   log:

     ERROR: view_partial(..._product-card) failed:
     Call to undefined function product_picture_url()

   Recovered by reverting File 16, re-running File 15
   with a corrected anchor and immediate grep
   verification, then re-applying File 16.

   This is a real process failure, not a code bug.
   Documented as an extension to Pattern 20 in
   docs/REMEMBER.md.

4. **Placeholder SVGs not written.**

   The same File 15 script wrote two SVG heredocs to
   public/assets/img/. The directory did not exist (or
   the heredocs did not run for some other reason).
   `cat >` fails silently if the parent directory does
   not exist. The placeholder fetch returned 404.

   Fixed by `mkdir -p public/assets/img` then
   re-writing the SVGs. Verified with `ls -la` and a
   browser fetch (HTTP 200).

   Also folded into the Pattern 20 extension.

## Post-Close Bug Fix - Variants Redirect (still 2026-09-30)

**Symptom:** After clicking "Save all variations" on
the variations manager, the operator was redirected to
the product editor with a blank content area. The
variants appeared to have been deleted.

**Root cause:** `saveVariants()`, `regenerateVariants()`,
and `deleteVariant()` in ProductController redirected to
`/products/{id}/edit?tab=variants`. The product editor's
`$tabs` array in `edit.php` has six tabs (basic, images,
pricing, inventory, shipping, seo). There is no
`variants` tab. The variations manager is a separate
page at `/products/{id}/variants`.

Redirecting to `?tab=variants` produced a page where no
tab matched the requested key. Every tab rendered
inactive; every tab-pane stayed hidden. The operator saw
a blank tab-content area below the tab nav and
reasonably concluded the variants were gone.

**Actual state of the DB:** all 12 variants for product
1 remained `status = 'active'` through the entire
incident. Nothing was lost.

**Fix:** replace the phantom redirect target with the
real one in 5 controller locations and 1 view link.
`saveVariants()` line 725 already used the correct URL -
the other five callers did not.

**Pattern note:** This is a "route that exists in the
code but not in the routing table" class of bug. The
URL `/products/{id}/edit?tab=variants` was syntactically
valid and rendered a 200 response. The failure was
semantic: `activeTab` was set to a value that matched no
tab key. No error, no exception, no log entry - just
silent empty state.

Worth adding to REMEMBER.md as a sibling to Pattern 22
(prefix-match active state breaks on strict-prefix
routes). Both are "silent active-state mismatch" bugs.
The category is: the caller and the recipient disagree
about what identifiers exist.

## Post-Close Bug Fix - Variant Images Card (still 2026-09-30)

**Symptom:** The Images tab in the product editor did
not render the "Variant images" card even for products
with a Color axis (Red, Blue). The card was written in
File 24 but never appeared. No error, no exception, no
log entry. The console showed
`data-ra-variant-images-card` was absent from the DOM.

**Two stacked bugs. The first masked the second.**

**Bug A1 - variable shadowing.**

`_tab_images.php` iterated the axis values with
`foreach (... as $val)`. But `$val` is a closure defined
at the top of `edit.php` (line 21) and read by every
other tab: `_tab_basic.php`, `_tab_pricing.php`,
`_tab_inventory.php`, `_tab_shipping.php`,
`_tab_seo.php`. They are all `require`d in the same
scope by `edit.php`.

The moment `_tab_images.php` ran its loop, `$val`
became an array (the last axis value). The next require
in the chain, `_tab_pricing.php`, called
`$val('taxStatus', 'taxable')` on the array. PHP raised
"Array callback must have exactly two elements" - the
same class of error you would get if you called
`[$a, $b, $c](...)`.

Stack trace pointed to `_tab_pricing.php:5`. The bug
was in `_tab_images.php`. The `require` chain shares
scope; the error surfaces in the file that runs next.

Fix: rename the loop variable to `$axisValue`. The
docblock on `_tab_images.php` now documents the shared
scope and warns against shadowing `$val` or `$valBool`.

**Bug A2 - wrong key name.**

The loop read `$axisValue['id']`. But
`ProductVariantRepository::swatchAxesFor()` produces
value entries with key `attribute_value_id`, not `id`.
(The older `categoryVariantAxes()` uses `id`. Different
shapes, same concept.)

The `?? 0` fallback swallowed the missing key. Every
value read as 0. Every iteration hit
`if ($valueId <= 0) continue;`. `$colorValues` stayed
empty. `$hasColorValues` was false. The card did not
render.

Fix: read `$axisValue['attribute_value_id']`. Update
the tab's docblock to document the exact shape
`swatchAxesFor()` produces.

**How the bugs were found:** the diagnostic that closed
this issue was a single line logged from
`_tab_images.php`:

    error_log('TEMP-DIAG', [
      'variantAxes_count'    => count($variantAxes),
      'variantImages_count'  => count($variantImages),
      'first_axis_is_color'  => $variantAxes[0]['is_color_axis'] ?? 'MISSING',
      'colorValues_count'    => count($colorValues),
      'hasColorValues'       => $hasColorValues,
    ]);

Its output was:

    variantAxes_count:    2
    variantImages_count:  6
    first_axis_is_color:  true
    first_axis_values_ct: 2
    colorValues_count:    0
    hasColorValues:       false

The first four values confirmed the pipeline was
correct. The last two isolated the failure to the loop
body. Five seconds of reading the loop body revealed
the wrong key name.

**Pattern notes to add to REMEMBER.md:**

  Pattern 28 (view_partial does not inherit outer
  scope) is about variables that fail to reach a
  partial. This bug is the mirror image: a `require`-ed
  view file **shares** the outer scope, and any variable
  it reassigns pollutes every sibling that requires
  after it.

  Call it **Pattern 31 - require'd view files share
  scope; do not shadow caller variables.**

  Rule: a view file that is `require`d (not
  `view_partial`'d) runs in the same PHP scope as its
  caller and every other `require`-ed sibling. Anything
  defined or reassigned in one file leaks to the next.
  Never assign to a variable whose name matches a
  convention established by the caller. In this codebase
  that convention includes `$val`, `$valBool`, `$err`,
  `$product`, `$activeTab`, `$mode`, `$old`, `$errors`,
  `$categories`, `$brands`, `$categoryIds`, `$tagIds`,
  `$inventory`, `$attributes`.

  Audit: before adding a `require`-ed file (or adding
  a loop to an existing one), list the variables the
  caller has already defined. Any new local variable
  that collides with the list is a latent bug.

  Pattern 32 - contract drift between producer and
  consumer shapes.

  The value shape returned by
  `ProductVariantRepository::swatchAxesFor()` uses
  `attribute_value_id`. The shape returned by
  `categoryVariantAxes()` uses `id`. The same concept,
  different key names. When the tab's data source was
  switched from one to the other (File 24a), the loop
  in the tab was not updated to match. The `?? 0`
  fallback hid the mismatch.

  Rule: when a consumer is repointed at a different
  producer, read the producer's exact output shape and
  compare it against every read in the consumer. Grep
  for `?? ` in the consumer body: any read that is
  guarded by `?? default` may be silently falling back
  on a key that no longer exists. A `?? ''` or `?? 0`
  on a wrong key name produces no error, only
  emptiness.

  This pattern is a sibling of Pattern 15 (snake_case
  vs camelCase in views). Both are "same concept,
  different key" bugs that produce silence rather than
  exceptions.
