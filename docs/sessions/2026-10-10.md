## Bugs found

1. **`super_admin` vs `super-admin` mismatch.** Four code
   locations used the underscored form while every seeder
   used the hyphenated form. Result: two guards in
   AdminUserController were inert, and User::isSuperAdmin()
   always returned false. An admin could have locked the
   platform by demoting the sole super-admin. Fixed in
   `f637871`.

2. **Empty permission sets on four seeded roles.**
   `catalog-manager`, `order-manager`, `marketing`, and
   `support` had zero permissions assigned since the
   original seed. Any user assigned to them could do
   nothing in the admin panel. Fixed in seeder 0012.

3. **Draft "copy from role" dropdown with no working
   backend.** The first draft of `create.php` included a
   "Start from existing role" dropdown. The JS only logged
   a comment about needing a server-rendered map. Removed
   before commit - shipping a dead affordance is worse
   than not shipping it. Logged as deferred.

## Decisions made

- **Roles as freely editable bundles of permissions.**
  The design conversation clarified: merchants do not need
  multi-role-per-user when roles themselves are freely
  editable. The permission model is: users -> one role ->
  any subset of the 49 permissions. Single-role UI is
  deliberate.

- **super-admin is is_system = 1.** Locked permissions,
  locked name and description, cannot be deleted. This is
  the platform's recovery anchor. If super-admin's set
  could be reduced, a merchant could brick the platform
  by removing the wrong toggle. Every other role is fully
  editable, including store-admin.

- **Permission vocabulary is developer-defined.** Merchants
  cannot invent new permission slugs - they correspond to
  capabilities that exist in code. They CAN invent new
  roles and toggle any subset of the seeded vocabulary.
  This matches Shopify, Adobe, Kibo, and Spree.

- **Multi-store scoping via store_id NULL / non-null.**
  Global roles (store_id NULL) visible everywhere.
  Store-scoped roles visible only in their own store.
  New roles created through the admin are scoped to the
  current store.

- **RoleRepository stays free of Commerce imports.**
  StoreContext is not injected. Callers pass the store
  id explicitly. Platform keeps zero knowledge of
  Commerce.

- **No FK on core_roles.store_id.** Migration 0101 set
  the precedent for the three other Core tables that
  reference commerce_stores. Consistency over
  referential integrity here. Documented.

- **`core.roles.manage` retired.** Replaced by four
  granular slugs matching the sibling `core.users.*`
  pattern. The FK cascade handles removal cleanly.

## Session in the larger arc

008K is now four of five sub-stages complete. Orders,
Customers, Users, Roles are real. Only Coupons remains.

The RBAC layer is complete. Every admin surface is
gated by a permission that a merchant can toggle on any
custom role. The permission vocabulary covers the entire
platform as of today. Future stages that add admin
surfaces add new permission slugs to the same seeder
family, assign defaults, and the roles editor picks them
up automatically.

The multi-store foundation is now in place. A second
store's admin will see only their store's custom roles
plus the global seeded ones. No schema change needed
when the platform is resold to a multi-store customer.
