## Worked on

- **Read the shipped state before writing anything.** The
  008I plan document listed three email templates as
  missing. A find showed the templates already existed
  at `resources/emails/newsletter/`, not
  `resources/views/emails/newsletter/` as the plan
  document said. Same class of correction as the
  session `2026-10-11-4.md` record. The plan document is
  a map, not the territory.

- **Added two methods to `SubscriberService`.**
  `confirmByToken()` and `unsubscribeByToken()` verify a
  signed token, call the existing `confirm()` /
  `unsubscribe()` methods, and return a result array the
  controller can render directly. `unsubscribeUrlFor()`
  signs a 90-day unsubscribe token. All three are
  additive; no existing method changed.

- **Added the per-email confirmation rate limit.**
  The IP-level route limiter stops a single-source
  burst. A botnet with one request per IP is not stopped
  by it. `sendConfirmation()` now checks the
  `RateLimiter` keyed on sha256(email), capped at 3
  sends per 24 hours. When the cap is hit, the response
  is identical to a successful send; no email goes out.
  `SubscriberService` gained a `RateLimiter` constructor
  parameter. No provider change because ADR-018
  auto-construction resolves it.

- **Built the storefront controller.**
  `NewsletterController` extends `StorefrontController`.
  Four actions. Honeypot check first, then
  `SubscriberService::subscribe()`, then a generic
  redirect-and-flash. `showConfirm()`, `showUnsubscribe()`,
  `performUnsubscribe()` all call the service methods.

- **Registered the four routes** in `routes/storefront.php`.
  `POST /newsletter/subscribe` gets
  `ratelimit:newsletter_subscribe,5,60` and `csrf`. The
  GET confirm and unsubscribe routes get `store` only.
  The POST unsubscribe gets `store` and `csrf`.

- **Wrote the two storefront views.**
  `confirm-result.php` is a shared result page for
  confirm and unsubscribe outcomes; the layout is the
  same for success and failure, only the icon and copy
  change. `unsubscribe-form.php` is the two-step
  confirmation form with a reason textarea.

- **Wired the two subscribe forms.** Both
  `footer.php` and `home.php` had
  `onsubmit="return false;"` with disabled inputs.
  Both now POST to `/newsletter/subscribe` with a CSRF
  field, a source field, a honeypot field, and
  enabled inputs.

- **Fixed the footer form CSS.** The stylesheet
  assumed a single-input layout in a horizontal row at
  480px+. The new form has two visible inputs plus a
  hidden field. Changed to stacked at every viewport,
  full-width inputs, full-width button.

## Bugs found

Three real bugs during the browser test pass, all fixed
before the commit.

1. **The confirmation email port was wrong.**
   `config/local.php` had `app.url = http://localhost:8081`.
   The store runs on 8084. The confirmation email's
   confirm link pointed at 8081, so clicking it produced
   ERR_CONNECTION_REFUSED. Fixed by editing
   `config/local.php`. Config is gitignored, so this is
   a deployment-time fix, not a code change.

2. **`SubscriberService::subscribe()` treated an
   already-confirmed subscriber as a new subscribe on
   resubmit.** Not a bug per se, but the idempotent path
   did not send another email and the rate limiter had
   nothing to count against. The behaviour is correct:
   a subscriber who is already confirmed is a no-op.

3. **Unsubscribe POST returned "link not valid" for a
   token whose subscriber did not exist.** The GET
   verified the token only, so the form rendered. The
   POST verified the token **and** looked up the
   subscriber. When the subscriber row was missing
   (test subscriber id 2 no longer existed), the POST
   returned `ok = false`. Not a security issue — the
   POST correctly refuses — but a UX gap. Logged as a
   follow-up.

## Decisions made

- **Email templates live at `resources/emails/`, not
  `resources/views/emails/`.** `EmailService::sendTemplate()`
  resolves from `resources/emails/`. The plan document
  was wrong. Recorded so the next reader does not go
  looking in the wrong place.

- **The per-email rate limit is 3 sends per 24 hours.**
  Far below any legitimate user's needs; far below what
  makes the inbox unusable for a victim. The cap is
  fixed, not setting-driven, so it cannot be weakened
  by a store setting.

- **The rate-limit key is `sha256(email)`, not the
  plaintext.** The `core_rate_limits` table stores the
  hash. No plaintext email address in an infrastructure
  table.

- **Honeypot, not CAPTCHA.** A CAPTCHA on a footer form
  is intrusive. A honeypot catches the overwhelming
  majority of bots at zero cost to the customer.

- **Uniform responses on the subscribe endpoint.**
  New, existing, refused, honeypot-tripped — same
  message. The response never reveals which case fired.

- **Two views, not four.** `confirm-result.php` serves
  both the confirm result and the unsubscribe result.
  Same layout, different message. `unsubscribe-form.php`
  is the only other view.

## Deferred / logged for follow-up

   The GET verifies the token only; it does not check
   that the subscriber row exists. A stale token
   therefore renders a form that always fails on

   the subscriber exists, and render the neutral error
   page directly if it does not.

## Session in the larger arc

008I Session 3a closes the customer side of the
newsletter: subscribe, double opt-in, unsubscribe.
The admin side (Sessions 1 and 2) shipped earlier
today. The only remaining work in 008I is the account
preferences toggle (Session 3b) and the queue worker
test (Session 4).

The per-email rate limit is the session's most
important security contribution. Without it, the
subscribe endpoint was a subscription-bomb vector:
a botnet with one request per IP could send unlimited
confirmation emails to a single victim address,
unaffected by the route-level IP limiter. The email
limiter closes that.

The whole flow was verified in the browser: green
flash, Mailpit email, click to confirm, DB row moves
to confirmed. Then unsubscribe: form, POST, DB moves
to unsubscribed, acknowledgement email. Then the
honeypot: no email, no DB row. Then the rate limit:
3 sends, 4th refused, `attempts=3` in
`core_rate_limits`.
