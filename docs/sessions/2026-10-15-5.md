### The 403 themed-path bug and its fix

Two files touched.

**PermissionMiddleware.** The middleware
short-circuited with a hand-rolled
`new Response('<h1>Forbidden</h1>...', 403)`.
That bypassed `App::renderException()`. The
browser rendered unthemed plain HTML for a
permission denial, while the router's 404 went
through `renderException()` and rendered
`resources/views/errors/404.php`. Two error
paths, one themed, one not.

The fix is one line:
`throw HttpException::forbidden()`. `App::run()`
catches the exception the same way it catches the
router's 404. `renderException()` reads the status
from the exception and renders
`resources/views/errors/403.php`.

**AuditLoggerMiddleware.** The middleware's
`handle()` ran `$response = $next($request);` with
no try/catch. A downstream throw meant the audit
logging block below the call never ran, so a
rejected POST left no audit row. The baseline
says explicitly: "a rejected write is still a
write attempt, and it must leave a trace." The
middleware did not honour that for thrown
responses.

The fix wraps `$next($request)` in a try/catch.
An `HttpException` is caught, logged with its
own status code via a new private `logAttempt()`
method, and rethrown so `App::renderException()`
still sees it. A generic `\Throwable` is caught
the same way, logged as 500, rethrown.

`logAttempt()` mirrors the normal-path logging:
it honours `LOGGED_METHODS` and `SKIP_PATHS`,
reads the store context, reads the current user,
and calls the same `AuditLogger::log()` the
normal path uses. The only difference is the
status source: `$e->getStatusCode()` instead of
`$response->statusCode()`.

## Bugs found

One real bug (the 403 themed path) plus one
latent gap (the audit middleware did not handle
throws).

**Bug 1.** The permission middleware returned a
hand-rolled `Response` for 403s, bypassing the
themed error view. Discovered during the tail's
error-pages walk. Fixed in 27db37b.

**Gap 1.** `AuditLoggerMiddleware` did not
handle a downstream throw. The gap was latent -
no middleware threw before today - but the
permission middleware's change to `throw` exposed
it. Closed in the same commit.

## Decisions made

**The permission middleware throws instead of
returning a themed Response.** Three options were
considered:

  - Return the themed HTML inline from the
    middleware. Narrow, but the middleware would
    have to know how to render a view, and the
    action is not its job.
  - Throw and let `App::renderException()` render.
    Smallest change, reuses the existing 404 path,
    one line.
  - Move the permission check out of middleware
    and into controller dispatch. Larger refactor,
    not warranted for a single behaviour.

The throw was chosen. The pipeline already
handles it (the router throws for 404, and the
App catches for both). Themed 403 comes through
the same door as the 404.

**The audit middleware catches and rethrows.**
Alternative was to let the audit gap stand and
rely on the App's INFO log line for 403s. The
baseline says the ledger must record rejected
attempts. The catch closes the gap with a small
additive change and no behaviour change for the
non-throwing path.

**The POST-403 audit path is verified on the
customer's deployment, not here.** The code is
correct by construction, but the operating rule
is verify-not-assume. The customer has the
deployment and the low-privilege account. The
verification lands in their pass.

## New patterns for REMEMBER.md

**A middleware that short-circuits with a
hand-rolled Response is invisible to
App::renderException().**

The permission middleware returned
`new Response('<h1>Forbidden</h1>...', 403)`
for every permission denial. The response was
valid HTML, had the correct status, and the
browser rendered it. What it did not do was
reach `App::renderException()`, so the themed
`resources/views/errors/403.php` never rendered.

The 404 went through `renderException()` because
the router throws `HttpException::unmatchedRoute()`.
The 403 did not, because the middleware returned
instead of throwing. Two paths that look the same
to a reviewer (both produce a 403) behave
differently at runtime.

The rule: a short-circuiting middleware should
throw the appropriate `HttpException` factory, not
construct a `Response` directly. The factory
routes through the same error handler the rest of
the framework uses. Any short-circuiting middleware
that returns its own Response is a candidate for
this bug.

**AuditLoggerMiddleware must wrap `$next` in
try/catch or a thrown 4xx from downstream leaves
no audit row.**

The middleware ran the logging block only on the
return path. `$next($request)` had no try/catch.
The baseline's rule - "a rejected write is still
a write attempt, and it must leave a trace" -
was honoured only for responses that returned, not
for responses that threw.

The rule: any middleware that auto-injects
audit logging must wrap `$next` so a downstream
throw still produces an audit row. The status
comes from the exception, the method and path
come from the request, and the logging call is
the same one the normal path uses.
