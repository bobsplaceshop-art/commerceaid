## Worked on

- **Diagnosed the SHJO product page rendering bug.** Three
  distinct bugs collapsed into one visible symptom: the size
  chip row rendered gallery-sized images, pushing the buy box
  below the fold.

- **First fix: swatch renderer contract.** `show.php` line 333
  emitted a `<picture>` for any value with a swatch-preview row.
  The view's own docblock already said image swatches were for
  color axes only. The code did not enforce it. Gated the branch
  on `$isColor` and added a defensive `.sf-swatch-chip img`
  CSS guard.

- **Second fix: storefront gallery filter.** With the size chips
  fixed, the thumbnail strip on SHJO still rendered nothing.
  The gallery reader (`ProductImageRepository::listForProduct()`)
  filtered on `attribute_value_id IS NULL`. SHJO's images were
  all assigned to color values, so every row was excluded from
  the storefront gallery even though the hero rendered through
  a different path. Added `listAllForProduct()` (no filter) and
  switched the storefront to it. The admin Images tab keeps the
  filtered reader.

- **Cascade audit before the second fix.** Grepped every caller
  of `listForProduct()` and every consumer of the swatch /
  variant / primary readers. Verified the admin path was not
  affected by the storefront change. Confirmed the gallery JS
  is count-agnostic.

- **Process incident: awk with PHP content.** The first attempt
  to insert the new repository method used an `awk` block
  containing `fn ($r) =>` in the printed lines. The shell parsed
  the `(` as a subshell operator before awk saw the script,
  producing a cascade of "no such file" errors and a truncated
  temp file. Recovered by switching to Python with a heredoc,
  which the codebase already uses for patch work. No files were
  harmed.

## Bugs found

1. **Swatch renderer emitted images on non-color axes.**
   `show.php` gated the image branch on `$swapMedia !== null`
   without checking `$isColor`. Any value with a swatch-preview
   row rendered a `<picture>`, including size values on products
   where the admin had assigned images to them. Since
   `.sf-swatch-chip` has no width or height constraint, the
   picture rendered at natural gallery size. Fixed in `2b46010`.

2. **Storefront gallery reader excluded every attribute-assigned
   image.** `listForProduct()` filtered on `attribute_value_id
   IS NULL`. Products whose images were all assigned to values
   (SHJO) rendered an empty thumbnail strip. Fixed in `54034c3`.
   See Pattern 32, second manifestation, in `docs/REMEMBER.md`.

3. **Admin primary-fallback check reads the filtered slice.**
   `Admin/ProductController.php:1357` uses `listForProduct()` to
   decide whether a product has a primary image. On a product
   whose images are all swatch rows, the filter returns `[]`,
   the fallback never runs, and the product can end up with
   zero primaries. Deferred. Same root cause as bug 2 but on
   the admin write path. Ships as its own commit.

4. **Two-primary invariant violation on SHJO.** The repository's
   class docblock claims to enforce "exactly one row per product
   carries the primary flag on every write that could break it."
   SHJO has two rows with `is_primary = 1` (product_image ids 1
   and 2). Either an admin save path bypassed the enforcement or
   the initial data load wrote both. Data cleanup is one SQL
   statement. The code path that produced the state needs its
   own investigation. Deferred.

5. **`listForProduc` typo.** `Admin/ProductController.php:418`
   calls `$variantRepo->listForProduc($productId)` — missing the
   `t`. Line 413 has the correct spelling. Line 418 will throw
   `Call to undefined method` if that branch executes. Latent
   until reached. Fix in the same commit as bug 3.

## Decisions made

- **Extend Pattern 32 rather than add Pattern 36.** Both
  manifestations are the same debugging motion: read the
  consumer, compare to the producer, find the mismatch. The
  existing pattern title ("contract drift between producer and
  consumer shapes") covers both. If either manifestation ever
  needs its own numbering, the sub-section can graduate.

- **Two sequential fix commits, not one.** Commit `2b46010`
  ships first because it is the user-visible symptom. Commit
  `54034c3` ships second because it is the underlying data
  model bug. Keeping them separate means a bisect on either
  finds the change cleanly.

- **Do not touch `listForProduct()`.** Its filter is correct
  for the admin Images tab. The bug was not the method, it was
  the method being used by two consumers with different
  requirements. Fix is to add an intent-named reader, not to
  loosen the existing one.

- **Do not chase the two-primary invariant now.** SHJO renders
  correctly. Bug 3's fix will clean up the state on next save.
  Data cleanup after bug 3 ships.

- **Python-heredoc patch protocol, not awk.** The awk failure
  confirms what REMEMBER.md's pattern 4 and 20 already say:
  shell-adjacent PHP patching is fragile. Python with a heredoc
  handles every case cleanly. Use it as the default.
