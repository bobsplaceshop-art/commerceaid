## Category image (d4f4438)

The category now renders two distinct image surfaces:

  - The detail page header renders a wide 3:1 banner from
    image_file_id.
  - The home page category grid and the category index card
    grid render square 4:5 cards from card_image_file_id.

Migration 0353 adds commerce_categories.card_image_file_id.
The Category model, CategoryRepository, CategoryController,
admin editor, and the two helpers (category_image_url,
category_primary_media_item) all read the new column with
fallback to the banner.

The picker upload handler in _block-media-picker.php was
reading data.file, a key MediaController::upload never
returns. MediaController::upload returns a flat object:
{ ok, id, uuid, url, name, mime, size, dimensions, variants }.
The picker's check now reads data.ok === true && data.id and
reads data.id, data.url from the flat shape. Defensive
text-then-parse replaces r.json() so a non-JSON error
response (500, 403 CSRF) surfaces the status instead of
"Unexpected token <".

product-images-admin.js already carried the same fix from a
prior session and documents the shape on lines 123-129.
Both consumers now read identically.

## HTTP client move (c6168d5)

HttpClient was in CorporateAid\Commerce\Services\Payment
but is a general-purpose HTTP client. ARCHITECTURE.md
section 3.2 puts shared infrastructure in Platform. Moved
to app/Platform/Support/HttpClient.php with namespace
CorporateAid\Platform\Support\HttpClient. Five payment
providers updated their use statements. Auto-construction
(ADR-018) resolves the class, so no container binding
needed changing.

The three public methods (postJson, post, get) and the
private request() gained an optional ?string $cookieJar
parameter. When set, CURLOPT_COOKIEJAR and
CURLOPT_COOKIEFILE are both set to the path so curl
persists and reuses cookies across calls. Payment
providers pass nothing and see unchanged behavior.

PerformanceCheckService used raw curl_* calls that PHPStan
level 8 could not verify. Its stub declares
CURLOPT_COOKIEJAR (10082) as non-empty-string, which is
wrong (a file path can be empty; the constant is not the
user-agent). Three argument.type errors. Rather than
suppress them with an ignoreErrors entry, the service now
uses HttpClient. The cookie-jar parameter makes its
login-then-timed-requests flow possible. No curl in the
diagnostics service. No new ignoreErrors entry in
phpstan.neon.

Also fixed in the same commit (found by the same
composer analyse run):

  - AdminPageController::reorderBlocks() used the short
    name PageDraftRepository without a use import. Fixed
    with a use statement. Without this, the drag-reorder
    POST would have 500'd on the first drop.
  - Category::fromRow() had a redundant
    && $row['card_image_file_id'] !== null after an isset()
    that already handles null. Dead code. Removed.

Cascade verified: Store Settings > Payments tab loads.
Stripe test connection returns HTTP 200 (key valid).
PayPal authentication returns HTTP 200 (credentials
valid). composer dump-autoload -o: 897 classes, no PSR-4
skip. composer analyse: [OK] No errors.

## Reorder (ca03eff)

Block reordering was the only builder operation writing
to commerce_page_blocks (published). Every other builder
write (add, config save, delete, duplicate) writes to
commerce_page_drafts. Both the sidebar and the preview
read through DraftManager::getMergedBlocks(), which starts
from published and overlays draft rows. A pending_update
draft row carries its own sort_order and overrides the
published value. So a drag wrote the new order to the
published table, the merge overrode it with the draft's
stale order, and the sidebar and preview showed different
orders because the tie between two identical sort_order
values resolved differently in each view's iteration
order. The preview was reliably wrong; the sidebar
appeared correct by luck.

Four linked fixes:

  1. AdminPageController::reorderBlocks() now calls
     PageDraftRepository::saveReorder() (which existed
     and was never called) instead of
     PageBlockRepository::reorder(). saveReorder() writes
     draft rows: existing pending_update rows get the new
     sort_order, blocks without a draft get a new
     pending_update row carrying the order, and
     pending_add rows (negative ids) get their order set
     by draft id. Reorder is now a draft edit like
     everything else.

  2. page-builder-customizer.js's drop handler signals
     the preview via
     postMessage({ action: 'updateBlock', reload: true })
     instead of iframe.contentWindow.location.reload().
     The bridge (preview-bridge.js) already handles that
     message; the old call silently no-oped in Chrome.
     Also adds a res.ok guard and a .catch so a failed
     reorder POST logs the status instead of pretending
     success.

  3. PageBlockRepository::update() gains an optional
     ?int $sortOrder third parameter. When non-null, the
     sort_order column is written in the same statement
     as config_json. Every existing caller passes no
     third argument and keeps today's behavior.

  4. DraftPublisher::publish() passes the draft's
     sort_order to update() at the pending_update branch,
     so a Publish after a reorder carries the new order to
     the published table. The old code assigned
     $existing->sortOrder = ... and then called update()
     without it (with a comment that said 'we'd also need
     a method to update sortOrder if it changed' — that
     method is now the optional parameter).

The whole workflow is coherent: drag writes a draft row,
the merged view renders the new order in the sidebar and
the preview, Discard reverts, Publish commits. The
published table's sort_order is written only at Publish
time, which matches the draft-edit model every other
builder operation follows.

## Bugs the discipline caught

The session was driven by the discipline: read, confirm
bytes, patch, verify. Several aborts and re-reads happened
because the process caught them:

  - A Python re.subn crash from backslashes in the
    replacement string (\\S in Platform\\Support). The
    atomic write meant the file was untouched; the tree
    stayed half-patched for one turn until the
    string-based patch replaced the regex.
  - A missing use PageDraftRepository; in the reorder
    path. Would have 500'd the first drag POST. Caught
    by PHPStan before the browser test.
  - A PSR-4 skip in composer dump-autoload when the
    namespace move landed but the write did not. Caught
    by the payments tab 500, diagnosed from the composer
    warning in the terminal.

Each was caught by a read, not fixed by a guess.
