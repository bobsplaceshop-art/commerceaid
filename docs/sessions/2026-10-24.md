## Reorder (ca03eff)

Block reordering was the only builder operation writing
to commerce_page_blocks (published). Every other builder
write (add, config save, delete, duplicate) writes to
commerce_page_drafts. Both the sidebar and the preview
read through DraftManager::getMergedBlocks(), which starts
from published and overlays draft rows. A pending_update
draft row carries its own sort_order and overrides the
published value. So a drag wrote the new order to the
published table, the merge overrode it with the draft's
stale order, and the sidebar and preview showed different
orders because the tie between two identical sort_order
values resolved differently in each view's iteration
order. The preview was reliably wrong; the sidebar
appeared correct by luck.

Four linked fixes:

  1. AdminPageController::reorderBlocks() now calls
     PageDraftRepository::saveReorder() (which existed
     and was never called) instead of
     PageBlockRepository::reorder(). saveReorder() writes
     draft rows: existing pending_update rows get the new
     sort_order, blocks without a draft get a new
     pending_update row carrying the order, and
     pending_add rows (negative ids) get their order set
     by draft id. Reorder is now a draft edit like
     everything else.

  2. page-builder-customizer.js's drop handler signals
     the preview via
     postMessage({ action: 'updateBlock', reload: true })
     instead of iframe.contentWindow.location.reload().
     The bridge (preview-bridge.js) already handles that
     message; the old call silently no-oped in Chrome.
     Also adds a res.ok guard and a .catch so a failed
     reorder POST logs the status instead of pretending
     success.

  3. PageBlockRepository::update() gains an optional
     ?int $sortOrder third parameter. When non-null, the
     sort_order column is written in the same statement
     as config_json. Every existing caller passes no
     third argument and keeps today's behavior.

  4. DraftPublisher::publish() passes the draft's
     sort_order to update() at the pending_update branch,
     so a Publish after a reorder carries the new order to
     the published table. The old code assigned
     $existing->sortOrder = ... and then called update()
     without it (with a comment that said 'we'd also need
     a method to update sortOrder if it changed' — that
     method is now the optional parameter).

The whole workflow is coherent: drag writes a draft row,
the merged view renders the new order in the sidebar and
the preview, Discard reverts, Publish commits. The
published table's sort_order is written only at Publish
time, which matches the draft-edit model every other
builder operation follows.

### What was fixed

`Container::class` was not registered as a self-instance. Any
class taking `Container $container` in its constructor and
resolved via `$container->get(Class::class)` received a fresh
empty container — no bindings, no instances. Any subsequent
`$this->container->get(X)` in the resolved class threw "cannot
auto-construct" for any X needing captured configuration.

The bug has been latent since Stage 008J. The router bypasses
it (`new $class($this->container)`). The smoke harness was the
first code path to resolve a controller through `get()`.

Fix: one line in `App::registerCoreServices()`:
`$c->instance(Container::class, $c);`

### 84bb976 — tree traversal and children-aware duplicate

The document model now supports nested blocks end-to-end:
flat list → tree → duplicate subtree → publish tree.

Four changes:

1. DraftManager::getMergedBlocks() overlays parent_id from
   the draft row for both pending_update (reparent) and
   pending_add (initial parent). Prior to this, every
   pending_add block came back as a root regardless of the
   draft row's parent_id — the tree was unrepresentable
   because the merge erased the relationship.

2. DraftManager::getMergedTree() returns roots with
   $children populated. Orphaned children (a parent whose
   id is not in the merged set — deleted parent, stale
   draft) attach to a synthetic '__orphaned__' root so
   content is never silently lost.

3. DraftManager::duplicateBlock() recurses. Public
   signature preserved; the recursion lives in a new
   private duplicateSubtree(). A Section with three
   children duplicates to a Section draft plus three child
   drafts, each pointing at the new Section's negative
   draft id.

4. PageDraftRepository::addDraftBlockWithConfig() accepts
   optional ?int $parentId = null. INSERT includes the
   parent_id column. Existing callers (addBlock path) pass
   no sixth argument and continue to create root drafts.

The commit merged the audit's 0.5c and 0.6 into one unit
because the tree creation and the tree publication are
the same mechanism. A 0.5c-only commit would have allowed
a merchant to duplicate a Section (creating child drafts
pointing at a negative draft parent id) and then hit
Publish, which — before 0.6 — inserted every pending_add
as a root. The tree would have been silently broken on
the storefront with no error. 0.5c and 0.6 ship together.

DraftPublisher::publish() is two-pass:

  Pass 1: pending_delete, pending_update, and root
          pending_add (parent_id null). Records
          draftRowId → newPublishedId for every root
          addition.
  Pass 2: pending_add with parent_id not null. Resolves
          a negative draft parent id to the positive
          published id created in pass 1. Passes the
          resolved id to blocks->create().

An unresolvable parent reference throws, rolling the
transaction back. A child that references a parent draft
not in this batch is a data integrity violation.

Migration 0355 — the tree work surfaced a schema bug.
commerce_page_drafts.parent_id was BIGINT UNSIGNED, which
cannot hold a negative draft id. The pending_add recursion
in duplicateSubtree() writes child drafts whose parent_id
is a negative number (the new section draft's id). The
column is now BIGINT (signed). The published table's
parent_id stays BIGINT UNSIGNED — published parents are
always positive.
