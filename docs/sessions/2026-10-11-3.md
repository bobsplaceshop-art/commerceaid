## Worked on

- **Verified prerequisites.** The two dependencies named in
  the roadmap were both live: Admin Orders (008K.1) and the

  refund arithmetic had no source of truth and the

- **Researched the industry-standard returns workflow.**
  Compared against Spree and AfterShip. The mature
  platforms all ship inspection, condition grading, and
  resellable flags as part of the "mark received" step. Our
  service's `markReceived()` was a bare status flip. Given
  the scope of this stage (roadmap named "mark received"),
  we added the one piece the standard treats as mandatory
  and deferred the rest:
    - **Added:** per-line received quantities. The merchant
      records what the warehouse actually counted, and the
      refund adjusts from that. A customer who requests
      three and the warehouse receives two gets refunded
      for two.
    - **Deferred:** condition grading (A/B/C/D) and the
      resellable / not-resellable per-line disposition.
      These are restocking concerns, not compliance ones,
      and the German Widerrufsrecht does not require them.
      Logged for a future sub-stage.

  Effective 19 June 2026, German merchants must provide a

  without login. The current customer-facing flow at

## Bugs found

1. **PHPStan `notIdentical.alwaysTrue` in TaxService.**
   The inner `$product !== null` check was redundant: the
   outer `if ($override !== null)` guard already proved
   non-null. This same check had been fixed once earlier
   in the session and reverted by a subsequent patch. Fixed
   in `4e3a8f2` with an explanatory comment.

2. **Sidebar array items interpreted as shell redirects.**
   Two lines from `sidebar.php` were pasted into the
   shell without heredoc wrapping. The shell treated the
   `['label' => 'Coupons', ...],` lines as `cat > Coupons,`
   and `cat > "Customer Approvals,"` redirections, creating
   two zero-byte files in the project root. Noticed in
   `git status --short` after the admin returns commit.
   Deleted. Working tree clean.

3. **Heredoc wrote to a missing parent directory.** The
   first attempt at `resources/views/admin/returns/show.php`
   failed silently because the `returns/` directory did
   not yet exist. `cat > file` does not error on a missing
   parent; the shell continues, and the following `php -l`
   reports "No such file or directory" which is easy to
   miss in a long paste. Fixed by `mkdir -p` before the
   heredoc. The trailing check `test -f ... && php -l ...`
   catches the failure loudly on subsequent writes.

## Decisions made

- **`markReceived` takes received quantities per line.**
  Industry standard. A partial return with a mismatched
  refund was the alternative, and it would have silently
  over-refunded the customer.

- **`returns.view` and `returns.moderate` as separate
  slugs.** Customer Support gets view-only. Store-admin
  and super-admin get both. Matches the sibling pattern
  from `review.view` / `review.moderate`.

- **State-aware action buttons on the show page.**
  A `requested` return shows Approve and Reject. An
  `approved` return shows Reject and Mark received.
  A `received` return shows Process refund. A terminal
  return shows nothing. The service enforces the same
  state machine server-side as the source of truth.

- **Date-range filtering.** The roadmap named it and the
  change is small. Two new WHERE clauses.

- **`mergeTabStatuses()` workaround for multi-status tabs.**
  The repository's `buildFilters()` filters on a single
  status. The `open` and `closed` tabs each aggregate
  multiple statuses. The clean fix (a `statuses` array
  param, matching `OrderRepository::paginate()`) is a
  follow-up. The workaround fetches each status
  separately and merges. Pagination for tabs with more
  than one status is best-effort; the counts are exact.

- **Deferred condition grading and resellable flags.**
  Not required for compliance; not required for the
  refund to be correct.

## Deferred

- **Condition grading (A/B/C/D) and resellable flags per
  line.** Future sub-stage. The schema would need two
  new columns on `commerce_return_request_items`.
- **`statuses` array param on `ReturnRequestRepository::`
  `buildFilters()`.** Replaces the `mergeTabStatuses()`
  workaround.
- **Receive modal shows only Requested and Actually
  received.** A future polish could also show Unit refund
  and Line refund recomputed side by side, so the merchant
  sees the refund arithmetic before submitting.
- **Refund card label on the show page.** Currently
  "as recorded on the request." After a partial refund,
  showing Requested amount and Applied amount as two
  separate cards would be clearer.
- **Widerrufsbutton.** Logged as COMPLIANCE-DE entry 22.
  Not scheduled. Deadline 19 June 2026.

## Session in the larger arc

008H closes. The stage shipped in three sessions plus
two reverted attempts and a six-month pause. The final
result is a coherent returns workflow:

  - Customer initiates from `/account/returns`.
  - Admin reviews, approves, or rejects.
  - Warehouse receives and records actual quantities.
  - Admin processes the refund.
  - Order totals and per-line returned quantities
    reflect what actually happened.

COMPLIANCE-DE entry 8 (14-day Widerrufsrecht window)
moves from Deferred to Done at stage close. The
Widerrufsbutton (entry 22) remains open. The 14-day
window itself is enforced by `ReturnRequestService::`
`isWithinWindow()`, which checks `windowDays()` from
delivery, with a configurable override per store and
a hard floor of 14 days for German deployments.

With 008H closed, the platform has both halves of the
commerce loop:

  - The customer side: browse, cart, checkout, order,
    return.
  - The merchant side: products, orders, customers,
    returns, users, roles, coupons, tax, shipping.

The pricing engine (008K.5) and returns (008H) are the
last two stages that touched the order totals
arithmetic. Both are shipped. The next stages (008I,
009, and beyond) build new capabilities on a stable
foundation.
