## Bugs found

Four distinct bugs. Each surfaced in the browser, each
fixed in the same session.

1. **Theme variable mismatch in auth.php + setup.css.**

   Both files referenced `--ra-fg`, `--ra-card-bg`,
   `--ra-hover`, `--ra-active`, `--ra-hover-bg`. None
   of those variables exists in app.css, which defines
   `--ra-text`, `--ra-surface`, `--ra-hover-nav`,
   `--ra-active-nav-bg`, `--ra-hover-row` instead.

   Every reference fell through to a hardcoded fallback.
   In light theme the fallbacks matched the real values,
   so the bug was invisible. In dark theme the fallbacks
   were the wrong polarity: white card, dark-navy inputs,
   dark text on dark backgrounds. The login page and the
   Store Settings page were both unreadable.

   Fixed by renaming every wrong reference to the
   correct name. 51 replacements in setup.css, 7 in
   auth.php.

2. **setup.css defined its own theme palettes.**

   A block under a bare `:root` selector set `--ra-bg`,
   `--ra-muted`, `--ra-input-bg`, etc., unconditionally.
   Because setup.css loads after app.css, this block
   overrode app.css's light palette on every theme. On
   `data-theme="system"`, app.css's `:root` block
   applied the dark palette to variables setup.css did
   not touch (--ra-surface), while setup.css's
   `:root` block applied the light palette to variables
   it did define. The result: dark card, light body,
   mixed polarity.

   Fixed by deleting the block. app.css is now the
   sole source of theme variables. setup.css
   contributes no `--ra-*` definitions.

3. **`color-scheme` not declared on theme roots.**

   Without `color-scheme: dark` or `color-scheme: light`,
   Chrome renders native `<option>` panels in the OS
   default scheme. The dropdown panel background was
   white on every theme, and the option text was
   washed-out grey.

   Fixed by declaring `color-scheme: dark` on the dark
   block and `color-scheme: light` on the light and
   system-light blocks. Also added an explicit
   `<option>` rule in setup.css.

4. **The Fonts tab save threw a 500 because
   `font_body_slug` was not on the `updateColumn()`
   allowlist.**

   `StoreRepository::updateColumn()` has an explicit
   allowlist of columns it will write. The list was
   written before the font settings existed and was
   never extended. Every save of the Fonts tab threw
   `InvalidArgumentException: Column font_body_slug is
   not updatable via updateColumn().`

   Diagnosed with a temporary diagnostic in
   `App::renderException()` that wrote the full
   exception to `storage/logs/temp-500.log`. It named
   the exception class, file, and line on the first
   reproduction.

   Fixed by adding the three font slug columns to the
   allowlist.

Bugs 1 through 3 are logged as a candidate for
`docs/REMEMBER.md` as "single source of truth for theme
variables". Bug 4 is logged as **Pattern 34** (below).

## New pattern candidate

**Pattern 34 - New columns on a whitelisted-update model
must be added to the whitelist in the same commit.**

  `StoreRepository::updateColumn()` has an explicit
  allowlist of columns. Adding a new settable column
  to `commerce_stores` without adding it to the list
  produces an exception that is silent until the new
  field is saved.

  Detection: `InvalidArgumentException: Column X is not
  updatable via updateColumn()` in the app log, or a
  500 on the save action.

  php -l and PHPStan level 8 do not catch this. The
  only catch is a browser test that actually submits
  the form with the new field populated.

  Applies to: any model with an explicit-update-column
  method. Same class of bug as the "forgot to bind"
  pattern that motivated stage 008J (Container
  Auto-Construction).

## Decisions made

- **Commit the three platform default fonts to the
  repo.** The storefront must render correctly on the
  very first page load, before any admin has opened
  the Fonts tab. Committing 11 files (~250 KB) is
  cheaper than a first-run bootstrap mechanism.

- **Merchant-selected fonts stay ignored.** They are
  configuration, not dependencies. Downloaded at save
  time and cached per store install.

- **Fall back to the catalog defaults per slot.** When
  a slot is empty, `store_font_selections()` returns
  the catalog entry for the platform default rather
  than null. Every slot always emits @font-face.

- **Log the font preview panel as a follow-up.**
  Building a live preview for the Fonts tab dropdowns
  is a merchant UX improvement, not a compliance
  requirement. It needs its own design (a new route,
  a new JS module, a per-selection download trigger).
  Logged in ROADMAP under Storefront polish as
  008G.4c.1.

- **Add a proper error logging system as a future
  task.** The current `Logger` silently drops entries
  when `file_put_contents` fails. Today's 500 never
  landed in `storage/logs/app.log` for that reason.
  A logger that writes to `error_log()` when its
  primary target fails, and that never loses an
  entry, is a genuine improvement. Separate stage or
  an addendum to stage 008J.
