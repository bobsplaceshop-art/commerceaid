## Bugs found

1. **`main-v2.css`'s `!important` conflict with
   `setup.css`.** The base modal rule and the
   mobile override both use `!important` on the
   same properties (`align-items`, `padding`).
   The base rule loads later by source order
   (`setup.css` at line 62 of the admin layout,
   `main-v2.css` at line 61). By cascade rules
   the base rule wins and the mobile override
   should be dead. It is not. The browser renders
   the bottom sheet at 390px and 768px. The
   mechanism is unverified. Left as-is because
   the behaviour is correct.

2. **`products/variants.php` on the wrong table
   treatment.** `data-responsive="scroll"` instead
   of `"cards"`. Caught at browser test time.
   Fixed in `94bee03`.

3. **The `form` file in the repository root.**
   A zero-byte redirect artifact from an earlier
   shell command. Deleted before the Session 3
   close commit.

4. **`check-html.php` still emits a warning, not
   a hard error, for tables missing
   `data-responsive`.** The Session 1 plan said
   the flip would happen once the breakpoints
   and component treatments landed. Session 1
   landed; the flip did not. Deferred to Session 5
   alongside `check-responsive.php`. Both are
   enforcement changes; they ship together.

5. **Card grids not fixed.** Named in the plan's
   Session 3 scope, absent from the work. See the
   Worked-on bullet above for the four views and
   the deferral reason.

## Decisions made

- **Filter bars use `.ra-filter-bar` on the form
  itself where the form is the control row, and on
  an inner wrapper where the form is a card.**
  The two shapes come from the code, not from a
  plan. The scripts read each shape before
  writing.

- **`products/variants.php` does not adopt the
  filter bar.** Its form is a search widget inside
  a larger filter structure. A toggle that
  collapses only the input is worse than the
  current state. If a future polish pass converts
  the whole card into a filter bar, that is the
  right time to adopt.

- **`.ra-form-grid` is not adopted.** The current
  Bootstrap grid already collapses to single
  column below 768px. Replacing it across 20 edit
  views for a ten-pixel boundary difference is
  not a return on the effort. The plan's bullet
  is evaluated and skipped. Deviation recorded
  here.

- **Card grids deferred to Session 5.** The four
  view-local grid rules stay where they are.
  Session 5's `check-responsive.php` will flag
  them as one class of finding. Fixing now,
  before the checker exists, risks fixing the
  wrong shape. Fix after, with the checker
  confirming.

- **The prevenger's `data-responsive` warning
  stays a warning until Session 5.** The flip to
  a hard error and `bin/check-responsive.php` are
  both enforcement concerns. One commit, one
  Session 5.

- **The sticky action bar stays as it is.** The
  `@media (max-width: 639px)` stack and the
  `@media (max-width: 900px)` left-offset change
  are both correct. Verified by browser. No
  changes.

- **The modal responsive mechanism is left as it
  is.** The browser behaviour is correct. The
  CSS cascade analysis does not explain it. Do
  not change what is working on the basis of an
  analysis that disagrees with the browser. If
  the modal CSS is ever touched, inspect the
  computed styles in DevTools first.

## New patterns for REMEMBER.md

**The cascade check has now failed four times
in one session, each in a different domain.**

The failure mode is the same: reading a fragment
and reasoning from the fragment, instead of
reading the whole file.

The specific form this time: a grep for a
property finds the property if present and says
nothing when absent. `grep 'display.*flex'
setup.css` returned hits from `.ra-modal-header`,
`.ra-modal-body`, and `.ra-modal-panel > form`.
None were `.ra-modal` itself. The rule under
examination had no `display: flex`, and that
absence was what mattered. The grep gave the
impression it did.

Rule: when checking whether a specific rule has
a specific property, read the rule, not a grep
across the file. When a whole-file question
exists, read the whole file.

**When CSS cascade reasoning contradicts observed
browser behaviour, the browser wins.** The
reasoning is a model. The browser is running the
code. If the browser is right, do not change
anything on the basis of the reasoning. If the
browser is wrong, the fix is in the code, not in
the reasoning. Either way, the browser is the
starting point of the investigation, not the
conclusion.

responsive at every width the platform targets:

The four cascade-check failures in one session
are the session's real lesson. They are not a
bug in the code. They are a bug in the process
- the process was already written down, and it
was not followed consistently. The remedy is
simple and mechanical: read the file before
reasoning about the file. Every time. Even when
the answer seems obvious.

The card-grid gap is the session's other lesson.
The plan named four sub-tasks and the session
delivered three. The fourth was not noticed until
the audit at browser-test time. The lesson:
enumerate the plan's deliverable list and tick
each item before writing the session close.
