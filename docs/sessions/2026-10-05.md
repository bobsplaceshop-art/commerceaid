## Bugs found

Two real bugs and one service-worker lifecycle
gotcha.

1. **Route collision on /offline.**

   Two route files registered /offline. The first one
   in load order (routes/storefront.php) won silently.
   The second (routes/commerce.php) was dead code. We
   added the branded view, but the placeholder
   continued to render.

   Fixed by deleting the duplicate and pointing the
   storefront route at the branded view. The collision
   was invisible until we tried to render the branded
   page. `php -l` and PHPStan do not catch it. Only a
   browser test that hits the URL.

   Logged as a Pattern 7 (Route Order) variant: two
   exact-path routes in different files are resolved
   by load order, not by specificity.

2. **Service worker lifecycle: cache is not
   invalidated by editing its dependencies.**

   We fixed the offline page markup. The SW kept
   serving the old cached page. Fixing a file does not
   update the SW cache - the SW must be re-installed
   (fetching the new sw.js) and its install handler
   must run to completion before the new content
   replaces the old.

   Recovery: unregister via chrome://serviceworker-
   internals/, or enable "Update on reload" in DevTools
   -> Application -> Service Workers.

   Related: the patch script uses Python's
   `open(p, 'w')` pattern, which truncates the file
   before writing. During that window, Chrome's SW
   fetch hit a 0-byte file. Chrome backoffs and does
   not refetch for 24h. Recovery required an explicit
   unregister.

   Logged as a new pattern for docs/REMEMBER.md:
   service worker files should be written atomically
   (temp file + rename), or the SW filename should
   change on each meaningful update.

3. **fetch() rejection in the SW navigation handler.**

   `event.respondWith(fetch(req).catch(() =>
   caches.match('/offline')))` resolves to undefined
   when the cache miss hits. `respondWith(undefined)`
   throws "Failed to convert value to 'Response'".

   Fixed by chaining a `.then()` on the cache match
   that returns a last-resort inline Response. Also
   added a cache.match('/offline') guard in the install
   handler so the cache always has something under
   that key.

### New patterns for docs/REMEMBER.md

Two patterns emerged that are worth locking.

**Pattern — Apache caches CSS by path on this
Windows/Laragon environment.**

  Editing a CSS file in place does not reliably
  update the served content, even after `touch`,
  Apache reload, full Apache restart, or browser
  cache clear. The file on disk is correct; the
  server serves stale bytes.

  Detection: compare `wc -c` of the file on disk
  with the length of `fetch(...).then(r => r.text())`
  in the browser. A byte-count mismatch means the
  cache is active.

  Workaround: rename the file. Update every reference
  in the codebase. Delete the old file. This has
  worked every time.

  Do not spend time trying to flush the cache. Rename.

**Pattern — a self-hosting change must audit every
template that references the old asset.**

  The 008G.4c self-hosting of Bootstrap Icons and
  Google Fonts updated three layouts. It missed:
    resources/views/errors/403.php
    resources/views/errors/404.php
    resources/views/errors/500.php
    app/Platform/Middleware/RateLimitMiddleware.php

  The CSP then blocked the CDN reference on those
  pages and their icons rendered as empty boxes.

  Rule: after self-hosting an asset, grep the entire
  codebase for the old CDN URL. Not just the layouts.
  Every view, every middleware, every inline HTML
  string.

Two bugs, both fixed in Session 3.

1. **`\u{221E}` in a single-quoted PHP string.**

   The category page's price chip used
   `'\u{221E}'` as the "no max" label. PHP does not
   process `\u{...}` escapes in single-quoted

   the project (FontCatalog em-dash, and now this).
   Logged for the session close: any `\u{...}` in
   PHP source must be in a double-quoted string or
   replaced with the literal UTF-8 character.

   `array_filter($currentFilters, fn ($v) => $v
   !== '' && $v !== null && $v !== 0)` inside the
   category controller. PHPStan flagged the second
   and third checks as always-true — `$currentFilters`
   is typed `array<string,string>`, so a non-empty
   string is never null or 0. Fixed by keeping only
   the `!== ''` check.

   Fourth occurrence of the "extra null check that
   PHPStan catches" bug in this stage's wider work.
   The pattern: match the codebase's existing idiom
   before writing a new nullable check.

### What Session 1 delivered

`app/Core/Container.php`:

  - `build(string $class): object` - reflects the
    constructor, resolves class-typed parameters
    recursively through `get()`, caches the recipe
    per class, caches the built instance as a
    singleton.

    cached, not bound, and names a concrete class,

  - `isInstantiable()` - abstract classes,

  - Untyped parameters must have a default.
  - Recipe cached per class. Reflection runs once
    per class per request.

### Bugs found

One process mistake, not a code bug.

`sed -n '138,143p'` on the provider returned the
`CustomerAuthService` binding instead of the
`ProductVariantRepository` binding. The line numbers
were stale - six removals had already shifted every

The lesson is a small extension to Pattern 23
(cascade check before every patch). The cascade

earlier snapshot of a file that has been edited

### Decisions made

- **Auto-construction is a fallback, not a
  replacement.** Explicit bindings always win. The
  change adds a fourth branch to `get()` that only
  fires when the first three do not.
- **`has()` stays strict.** Reports explicit
  registration only. The Kernel's middleware guard
  depends on this.
- **The cleanup pass is a separate commit from the
  mechanism change.** Removing a binding asserts
  that auto-construction produces an equivalent
  instance. Two concerns, two commits.
- **Nine removals, one file, one commit.** Each
  removal individually verified. The commit records
  every removed binding and the verification summary.
- **Bindings with any ambiguity stay.** A class that
  captures a primitive, calls a method after
  construction, holds shared state, or is depended
  on by many consumers keeps its explicit binding.
  The cleanup is conservative.

### Bugs found

Four real bugs, all caught in the browser test pass
of Session 2.

1. **`Database::insert()` wrong argument shape.**

   `ReturnRequestRepository::create()` and
   `ReturnRequestItemRepository::createMany()` were
   calling `$this->db->insert('table_name', $data)`
   where `$data` was an associative array. The
   `Database::insert()` signature is
   `insert(string $sql, array $params = [])` — it
   passes the first argument straight to
   `PDO::prepare()`.

   The first form submission threw:
   `SQLSTATE[42000]: Syntax error... near
   'commerce_return_requests'`. The table name was
   being prepared as a SQL statement.

   Diagnosed by direct CLI reproduction of
   `ReturnRequestService::open()` with real ids.
   Fixed by building the full INSERT statement and
   passing a positional params array, matching the
   shape used by `OrderRepository::create()` and
   `OrderItemRepository::createMany()`.

   Same class of bug as the "verify the codebase's
   existing idiom before writing a new read" pattern
   documented in earlier sessions. This time on the
   write side.

2. **`ReturnController extends StorefrontController`
   without the account shell wrap.**

   The first draft of the Session 2 controller
   extended the wrong parent. `AccountController`
   overrides `render()` to route every page through
   the account shell. `StorefrontController` does
   not. The new controller rendered raw views
   without the shell — no sidebar, no breadcrumb.
   Then the views' `if ($customer === null) return;`
   guards fired because the controller never passed
   `$customer` into the render data. The page
   rendered blank between the header and footer.

   Fixed by matching the shape of `MessageController`,
   `RecentViewController`, and `WishlistController`
   exactly: extend `StorefrontController` directly,
   use a private `renderAccount()` helper, and pass
   `'customer' => $customer` to every render call.

3. **`@file_put_contents` silently dropping every log
   entry.**

   `app/Platform/Support/Logger.php` line 45 wrote
   with `@file_put_contents($file, $line, FILE_APPEND
   | LOCK_EX)`. The `@` suppressed every warning.
   The return value was ignored. The file
   `storage/logs/app.log` had not been written to
   since 2026-09-30 23:39.

   Every exception in this session was dropped. The
   500 from bug 1 was invisible in the log.

   Fixed by checking the return value and falling
   back to `error_log()` with a `[ca-fallback]`
   prefix. The fallback destination is Apache's
   error log (or stderr on CLI). If the primary
   target ever stops failing, the prefix stops
   appearing.

4. **Third occurrence of the `view_partial()` shape
   change cascade.**

   The `order-detail.php` header was changed from a
   single `<span>` badge to a `<div>` wrapper around
   two badges. The wrapper needed a CSS rule
   (`.sf-order-detail-badges`) to lay the two badges
   side by side. Without it they stacked vertically.

   Caught on the second browser reload after the
   header change. Fixed by adding the wrapper rule
   to `storefront-auth.css` with the same
   read-then-write discipline applied to every PHP
   file in the session.

   The class-name collision check (grep the class
   across `app/`, `resources/`, `public/`) is what
   confirmed the new class was safe to add.

### Decisions made

- **Rewrote Session 2 after a full read pass.**
  The first attempt was built from a mental model.
  Reverted via `git reset --hard 50f77b6` and
  rebuilt after reading every file the stage
  touches and every file that depends on them.

- **Followed the existing controller pattern.**
  The three sibling controllers
  (`MessageController`, `RecentViewController`,
  `WishlistController`) all gate internally on
  `CustomerAuthService::user()` and use a private
  `renderAccount()` helper. The new
  `ReturnController` matches that shape exactly.
  No new pattern.

- **Reverted the abandoned draft on `backup/main`.**
  `git reset --hard` made `main` diverge from
  `backup/main`. The abandoned `85876f1` was
  force-replaced by the clean redo `8a3e56b`
  using `--force-with-lease`. The draft's content
  is not preserved anywhere. It was not worth
  keeping.

- **"Being returned" vs "returned" is
  status-driven.** In-flight means the return
  request is in status `requested`, `approved`,
  or `received`. Processed means `refunded`. The
  order item's `returned_quantity` only increments
  when Session 3 calls `processRefund()`.

  The order detail page shows:
    - `Qty N (N of M returned)` when
      `returned_quantity > 0`.
    - `Qty N (N being returned)` when in-flight > 0
      and nothing has been refunded yet.
    - `Qty N` alone otherwise.

- **The order snapshot does not change.** Order
  item `quantity`, `unit_price`, and `line_total`
  are frozen at order time. Returned and
  in-flight state are annotated on top of the
  snapshot. This is the reason the screenshot with
  `Qty 2` and `Qty 2 (1 being returned)` is
  correct: the customer bought two units, is
  returning one, and the historical record stays
  at two.

- **The refund / net-paid rows are dormant until
  Session 3.** `order-detail.php` renders
  "Refunded" and "Net paid" only when
  `$order->refundedTotal > 0`. That column is
  only set by `processRefund()`. The rows are in
  the code but will not appear on the customer
  side until the admin processes a refund.

### New patterns for docs/REMEMBER.md

One pattern candidate worth recording.

**Candidate - ORM-adjacent helper methods take an
argument shape, and the shape must be read before
calling them.** `Database::insert()` takes a SQL
string and a positional params array. It does not
take a table name and a column => value map. The
two shapes look similar; the error is a 500 with
a MySQL syntax error at the first argument.

The general rule: any time a call is made to a
helper that abstracts PDO, read the helper's
signature and body first. Do not assume its
argument shape from its name.

This overlaps with the cascade check discipline
but is specific enough to be its own pattern if
the project adds more write-side abstractions
later.
