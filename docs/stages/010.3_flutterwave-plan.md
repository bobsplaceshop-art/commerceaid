## Purpose

Flutterwave, an African payment aggregator with
coverage across 30+ countries and 30+ currencies.
The customer pays through Flutterwave's hosted
page; Flutterwave routes the payment to whichever
channel the customer chooses (card, mobile money,
bank transfer).

Flutterwave is the last sub-stage of Stage 010.
It is also the last provider that would change
the payments schema. After it closes, the payment
layer's schema is frozen.

Flutterwave's API differs from the four providers
already shipped in three ways:

  1. The webhook signature is a plain shared
     secret, not a cryptographic HMAC. Flutterwave
     sends the secret hash the merchant configured
     as the verif-hash header. Comparison is a
     string equality, not a hash computation.

  2. The webhook must return 200. Flutterwave
     does not care about the body. Any other
     status is a failure. Retries are three
     times, 30 minutes apart, if enabled.

  3. Partial refunds are supported by amount.
     The minimum refund is KES 10.

## The Flutterwave API v3

Base URLs:

  Sandbox  https://api.flutterwave.com/v3
  Live     https://api.flutterwave.com/v3

(Same base URL for both. The key determines the
environment.)

### Endpoints

  POST /payments
       - Create a payment and return the hosted
         checkout link
       - Bearer auth with the secret key
       - Body: tx_ref, amount, currency,
         redirect_url, customer (email, name,
         phonenumber), customizations, payment_options
       - Returns: status, data.link, data.tx_ref

  GET  /transactions/{id}/verify
       - Verify a transaction by its Flutterwave
         id
       - Bearer auth
       - Returns: status, data.status
         (successful | failed | pending),
         data.amount, data.currency, data.tx_ref

  POST /transactions/{id}/refund
       - Refund a transaction
       - Bearer auth
       - Body: amount (for partial; omit for full)
       - Returns: status, data

### The webhook

Flutterwave posts a JSON body to the registered
webhook URL when a transaction's status changes:

    {
      "event": "charge.completed",
      "data": {
        "id": 12345,
        "tx_ref": "ORD-000123",
        "status": "successful",
        "amount": 100.00,
        "currency": "KES",
        ...
      }
    }

The `event` field carries the event type. The
`data.id` is the Flutterwave transaction id. The
`data.tx_ref` is the merchant reference.

The response must be HTTP 200. Any other status
is treated as a failure. Retries are three
times, 30 minutes apart.

### Signature scheme

**This is the trap.** Flutterwave sends the
secret hash the merchant configured in the
dashboard as the `verif-hash` header. It is
literally a plain string, not an HMAC of the
payload.

The verification is:

    $header = $headers['verif-hash'] ?? '';
    $expected = $this->settings->string(
        'payments.flutterwave.secret_hash', ''
    );
    return $header !== '' && hash_equals($expected, $header);

`hash_equals()` for timing safety, though the
risk is theoretical since both sides are the
merchant's own secret.

Do not compute an HMAC of the payload. That is
the mistake the Flutterwave docs' less-experienced
readers make. The header carries the secret
itself.

## The charge flow

    1. Customer selects "Flutterwave" at checkout.
    2. CheckoutController::place() creates the
       order with payment_status = 'unpaid' and
       payment_provider_key = 'flutterwave'.
    3. PaymentChargeService::charge() calls
       Provider::charge().
    4. FlutterwaveProvider::charge() does:
         a. POST /payments with tx_ref = the order
            number, amount, currency,
            redirect_url.
         b. Store the tx_ref and the transaction
            id in commerce_flutterwave_requests.
         c. Return ['ok' => true,
                    'redirect_url' => $data['link'],
                    'provider_reference' => $txRef].
    5. The controller redirects the customer to
       Flutterwave's hosted page.
    6. The customer pays.
    7. Flutterwave redirects to the redirect_url
       with ?transaction_id=...&tx_ref=...&status=...
    8. FlutterwaveReturnController reads the
       transaction_id, calls GET /verify, writes
       the paid state if status is 'successful'.
    9. Flutterwave posts the webhook to
       /webhooks/flutterwave.
    10. WebhookController::flutterwave() verifies
        the verif-hash, calls handleWebhook().
    11. The handler calls GET /verify, writes the
        paid state if 'successful'.

The return controller and the IPN handler are
idempotent against each other: both check
payment_status === 'paid' before writing.

## The refund flow

Simple. POST /transactions/{id}/refund with the
amount. Partial refunds are supported. Minimum
refund is KES 10.

The plan defaults refund_enabled to false. When
disabled, the refund is recorded offline by
PaymentRefundService without a Flutterwave call.
When enabled, the provider calls the refund
endpoint with the transaction id stored on the
order's payment_reference.

## Settings

Six credential entries:

    payments.flutterwave.mode            sandbox | live
    payments.flutterwave.public_key
    payments.flutterwave.secret_key
    payments.flutterwave.secret_hash
    payments.flutterwave.redirect_url
    payments.flutterwave.refund_enabled  bool, default false

The `secret_hash` is the value the merchant
configures in the Flutterwave dashboard. It is
returned in the verif-hash header on every
webhook.

The `redirect_url` is where the customer returns
after paying.

## The new table

Migration 0345:

    commerce_flutterwave_requests
      id                   BIGINT UNSIGNED PK AUTO_INCREMENT
      store_id             BIGINT UNSIGNED NOT NULL
      order_id             BIGINT UNSIGNED NOT NULL
      tx_ref               VARCHAR(80) NOT NULL
      transaction_id       VARCHAR(60) NULL
      status               ENUM('pending','completed','failed')
                           NOT NULL DEFAULT 'pending'
      amount               DECIMAL(18,4) NOT NULL
      currency_code        CHAR(3) NOT NULL
      failure_reason       VARCHAR(255) NULL
      created_at           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
      updated_at           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                          ON UPDATE CURRENT_TIMESTAMP

      UNIQUE KEY uniq_com_flutter_tx_ref (tx_ref)
      KEY idx_com_flutter_order (order_id)
      KEY idx_com_flutter_status_created (status, created_at)
      FK store_id -> commerce_stores(id) CASCADE
      FK order_id -> commerce_orders(id) CASCADE

The unique key on tx_ref is the idempotency guard.
Flutterwave delivers webhooks at least once; a
duplicate hits the unique key and the handler
no-ops.

## The webhook route

    POST /webhooks/flutterwave

Registered in routes/commerce.php beside the
existing Stripe, PayPal, M-Pesa, and Pesapal
routes. The same middleware list: ['store']. No
CSRF.

WebhookController gains a flutterwave() method,
mirroring stripe(), paypal(), mpesa(), and
pesapal(). Flutterwave's webhook carries a JSON
body, so the shared handle() works without a
synthetic body. The one difference: the response
must be 200, not 204.

---

## The return controller

    GET /checkout/flutterwave/return

A new FlutterwaveReturnController, mirroring
PesapalReturnController and StripeReturnController.
Reads the transaction_id and tx_ref from the
query, calls GET /verify, writes the paid state
if 'successful', redirects to confirmation.

## Test approach

Flutterwave's sandbox uses test keys from the
developer dashboard. The hosted payment page
accepts test card numbers (4242 4242 4242 4242
and similar) and test mobile money flows.

The smoke case: a synthetic webhook body against
a seeded pending row, with the correct
verif-hash header. Asserts verifyWebhook() returns
true, handleWebhook() calls the verify endpoint
(which returns 'successful' for a real test
transaction), and the order flips to paid.

The offline part of the smoke case exercises
verifyWebhook() and extractEventId() without the
HTTP call. The handleWebhook() call needs the
network. The smoke case can assert the offline
parts and skip the network part, or hit the
sandbox.

A second smoke case mirrors the other providers'
route tests: exercises WebhookController::flutterwave()
with a synthetic body.

## What is not in this sub-stage

  - Flutterwave Transfers (payouts). The platform
    is payin-only.
  - Subaccounts (split payments, marketplaces).
    Not applicable to a single-merchant store.
  - Payment plans (recurring). The platform does
    not support subscriptions today.
  - Multi-currency conversion. Flutterwave
    supports multiple currencies; the store's
    currency is what is charged.

## Open questions

  1. **The webhook's event field.** Flutterwave
     sends `event: "charge.completed"`. The
     event type should be used in the
     commerce_webhook_events row's event_type
     column. Read `$event['event']` for the
     type.

  2. **The verif-hash header.** The header name
     arrives as `verif-hash`. The
     WebhookController's lowercasedHeaders()
     method iterates a fixed list of names.
     Flutterwave's header must be added to that
     list, or the controller reads it from the
     request directly in the flutterwave()
     method.

  3. **The webhook's expected response.** The
     Flutterwave docs are explicit that 200 is
     required. The shared handle() returns 204
     on success for other providers. The
     flutterwave() method overrides the success
     response to 200 with a JSON body (or an
     empty 200).

These are resolved in the sections above.
Reviewed at Session 1 open.
