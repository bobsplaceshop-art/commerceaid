# Stage 008G.4a.1 - Media Library Page

**Status:** In progress
**Opened:** 2026-09-30
**Depends on:** 008G.4a (upload pipeline)

---

## Goal

An admin page at `/commerce/ca-admin/media` for browsing,
filtering, and managing uploaded files. Grid view with
thumbnails. Search, filter, sort, paginate. Delete with
usage awareness. Replace in place.

---

## What Already Exists

The read of the codebase confirms:

- `core_entity_files` is a Platform polymorphic link
  table. Its API (`EntityFileRepository`) is defined.
  No Commerce code writes to it yet.
- `core_media_meta` and `core_media_variants` are the
  Commerce-side metadata tables from 008G.4a.
- `MediaRepository` handles upload, lookup, meta updates,
  and variant resolution. It does not know about stores.
- `MediaItem` exposes `url()`, `variantUrl()`,
  `dimensionsLabel()`, `humanSize()`, `altText()`,
  `isImage()`, `hasDimensions()`, `aspectRatioLabel()`.
- The admin has list/table/grid patterns in
  `resources/views/admin/products/index.php`.

---

## What This Stage Builds

The browse/manage surface for uploaded files.

The stage is smaller than 008G.4a. No new tables. No new
Platform code. No new service. Just:

  - A repository method to list a store's files
  - A repository method to compute a file's usage count
  - A controller with list/delete actions
  - A grid view with filters
  - A link from the admin sidebar

## Decisions Locked

### Decision 1 - Files are scoped to a store via core_entity_files

Every upload writes a link:

    file_id       = the newly uploaded file
    entity_type   = 'store'
    entity_id     = the current store ID
    file_category = the upload context ('store-logo', etc.)
    linked_by     = the uploading admin user

The unique key on `(file_id, entity_type, entity_id,
file_category)` means re-uploading the same file for the
same store and context is a no-op. FileService::link()
handles this.

The media page reads files by joining `core_entity_files`
on `entity_type = 'store'` and `entity_id = <store>`.

### Decision 2 - MediaRepository writes the link

`storeFromUpload()` gains two parameters: `int $storeId`
and uses its existing `?int $userId` for `linked_by`.

The controller (SettingsController, MediaController)
resolves the current store ID from StoreContext and
passes it in. The repository does the write.

Rationale: the link is part of the upload transaction.
If the file row exists but the link does not, the file is
orphaned. Both writes belong in the same method.

### Decision 3 - Read-side uses a JOIN, not EntityFileRepository

`MediaRepository::paginateForStore()` runs a single query:

    SELECT f.*, m.*
      FROM core_files f
      INNER JOIN core_entity_files ef
        ON ef.file_id = f.id
      LEFT JOIN core_media_meta m
        ON m.file_id = f.id
     WHERE ef.entity_type = 'store'
       AND ef.entity_id = ?
       AND f.deleted_at IS NULL
     ORDER BY f.created_at DESC
     LIMIT ? OFFSET ?

Filters (mime, search, category) and sort add clauses.

The `EntityFileRepository` is not used for listing. It is
the write-side API. Reads join directly, which is one
query instead of two, and pagination stays in SQL.

### Decision 4 - No backfill for existing uploads

Two files were uploaded in the previous session without a
store link. They render correctly in the storefront (the
store logo and favicon columns point to them). They will
not appear in the media page.

A backfill migration is not worth the complexity. The
operator can re-upload from the media page if they want
the files listed. Pre-launch stage; the two files are
test data.

### Decision 5 - Delete is soft, and checks usage

`MediaRepository::softDelete()` already exists. The media
page adds two layers on top:

  - `usageCountForFile(int $fileId): int` counts how many
    rows in `core_entity_files` reference the file. A file
    linked to a store logo has count 1. A file linked to
    three product images has count 3.
  - The delete action checks the usage count first. If it
    is > 0, the response is a 409 with a JSON message
    naming where the file is used. The admin must
    unlink first (from the referencing entity's edit page)
    before deleting here.

A "force delete" bypass is not offered. Accidental
removal of a file that is still in use is a class of
bug we do not need to ship.

### Decision 6 - Replace-in-place is deferred

The ROADMAP entry mentions "replace in place (new upload
swaps the file behind an existing media ID, no
re-linking)". That is a nice-to-have but not essential
for this stage.

Replace-in-place has real complexity: the old file must
be verified as no longer referenced by any other entity,
the swap has to be atomic across `core_files` and every
referencing row, and the disk artifact cleanup has to
happen after the swap succeeds. It is a stage of its own.

For 008G.4a.1, the operator deletes and re-uploads. If
that workflow turns out to be common, 008G.4a.1a adds
replace-in-place.

### Decision 7 - No image editing

No crop, no rotate, no filters, no alt-text editor. The
media page is a browser, not an editor. Alt text and
credit can be set from the file detail modal (a small
form). Image editing is a Stage 012 concern if it ever
becomes one.

## Files To Modify

### app/Commerce/Repositories/MediaRepository.php

Add:

    paginateForStore(int $storeId, array $filters, int $page, int $perPage): array
      Returns ['items' => array<MediaItem>, 'total' => int,
               'page' => int, 'per_page' => int, 'pages' => int].
      Filters: q (filename search), mime (prefix match),
               category (file_category), sort (newest |
               oldest | name | size).

    usageCountForFile(int $fileId): int
      COUNT from core_entity_files WHERE file_id = ?.

    findUsageForFile(int $fileId): array
      Returns the entity_type / entity_id / category
      rows that reference the file. Used by the delete
      modal to show "used by: store logo, product #42".

    linkToStore(int $fileId, int $storeId, string $category, ?int $userId): void
      Writes the core_entity_files row. Idempotent via
      the UNIQUE key. Uses INSERT IGNORE.

Modify:

    storeFromUpload() gains a required int $storeId parameter.
    After the file and variants are registered, it calls
    linkToStore() with the store ID, context, and the
    uploading user ID.

### app/Commerce/Controllers/Admin/MediaLibraryController.php (new)

Three actions:

    index(Request, array): Response
      Renders the grid. Reads filters and page from the
      query string. Calls MediaRepository::paginateForStore().
      Passes the result to the view inside the admin shell.

    delete(Request, array): Response
      POST. Reads a file ID from the body. Checks usage
      count. If in use, flashes an error and redirects
      back with the filter query string preserved. If
      not in use, calls softDelete() and redirects.

    updateMeta(Request, array): Response
      POST. Reads alt_text and credit from the body.
      Updates the core_media_meta row via
      MediaRepository::updateMetaText().

### app/Commerce/Controllers/Admin/SettingsController.php

saveFileColumn() passes the store ID to storeFromUpload().

### resources/views/partials/sidebar.php

Add a Media nav item under the existing 'catalog' group,
next to Products, Categories, Brands, Inventory, and
Attributes.

The media library holds product images, category banners,
brand logos, and store branding. That is catalog-adjacent.
A merchant looks for "where do I manage the images in my
store" in the same mental bucket as their products.

A separate "Content" group would be premature: it would
have one item today. If blog posts and CMS pages arrive
later, they can start their own group then.

The nav item declares:

    ['label' => 'Media',
     'href'  => '/commerce/ca-admin/media',
     'icon'  => 'bi-images']

No permission gate - any admin can browse files.

Cascade (verified by grep): the sidebar is a single
partial rendered from the admin layout. Adding a group
item is a one-line change to the `$groups` array. No
view structure changes. No permission wiring needed
beyond the item itself.

## Test Protocol

    T-1  Visit /commerce/ca-admin/media. The grid renders.
         The two existing test uploads are NOT shown
         (no store link). An empty-state message appears
         explaining what the grid shows and how to add
         files.

    T-2  Upload a new logo from Store Settings. Return to
         /commerce/ca-admin/media. The file appears in
         the grid.

    T-3  Filter by category "store-logo". The new logo
         appears; other uploads do not.

    T-4  Search for part of the filename. Only matching
         files appear.

    T-5  Sort by size descending. The largest file is
         first.

    T-6  Click Delete on the store logo file. The delete
         is blocked: "This file is used by: store logo."
         The Delete button is disabled in the modal.

    T-7  Remove the store logo from Settings (unlink).
         Return to the media page. Delete now succeeds.

    T-8  Update alt text from the detail modal. The value
         persists on reload.

    T-9  Pagination: upload 30 files, verify the page
         shows 24 and offers a next page.

    T-10 Verify no store's files leak into another
         store's media page. Requires a second store in
         dev; may be skipped if only one exists.

## Out of Scope

- Replace-in-place (008G.4a.1a if needed).
- Image editing (crop, rotate, filters).
- Bulk actions (select N, delete all, edit meta for
  many).
- Uploading from the media page itself. Uploads happen
  from the entity's edit page (Store Settings,
  eventually the product editor). The media page is
  browse + manage, not a second upload path.
- Alt text or credit editing outside the detail modal.
- Real-time search (AJAX). Filtering is a page reload.
- A public media browser. The media page is admin only.
