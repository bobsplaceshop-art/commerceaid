**Date opened:** 2026-09-28
**Status:** Planned

(guest order claim), Stage 008C (customer auth)

## Purpose

Every /account/* page shares one shell. Left sidebar
navigation, breadcrumbs, consistent header. The pages that
exist (dashboard, orders, addresses, password, claims) gain
a shared visual frame. New pages added by later sub-stages
(wishlist, recent, messages, returns) slot into the same
frame automatically.

Reference: AliExpress-class account portal (sidebar, tabbed
sections). We build better: our sidebar groups logically,
our active state is exact-match, our mobile strategy is a
scrollable tab strip rather than a drawer that hides the
structure.

## The Shell Architecture

Views cannot be wrapped mid-render. So the shell is a
view that renders the inner view.

    AccountController::render($view, $data)
        |
        v
    parent::render('storefront.account._shell', $data + [_account_inner_view])
        |
        v
    StorefrontController::render('storefront.account._shell', $data)
        |
        v
    View::render('storefront.account._shell', $data, 'storefront.layouts.main')
        |
        v
    The shell view:
        - Renders the sidebar partial (left column)
        - Renders the inner view via view_partial(_account_inner_view) in the right column
        - Both wrapped in layout chrome

One controller override. One new shell view. One new sidebar
partial. Existing views lose their outer wrapper but keep
their content.

## The Sidebar Structure

Grouped, collapsible sections with localStorage persistence
(same pattern as the admin sidebar).

    My Account
      Dashboard
      Addresses
      Password

    My Orders
      Orders
      Claims          (badge when claimable orders exist)

    Returns           (link to 008H - "coming soon" until then)

    Wishlist          (link to 008G.1 - "coming soon")

    Recently Viewed   (link to 008G.2 - "coming soon")

    Messages          (link to 008G.3 - "coming soon", badge placeholder)

Active item highlighted via exact-match on the current path
(the same rule as the admin sidebar - prefix matching broke
on the admin Dashboard link, so we don't repeat that).

Groups collapse and expand. Active group defaults open.
State persists to localStorage['sf-account-nav'].

## The Mobile Strategy

At <768px, the sidebar becomes a horizontally-scrollable
tab strip at the top of the page. Each nav item is a chip.
The active chip is highlighted. The customer scrolls
horizontally to see more items.

Why not a drawer:
  - A drawer hides the navigation until the customer taps
    the hamburger. That adds a step.
  - Account pages are used to CHECK things, not browse.
    Seeing the destinations at a glance is faster.
  - Horizontal scroll is a native mobile pattern that
    customers already understand from app tab bars.

## What Stays the Same

- `storefront.layouts.main` remains the outer layout.
  Header and footer unchanged.
- Every existing account method keeps its signature and
  its data assembly.
- The order detail page's content is unchanged. Only the
  outer wrapper changes.
- The auth pages (login, register, forgot, reset) stay
  outside the shell. They use `.sf-auth-wrap` +
  `.sf-auth-card` unchanged. Auth is not account management.
