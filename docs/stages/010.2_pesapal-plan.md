## Purpose

Pesapal, a Kenyan payment gateway that
aggregates multiple payment methods: card
(Visa, Mastercard), mobile money (M-Pesa,
Airtel Money), and bank transfers. The customer
pays through Pesapal's hosted page; Pesapal
routes the payment to whichever method the
customer chooses.

Pesapal is the second real provider after
M-Pesa. Its flow is a redirect, not an in-page
STK push. The customer leaves the site, pays on
Pesapal's hosted page, and Pesapal sends them
back. This makes it closer to Stripe and PayPal
than to M-Pesa.

Two things make Pesapal distinct:

  1. The verification is an outbound call to
     Pesapal's transaction status endpoint, not a
     signature check. Pesapal does not sign its
     IPN notifications.

  2. The access token expires after 5 minutes.
     The provider fetches a fresh token on each
     request rather than caching it for an hour
     like PayPal's OAuth or M-Pesa's Daraja
     token.

## The Pesapal API 3.0

Base URLs:

  Sandbox  https://cybqa.pesapal.com/pesapalv3
  Live     https://pay.pesapal.com/v3

### Endpoints

  POST /api/Auth/RequestToken
       - OAuth-like token generation
       - Body: consumer_key, consumer_secret
       - Returns: token (valid 5 minutes),
         expiryDate

  POST /api/Transactions/SubmitOrderRequest
       - Create an order and return the redirect URL
       - Bearer auth with the token
       - Body: id (merchant reference),
         currency, amount, description,
         callback_url, notification_id,
         billing_address
       - Returns: order_tracking_id, redirect_url,
         merchant_reference

  GET  /api/Transactions/GetTransactionStatus
       - Query the status of an order
       - Bearer auth
       - Query: orderTrackingId
       - Returns: payment_status_description
         (PENDING | COMPLETED | FAILED | INVALID),
         confirmation_code, amount, currency

  POST /api/Transactions/RefundRequest
       - Refund a completed payment
       - Bearer auth
       - Body: confirmation_code, amount,
         username, remarks
       - Returns: 200 (received) or 500 (rejected)
       - Limitations: merchant must approve;
         multiple refunds not allowed; mobile
         money can only be fully refunded;
         card can be partial

### The IPN (Instant Payment Notification)

Pesapal posts to the registered IPN URL when a
transaction's status changes. The IPN carries
query parameters:

  pesapal_notification_type=CHANGE
  pesapal_transaction_tracking_id=<tracking id>
  pesapal_merchant_reference=<merchant ref>

The platform must respond to the IPN with HTTP
200 and echo the same query parameters back.
Pesapal does not sign the IPN. The verification
is an outbound call to GetTransactionStatus
using the tracking id.

### Signature scheme

Pesapal does not sign its IPN notifications.
There is no HMAC header and no certificate. The
verification path is:

  1. Read the order_tracking_id from the IPN.
  2. Look it up in commerce_pesapal_requests.
  3. Call GetTransactionStatus with the id.
  4. Read payment_status_description from the
     response.
  5. If COMPLETED, mark the order paid.

Step 2 is the security boundary. A callback
whose tracking id does not match a pending
request this store initiated is refused before
the outbound call.

## The charge flow

    1. Customer selects "Pesapal" at checkout.
    2. CheckoutController::place() creates the
       order with payment_status = 'unpaid' and
       payment_provider_key = 'pesapal'.
    3. PaymentChargeService::charge() calls
       Provider::charge().
    4. PesapalProvider::charge() does:
         a. POST /api/Auth/RequestToken to fetch
            a token.
         b. POST /api/Transactions/SubmitOrderRequest
            with the order details.
         c. Store the order_tracking_id and
            merchant_reference in
            commerce_pesapal_requests.
         d. Return ['ok' => true,
                    'redirect_url' => $redirectUrl,
                    'provider_reference' => $orderTrackingId].
    5. The controller redirects the customer to
       Pesapal's hosted page.
    6. The customer pays.
    7. Pesapal redirects to the callback URL the
       platform supplied. The customer lands on
       /checkout/pesapal/return.
    8. The PesapalReturnController reads the
       tracking id, calls GetTransactionStatus,
       and writes the paid state if the IPN has
       not arrived yet.
    9. Pesapal posts the IPN to /webhooks/pesapal.
    10. WebhookController::pesapal() verifies the
        tracking id against the pending set and
        calls handleWebhook().
    11. The handler writes payment_status = 'paid',
        paid_at, payment_reference (the
        confirmation_code).

The return controller and the IPN handler are
idempotent against each other: both check
payment_status === 'paid' before writing.

## The refund flow

Pesapal's refund API has limitations:

  - The merchant must approve the refund.
  - Multiple refunds are not allowed. One
    refund per payment.
  - Mobile money payments can only be fully
    refunded. Card payments can be partial.
  - Refunds are in the original currency.

The plan defaults refund_enabled to false. When
disabled, the refund is recorded offline by
PaymentRefundService without a Pesapal call.
When enabled, the provider calls the refund
endpoint with the confirmation_code stored on
the order's payment_reference.

## Settings

Six credential entries:

    payments.pesapal.mode             sandbox | live
    payments.pesapal.consumer_key
    payments.pesapal.consumer_secret
    payments.pesapal.ipn_id
    payments.pesapal.callback_url
    payments.pesapal.refund_enabled   bool, default false

The ipn_id is returned by Pesapal when the IPN
URL is registered. The callback_url is where
the customer returns after paying.

## The new table

Migration 0344:

    commerce_pesapal_requests
      id                   BIGINT UNSIGNED PK AUTO_INCREMENT
      store_id             BIGINT UNSIGNED NOT NULL
      order_id             BIGINT UNSIGNED NOT NULL
      order_tracking_id    VARCHAR(80) NOT NULL
      merchant_reference   VARCHAR(80) NOT NULL
      status               ENUM('pending','completed','failed')
                           NOT NULL DEFAULT 'pending'
      payment_status_description VARCHAR(60) NULL
      confirmation_code    VARCHAR(60) NULL
      amount               DECIMAL(18,4) NOT NULL
      currency_code        CHAR(3) NOT NULL
      created_at           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
      updated_at           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                          ON UPDATE CURRENT_TIMESTAMP

      UNIQUE KEY uniq_com_pesapal_tracking (order_tracking_id)
      KEY idx_com_pesapal_order (order_id)
      KEY idx_com_pesapal_status_created (status, created_at)
      FK store_id -> commerce_stores(id) CASCADE
      FK order_id -> commerce_orders(id) CASCADE

The unique key on order_tracking_id is the
idempotency guard. A duplicate IPN hits the
unique key on the row and the handler no-ops.

## The webhook route

    POST /webhooks/pesapal

Registered in routes/commerce.php beside the
existing Stripe, PayPal, and M-Pesa routes. The
same middleware list: ['store']. No CSRF.

WebhookController gains a pesapal() method,
mirroring stripe(), paypal(), and mpesa(). The
handle() method already funnels; adding Pesapal
is three lines.

---

## The return controller

    GET /checkout/pesapal/return

A new PesapalReturnController, mirroring
StripeReturnController and PayPalReturnController.
Reads the order number and tracking id from the
query, calls GetTransactionStatus, writes the
paid state if the IPN has not arrived yet,
redirects to confirmation.

## What is not in this sub-stage

  - Multi-currency conversion. Pesapal supports
    multiple currencies; the store's currency is
    what is charged.
  - Recurring payments. Pesapal supports
    subscriptions; the platform does not.
  - Refund on mobile money (full only). The
    provider records the intent; the merchant
    approves in the Pesapal dashboard.
  - A waiting page. The customer leaves for
    Pesapal's hosted page and returns. No
    polling.

## Open questions

  1. **The IPN response format.** Pesapal
     requires the platform to echo the query
     parameters back with HTTP 200. The
     WebhookController's handle() returns
     Response::noContent() (204) for other
     providers. The Pesapal handler must
     respond 200 with the echoed body. That is
     a per-provider response shape, not a
     change to the shared handle().

  2. **The merchant approval on refunds.**
     Pesapal's refund API returns 200 when the
     request is received, not when the refund
     is processed. The refund row stays pending
     until Pesapal confirms. The status polling
     for refunds is a follow-up.

  3. **The 5-minute token.** The token expires
     after 5 minutes. The provider fetches a
     fresh token on each charge and each status
     call. No caching. The extra round trip is
     acceptable.

These are resolved in the sections above.
Reviewed at Session 1 open.
