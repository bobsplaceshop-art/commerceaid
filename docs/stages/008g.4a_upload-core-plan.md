# Stage 008G.4a - Upload Core + Store Branding

**Status:** In progress
**Opened:** 2026-10-02
**Depends on:** 008G (storefront polish), 008A (Store model),
008E.1 (Settings page)

---

## Why This Sub-Stage Exists

The original 008G.4 PWA plan assumed a static icon path.
During review, the customer identified the sequencing
problem: the Store model already carries logo_file_id,
favicon_file_id, pwa_name, pwa_short_name, pwa_theme_color,
pwa_background_color - and no code reads them because there
is no working upload path in the Commerce admin.

Shipping PWA first would be "a cart in front of the donkey."

File upload is load-bearing infrastructure. Store branding,
product images, category banners, blog heroes, and PWA
icons all depend on it. This sub-stage builds the upload
path and wires it to Store Settings. Product images,
media page, and PWA follow in 008G.4a.1, 008G.4a.2, and
008G.4b.

## What Already Exists (Read Before Designing)

Most of the upload pipeline exists in Platform. This
sub-stage is composition, not greenfield.

**FileService** (`app/Platform/Services/FileService.php`)
- `store(array $file, ?int $userId, string $category, int $maxMb): File|string[]`
- Full pipeline: `is_uploaded_file` check, validation,
  SHA-256 hashing, dedup by hash, UUID filename,
  subdirectory routing by category, `move_uploaded_file`,
  cleanup on DB failure.
- Bound in `App.php` as a singleton. Commerce can already
  resolve it via the container.

**FileValidator** (`app/Platform/Validation/FileValidator.php`)
- Extension allowlist (not denylist).
- MIME sniff via `finfo_file` (never trusts browser).
- Null byte rejection.
- Double extension rejection.
- Content scan for PHP tags, shebangs, `<script>`.
- Per-field max size.
- Returns `string[]` errors.

**FileRepository** (`app/Platform/Repositories/FileRepository.php`)
- `findById`, `findByUuid`, `findByHash`, `create`,
  `softDelete`, `hardDelete`, `forEntity`.

**EntityFileRepository**
- Polymorphic link table `core_entity_files`.
- `link`, `unlink`, `unlinkAll`, `linkCountForFile`.
- `FileService::unlink()` auto-soft-deletes when link
  count hits zero.

**File model** (`app/Platform/Models/File.php`)
- All metadata columns, `humanSize()` helper.

**FileService::directoryFor()** currently routes:
- `avatar`/`avatars` → `storage/uploads/avatars`
- `logo`/`branding` → `storage/uploads/branding`
- `cv`/`certificate`/`id_proof`/`candidate_docs` →
  `storage/uploads/candidate_docs`
- `report`/`reports`/`export` → `storage/uploads/reports`
- default → `storage/uploads/candidate_docs`

Only one caller of `store()` exists today:
`CustomFieldValueSaver` (Platform).

**Store Settings page** (`app/Commerce/Controllers/Admin/SettingsController.php`)
- Definition-driven. Adding a field is one line in
  `StoreSettingDefinitions::forGroup()`.
- Supports text, boolean, select, color field types.
- Stores values in `commerce_store_settings` key-value
  table (NOT columns on `commerce_stores`).

**Store model** already carries:
- `logoFileId`, `faviconFileId` (FKs to `core_files`)
- `pwaName`, `pwaShortName`, `pwaThemeColor`,
  `pwaBackgroundColor`
- All null/empty. Nothing writes them.

## What This Sub-Stage Builds

A working upload path in the Commerce admin, plus the
Store Settings fields that use it.

**Not a rebuild.** A thin composition layer on top of
Platform's existing infrastructure.

Concretely:

1. A new `core_media_meta` table for image-specific
   metadata (dimensions, alt text, upload context).
2. A `MediaRepository` reading `core_files` +
   `core_media_meta`.
3. A `MediaController` (admin) — upload, delete.
4. A `MediaServeController` — stream a file by UUID with
   cache headers.
5. A file-type field renderer for the Settings page.
6. A reusable upload widget partial.
7. Six new Store Settings fields: logo, favicon, PWA
   name, PWA short name, PWA theme color, PWA background
   color.
8. Wiring the six Settings fields to write `logo_file_id`,
   `favicon_file_id`, and the four PWA columns on
   `commerce_stores` — not to `commerce_store_settings`.

The last point is the key architectural decision. See
Decision 2 below.

## Compliance Notes

Two areas of data protection and copyright law shape the
media pipeline. Neither was covered by the original plan.
Both are added before any code lands.

### EXIF stripping on upload

Photographs taken on phones carry EXIF metadata: GPS
coordinates, camera make and model, serial number,
timestamps, sometimes the photographer's name. Under
DSGVO Art. 4 and Art. 5, GPS coordinates in particular are
personal data, and storing or serving them without a legal
basis is a violation. German DSGVO enforcement is active
on this specific point.

When a customer uploads a photo (a store hero image, a
product photo taken on their phone, a category banner),
that metadata is not relevant to running the store. It
serves no functional purpose and creates a compliance
exposure.

Decision: every image uploaded through the media pipeline
is re-encoded to strip EXIF before it lands in
storage/uploads/.

The pipeline step:

1. FileService validates and stores the file (unchanged).
2. MediaProcessor reads the stored file with GD.
3. MediaProcessor writes a fresh copy without EXIF.
4. The fresh copy replaces the stored file.
5. MediaProcessor reads dimensions from the fresh copy.

Re-encoding drops EXIF because the JPEG and PNG encoders
in GD write new image data and do not carry through the
APP1 metadata segment (JPEG) or the textual chunks (PNG).
WebP behaves the same way.

GD is used, not Imagick. GD is in the required extension
list per SPECIFICATION.md. Imagick is not guaranteed on
shared cPanel hosting.

Failure handling: if the re-encode fails (corrupt image,
GD error), the file is rejected and removed from disk.
We do not fall through to "store the original." A file
with un-stripped EXIF is worse than no file.

Files affected: only images. PDFs, CSVs, and other
document uploads pass through unchanged - they carry no
EXIF metadata.

### UrhG § 13 - attribution

The German Copyright Act grants authors the right to be
attributed. When a customer uploads a photograph or
illustration created by someone else, the correct practice
is to record the creator's name alongside the file.

The `credit` column on core_media_meta holds this value.
It is optional. Most uploads (a customer's own photo, a
logo the business owns) do not need a credit. The column
exists so the field is available when the media page
exposes it in the admin.

The plan does not require entering a credit. It requires
that the field exists so a customer can enter one if
they need to.

### Service worker and TTDSG § 25

The German implementation of the EU ePrivacy Directive
(TTDSG § 25) requires consent for "storage on the user's
device" unless the storage is "strictly necessary" for
providing an expressly requested service.

The PWA service worker (008G.4b) caches storefront assets
in the browser. The German regulatory reading is that
functional-necessary caching for a user-initiated feature
(the customer chose to install the PWA, or is using a site
that registers one) is exempt from the consent
requirement under § 25(2)(2). The service worker is
treated as an operational feature, not a tracking
mechanism.

The stage does not need a consent banner change. The
existing cookie consent banner is about cookies, not
service workers, and the service worker falls under the
strictly-necessary exemption.

This position is documented in the plan and will be
referenced in the 008G.4b plan when that sub-stage ships.

### Deletion rules

When a customer's account is deleted, DSGVO Art. 17 gives
them the right to erasure. For media:

- **Store branding media** (logo, favicon, PWA icons):
  uploaded by an admin, owned by the business, not the
  customer. No customer has a right to this media. It is
  not deleted on customer account deletion.

- **Product media**: uploaded by the merchant or an admin,
  owned by the business. Not deleted on customer account
  deletion.

- **Customer avatars** (future): owned by the customer.
  Deleted on account deletion. `FileService::unlink()`
  already handles the cascade via `core_entity_files`.

- **Any file linked to a deleted entity**: soft-deleted by
  the existing `FileService::unlink()` flow when the last
  link is removed.

- **Hard delete**: not used in this stage. Files are
  soft-deleted. A future cleanup job can purge
  soft-deleted files older than N days after verifying no
  restore is pending.

The current design already satisfies Art. 17 by way of the
cascade. No new code is required.

### Data minimisation

DSGVO Art. 5(1)(c) requires that personal data be
"adequate, relevant and limited to what is necessary."
The core_media_meta table stores only:

- Dimensions (width, height, aspect ratio) - technical
  metadata, not personal.
- Alt text - accessibility text, operator-authored.
- Credit - attribution, operator-authored.
- Context - a fixed enum-like string.
- Timestamps.

No customer identifiers. No file paths. No EXIF. No
geolocation. Nothing that could be used to track a
customer through their uploads.

The `uploaded_by` column on core_files is the only link
to an individual. It references `core_users`, not
`commerce_customers`. For storefront-facing uploads
(future: customer avatars), uploaded_by is null. For
admin uploads, it records which admin uploaded the file
- the same practice as core_entity_files.linked_by.

## Decisions Locked

### Decision 1 - Media metadata in a separate table

`core_files` stores file-level data (mime, size, sha256,
storage path). It does NOT store:
- Image dimensions (width × height in pixels)
- Alt text
- Aspect ratio
- Upload context (which admin page it came from)

These are image-specific. A PDF has no dimensions. A CSV
has no alt text.

New table `core_media_meta`:

    id            BIGINT UNSIGNED PK
    file_id       INT UNSIGNED  FK -> core_files(id) CASCADE
    width         INT UNSIGNED NULL
    height        INT UNSIGNED NULL
    aspect_ratio  DECIMAL(6,3) NULL
    alt_text      VARCHAR(500) NULL
    context       VARCHAR(60) NOT NULL DEFAULT 'general'
    created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
    updated_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                  ON UPDATE CURRENT_TIMESTAMP

    UNIQUE KEY uniq_file (file_id)
    KEY idx_context (context)

One row per file. Absent row = file has no image metadata
(non-image, or legacy).

The FK to `core_files.id` is `INT UNSIGNED` — matches
`core_files`'s PK type. Not `BIGINT`. See Pattern 17.

### Decision 2 - Store Settings fields write to Store columns, not key-value

The Settings page stores values as key-value rows in
`commerce_store_settings`. That works for string settings
like "currency display format" or "low stock threshold".

It does NOT work for a logo. A logo is:
- A file on disk
- A row in `core_files`
- An integer FK on `commerce_stores.logo_file_id`

That's a relationship, not a string.

Decision: the six new Settings fields write directly to
`commerce_stores` columns, not to `commerce_store_settings`.
The Settings form POST still goes to the same controller
action, but the controller detects which fields are
"store-column fields" vs "key-value fields" and routes
them accordingly.

The definition array gains a new shape:

    'store.logo_file_id' => [
        'label'    => 'Logo',
        'type'     => 'file',
        'target'   => 'column',        // new
        'column'   => 'logo_file_id',  // new
        'accept'   => 'image/*',
        'max_mb'   => 5,
        'help'     => 'Shown in the header. PNG, JPG, SVG. Max 5 MB.',
    ],

Default `target` is `'key_value'` (current behavior). The
Settings controller checks the target and either calls
`$settings->set(...)` or updates the Store row via
`StoreRepository::updateColumn(...)`.

New method on `StoreRepository`:

    public function updateColumn(int $storeId, string $column, mixed $value): void

Whitelist the column names. Never accept arbitrary
column names from the definition array without validation.

### Decision 3 - File serving via a controller, not static paths

Uploaded files live in `storage/uploads/` which is outside
`public/`. They cannot be served by Apache directly.

Two options:
1. Symlink `public/media` → `storage/uploads`.
2. Stream through a controller.

Option 2 is correct for this codebase. It allows:
- Deleted files to return 404 immediately (no symlink
  cache).
- Access control if needed later (currently public).
- Cache headers controlled per file type.

New `MediaServeController`:
- Route: `GET /media/{uuid}`
- Resolves the file by UUID (`FileRepository::findByUuid`).
- Returns 404 if not found or soft-deleted.
- Streams with `fpassthru`.
- Sets `Cache-Control: public, max-age=31536000, immutable`
  (UUIDs are stable; content never changes for a given
  UUID).
- Sets `Content-Type` from the stored mime.
- Sets `Content-Disposition: inline` for images,
  `attachment` for others.

The `uuid` is the public reference. Numeric IDs are never
exposed in URLs.

### Decision 4 - File validation: strict, image-aware

`FileValidator` allows jpg, jpeg, png, gif, pdf, doc,
docx, xls, xlsx, csv, txt. For Store Settings uploads we
want images only. The `accept` attribute in the definition
controls the browser file picker, but server-side
validation must also enforce it.

New method on FileValidator:

    public function validateAsImage(array $file, int $maxMb): array

Returns errors if the file is not a valid image, or if
dimensions fall outside the allowed range. Uses
`getimagesize()` to read dimensions without decoding.

Rules for images:
- Min width: 64
- Min height: 64
- Max width: 4000
- Max height: 4000
- Max size: 5 MB (overridable per field)
- SVG not allowed (dimension check impossible; content
  scan inadequate for SVG's script vectors)

Favicon exception: min 16×16, max 512×512, allows SVG
with an extra content check.

### Decision 5 - `directoryFor()` extended for commerce

`FileService::directoryFor()` gains commerce categories:

    'store-branding'  => 'storage/uploads/store-branding',
    'product-image'   => 'storage/uploads/product-images',
    'category-image'  => 'storage/uploads/category-images',
    'brand-logo'      => 'storage/uploads/brand-logos',

And the default fallback changes from
`storage/uploads/candidate_docs` to `storage/uploads/general`.

Rationale: `directoryFor()` is a category-to-directory
map. Adding entries does not leak product knowledge into
Platform — it just routes a category name to a folder.

The fallback change is safe: only one caller passes
`store()` today (CustomFieldValueSaver), and it always
passes an explicit category.

Cascade scope: 1. Verify with:
    grep -rn "->store(" app/ --include="*.php"

New private method `saveColumnSetting()`:

    private function saveColumnSetting(
        string $key,
        array $def,
        Request $request,
        ?int $userId
    ): void {
        $column = (string) ($def['column'] ?? '');
        if ($column === '') return;

        $field = $this->fieldName($key);
        $storeContext = $this->container->get(StoreContext::class);
        $storeId = $storeContext->id();

        // File field: check for upload, else check for remove.
        if (($def['type'] ?? '') === 'file') {
            $files = $_FILES['_upload'] ?? null;
            // ... handle upload, set column to new file id,
            // or clear column if a remove flag was posted.
            return;
        }

        // Scalar field (text, color).
        $posted = $request->input($field, null);
        if ($posted === null) return;
        $this->container->get(StoreRepository::class)
            ->updateColumn($storeId, $column, $posted);
    }

Cascade: existing fields in `StoreSettingDefinitions`
have no `target` key, so they default to `'key_value'` and
take the current path. No existing behavior changes.

## Out of Scope

- Product image upload (008G.4a.2).
- Category banner upload (later).
- Media browse page (008G.4a.1).
- PWA manifest and service worker (008G.4b).
- Image cropping / resizing on upload. Files are stored
  as uploaded. Thumbnails are a media page concern.
- Multiple files per field. Each branding field takes
  one file.
- SVG for the logo. Rejected on the general image path
  due to script injection risk. A separate validated SVG
  path may come in a later stage.
