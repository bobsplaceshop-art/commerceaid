**Status:** Planning

sub-stages 010.4-010.6 (offline methods)
**Blocks:** Nothing. Pesapal (010.2) and

---

## Purpose

Safaricom's M-Pesa, one of the largest mobile-money
networks in Africa. The customer enters a phone
number at checkout. Safaricom sends the phone a
prompt for the customer's PIN. The customer enters
the PIN. Safaricom confirms the payment over a
callback.

M-Pesa is the first real non-card, non-PayPal
provider in the codebase. Stripe and PayPal both
use a redirect flow (customer leaves the site,
comes back). M-Pesa uses a direct-charge flow with
an out-of-band customer action (the PIN prompt
arrives on the phone, the customer enters it
while the browser polls).

That difference is the point of this sub-stage. The
`PaymentProvider` interface was designed with both
flows in mind but the direct-charge case is only
tested by M-Pesa.

## The Daraja API

Safaricom's developer platform. Base URLs:

  Sandbox  https://sandbox.safaricom.co.ke
  Live     https://api.safaricom.co.ke

### Endpoints

  GET  /oauth/v1/generate?grant_type=client_credentials
       - OAuth token, valid ~1 hour
       - HTTP Basic auth: consumer_key + consumer_secret

  POST /mpesa/stkpush/v1/processrequest
       - Initiate the STK push
       - Bearer auth with the access token
       - Body: BusinessShortCode, Password,
         Timestamp, TransactionType, Amount,
         PartyA (customer phone), PartyB (shortcode),
         PhoneNumber, CallBackURL,
         AccountReference, TransactionDesc
       - Returns: MerchantRequestID,
         CheckoutRequestID, ResponseCode,
         ResponseDescription

  POST /mpesa/stkpushquery/v1/query
       - Poll the status of a pending STK push
       - Bearer auth
       - Body: BusinessShortCode, Password,
         Timestamp, CheckoutRequestID
       - Returns: ResultCode, ResultDesc, and
         (on completion) the M-Pesa receipt number

  POST /mpesa/v1/refund (optional, on newer
       plans; many integrations use manual refunds)
       - Refund an M-Pesa transaction
       - Not universally available. The merchant's
         Daraja plan determines whether this works.
         Fallback: record the refund as succeeded
         via the offline path when the refund API
         is not configured.

### The callback

M-Pesa POSTs to the CallBackURL when the customer
completes or cancels. The payload is JSON:

    {
      "Body": {
        "stkCallback": {
          "MerchantRequestID": "...",
          "CheckoutRequestID": "ws_CO_...",
          "ResultCode": 0,
          "ResultDesc": "The service request is
                         processed successfully.",
          "CallbackMetadata": {
            "Item": [
              {"Name": "Amount", "Value": 100},
              {"Name": "MpesaReceiptNumber",
               "Value": "SGR7K7T3QZ"},
              ...
            ]
          }
        }
      }
    }

`ResultCode = 0` means success. Anything else is a
failure (customer cancelled, wrong PIN, timeout,
insufficient funds).

### Signature scheme

**M-Pesa does not sign its callbacks.** There is
no HMAC header, no certificate. The callback
payload arrives as-is.

That means `verifyWebhook()` cannot use a
cryptographic check. The verification is a
comparison: extract the `CheckoutRequestID` from
the callback body, look up the provider's own
record of pending STK pushes, and confirm the
CheckoutRequestID matches a request this provider
initiated. A callback whose CheckoutRequestID is
not in the pending set is a forgery or a replay.
Return false.

The pending set lives in a new table,
`commerce_mpesa_requests`, written by `charge()`
and consumed by `verifyWebhook()` and
`handleWebhook()`. The table is a small cache,
not an audit log — a cleanup cron deletes rows
older than 24 hours.

## The charge flow

**Different shape from Stripe and PayPal.** Both
of those redirect the customer away and back. The
M-Pesa customer stays on the site.

    1. Customer selects "M-Pesa" at checkout.
    2. CheckoutController::place() creates the
       order with payment_status = 'unpaid' and
       payment_provider_key = 'mpesa'.
    3. PaymentChargeService::charge() calls
       Provider::charge().
    4. MpesaProvider::charge() does:
         a. GET /oauth/v1/generate to fetch a token.
         b. INSERT a row into commerce_mpesa_requests
            with the order_id, a generated
            CheckoutRequestID (from the API response),
            the customer's phone, the amount, and a
            pending status.
         c. POST /mpesa/stkpush/v1/processrequest.
         d. Store the CheckoutRequestID and the
            MerchantRequestID on the row.
         e. Return ['ok' => true,
                    'provider_reference' => $checkoutRequestId]
            WITHOUT a redirect_url.
    5. The controller sees no redirect_url and,
       instead of redirecting, renders a "waiting
       for your PIN" page.
    6. The customer enters their PIN on the phone.
    7. Safaricom POSTs to the callback URL.
    8. WebhookController::mpesa() verifies the
       CheckoutRequestID against the pending set.
    9. Provider::handleWebhook() writes payment_status
       = 'paid', paid_at, payment_reference (the
       M-Pesa receipt number) on the order.
    10. The waiting page polls
        POST /checkout/mpesa/status (a small AJAX
        endpoint) which reads the order's
        payment_status. When it flips to 'paid',
        the page redirects to the confirmation.

A customer whose phone does not ring (wrong number,
Safaricom delay) sees a "Did not receive the prompt?"
link. That link cancels the pending request and
returns the customer to the payment step.

## The refund flow

M-Pesa refunds are conditional. Not every Daraja
plan exposes the refund endpoint. The merchant's
settings include a `payments.mpesa.refund_enabled`
flag.

  - If `refund_enabled = false` (default), the
    provider's `refund()` returns `ok = true` with
    `refund_id = 'offline'`. The refund is recorded
    as succeeded by `PaymentRefundService` without
    an API call. The merchant refunds through the
    M-Pesa dashboard manually.

  - If `refund_enabled = true`, the provider calls
    the Daraja refund endpoint. On success, the
    row is written with the M-Pesa refund id. On
    failure, the row stays pending and the retry
    cron picks it up.

The plan defaults `refund_enabled` to false. The
merchant opts in after confirming their plan
exposes the endpoint.

## Settings

Six credential entries, following the Stripe and
PayPal naming pattern:

    payments.mpesa.mode            select: sandbox | live
    payments.mpesa.consumer_key    string
    payments.mpesa.consumer_secret string
    payments.mpesa.shortcode       string  (Paybill or Till number)
    payments.mpesa.passkey         string  (Lipa na M-Pesa online passkey)
    payments.mpesa.callback_url    string  (https://.../webhooks/mpesa)

Two behaviour toggles:

    payments.mpesa.transaction_type   select: CustomerPayBillOnline | CustomerBuyGoodsOnline
    payments.mpesa.refund_enabled     bool, default false

All entries live in `StoreSettingDefinitions::DEFINITIONS`
under the `GROUP_PAYMENTS` group. The Settings >
Payments tab renders them automatically.

The `callback_url` is per-store because each
deployment has its own domain. The merchant copies
the URL into the Daraja dashboard when registering
the callback.

## The new table

Migration 0343:

    commerce_mpesa_requests
      id                   BIGINT UNSIGNED PK AUTO_INCREMENT
      store_id             BIGINT UNSIGNED NOT NULL
      order_id             BIGINT UNSIGNED NOT NULL
      checkout_request_id  VARCHAR(80) NOT NULL
      merchant_request_id  VARCHAR(80) NULL
      phone_number         VARCHAR(20) NOT NULL
      amount               DECIMAL(18,4) NOT NULL
      status               ENUM('pending','completed','failed')
                           NOT NULL DEFAULT 'pending'
      result_code          INT NULL
      result_description   VARCHAR(255) NULL
      mpesa_receipt        VARCHAR(60) NULL
      created_at           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
      updated_at           DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                          ON UPDATE CURRENT_TIMESTAMP

      UNIQUE KEY uniq_com_mpesa_checkout (checkout_request_id)
      KEY idx_com_mpesa_order (order_id)
      KEY idx_com_mpesa_status_created (status, created_at)
      FK store_id -> commerce_stores(id) CASCADE
      FK order_id -> commerce_orders(id) CASCADE

A cleanup cron (`bin/cleanup-mpesa-requests.php`)
deletes rows with status 'pending' and created_at
older than 24 hours. The cleanup is not urgent;
the table grows slowly and a few hundred stale
rows are harmless. But the cron is part of the
sub-stage so the table does not grow unbounded.

## The webhook route

    POST /webhooks/mpesa

Registered in `routes/commerce.php` beside the
existing Stripe and PayPal webhook routes. The
same middleware list: `['store']`. No CSRF.

`WebhookController` gains a `mpesa()` method,
mirroring `stripe()` and `paypal()`. The three
methods share the same shape: read the raw body,
resolve the provider, verify the signature (or
the CheckoutRequestID), record the event in
`commerce_webhook_events`, call the provider's
`handleWebhook()`, return 200.

---

## The status endpoint

    POST /checkout/mpesa/status

Middleware `['store', 'csrf']`. Accepts the
`order_number`. Returns JSON:

    {"status": "unpaid" | "paid" | "failed"}

The waiting page polls this every 3 seconds. When
the status flips, the page redirects.

Rate limit: `ratelimit:mpesa_status,30,60`. A
customer polling every 3 seconds for a minute
uses 20 calls. Three retries in a minute is a
reasonable ceiling.

## Sessions

Three sessions.

### Session 1 - plan + schema + settings

  - This plan document.
  - Migration 0343 (commerce_mpesa_requests).
  - Settings entries (six credentials + two toggles).
  - MpesaRequestRepository (read/write the pending
    set; the provider and the webhook controller
    use it).

No provider class yet. The table and the settings
exist. The webhook route and its controller method
ship in Session 3, together with the provider
class. A stub route that returns 200 without
acting is worse than no route; the customer's
provider dashboard would show a successful
delivery for a webhook the app did not handle.

### Session 2 - the provider class

  - MpesaProvider implements PaymentProvider.
  - OAuth token caching (one token per request,
    same pattern as PayPalProvider).
  - charge(): STK push, insert the pending row,
    return the checkout request id.
  - capture(): no-op, returns ok. M-Pesa has no
    capture step.
  - refund(): conditional on refund_enabled.
  - verifyWebhook(): CheckoutRequestID lookup.
  - handleWebhook(): update the order on ResultCode 0,
    log the failure on any other code.

### Session 3 - the storefront flow + the webhook

  - The waiting page view.
  - The AJAX status polling.
  - The "Did you not receive the prompt?" cancel.
  - WebhookController::mpesa().
  - The cleanup cron.
  - Browser test against the Daraja sandbox.

## Test approach

The Daraja sandbox uses a fixed test Paybill. The
customer's phone number must be one of the
sandbox's whitelisted test numbers. Sandbox
callbacks go to a URL the merchant registers in
the Daraja dashboard.

The provider class can be tested against the
sandbox with a real STK push and a real callback.
The `bin/smoke-cases/` harness can exercise the
charge path against the sandbox when the network
is available, or use a fixture CheckoutRequestID
and a mock callback for offline test runs.

Two new smoke cases:

  1. `mpesa-stk-push` - a real charge against the
     sandbox, asserting the pending row and the
     CheckoutRequestID.
  2. `mpesa-callback` - a synthetic callback
     against a seeded pending row, asserting the
     order goes paid and the receipt lands.

The second does not need the network. It is the
regression guard for the CheckoutRequestID
verification.

## What is not in this sub-stage

  - M-Pesa B2C (business-to-customer payouts).
    That is a separate flow with its own security
    model. Deferred.
  - M-Pesa on the API is the customer-pays path
    (C2B). That is what this sub-stage ships.
  - Multi-currency. M-Pesa is KES-only on the
    Daraja API. The store's currency must be KES
    for M-Pesa to be offered. The `isConfigured()`
    check reads the store's default currency.
  - Partial refunds. M-Pesa's refund API refunds
    the full amount. A partial refund falls back
    to the offline path.
  - Subscription charges. Recurring M-Pesa
    billing is not part of the Daraja API.

## Open questions

  1. **Currency gating.** M-Pesa is KES-only.
     Should `isConfigured()` return false when the
     store's currency is not KES? Yes. The
     provider cannot function otherwise. The
     merchant sees "M-Pesa is not available for
     your store's currency" in the Settings
     panel.

  2. **Phone number collection.** M-Pesa needs
     the customer's phone. The checkout already
     collects a phone on the shipping step. Does
     the M-Pesa payment step reuse it, or prompt
     again? Recommendation: reuse when present,
     prompt only when missing. Avoid a second
     phone entry.

  3. **Retry after failure.** A failed STK push
     (customer cancelled, wrong PIN) leaves the
     order unpaid. The customer can retry from
     the payment step. Each retry inserts a new
     pending row. The old row is marked failed
     by the callback. The pending set grows but
     stays small because the cleanup cron runs
     every hour.

  4. **Callback URL registration.** The Daraja
     dashboard requires the URL at account
     setup. Can the merchant change it later?
     Yes - the Daraja dashboard allows updating
     the callback URL. The store's settings
     entry is a reference; the merchant copies
     it into Daraja.

These are resolved in the sections above.
Reviewed at Session 1 open.
