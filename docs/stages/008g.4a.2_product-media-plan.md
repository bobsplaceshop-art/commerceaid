# Stage 008G.4a.2 - Product Media

**Status:** In progress
**Opened:** 2026-09-30
**Depends on:** 008G.4a (upload pipeline),
008G.4a.1 (media library page)

---

## Goal

Wire real product images and category images through the
upload pipeline. Replace every picsum.photos placeholder on
the storefront with a real uploaded file. Rebuild the
product detail variant selector as a swatch-based picker
that shows a preview image per variant axis value.

Every product page, every product card, and every category
surface becomes real photography.

## Decisions Locked

### Decision 1 - Full scope, not phased

Variant-specific images ship in this stage. The schema
supports them today (`variant_id` nullable on
`commerce_product_images`). Splitting the work would mean
touching the same files three times.

Scope includes:
  - Product gallery images (multiple per product)
  - Per-variant image assignment (Color: Red -> image)
  - Category images (one per category)
  - Storefront consumption everywhere
  - Swatch-based variant selector with preview images

### Decision 2 - ProductImage model + ProductImageRepository

A dedicated `ProductImage` model and
`ProductImageRepository` (separate from `ProductRepository`).
Same pattern as `InventoryRepository`: one concept, one
repository.

`ProductImageRepository` methods:

  listForProduct(int $productId): array<ProductImage>
    Ordered by sort_order ASC, id ASC.

  listForVariant(int $variantId): array<ProductImage>
    Ordered by sort_order ASC.

  primaryFor(int $productId): ?ProductImage
    Returns the row with is_primary = 1, or the lowest
    sort_order if none is primary.

  findById(int $id): ?ProductImage

  add(int $productId, int $fileId, ?int $variantId, ?string $altText): int
    Inserts a new row. Computes the next sort_order.

  update(int $id, array $fields): void
    alt_text, sort_order, is_primary, variant_id.

  remove(int $id): void
    Deletes the row. If the removed row was primary, the
    next-lowest sort_order row becomes primary.

  setPrimary(int $productId, int $imageId): void
    Clears is_primary on every other row for the product,
    sets it on the target.

  reorder(int $productId, array<int> $imageIds): void
    Updates sort_order to match the array's order.

  syncForProduct(int $productId, array $imageIds): void
    Given a list of image IDs the admin kept, deletes rows
    that are no longer present. Used by the save flow if
    we go with a "delete on save" pattern; otherwise not
    needed.

### Decision 3 - The Images tab is the sixth product tab

The product editor's tab list is an array in
`resources/views/admin/products/edit.php` (lines 88-95).
One new entry:

    'images' => ['label' => 'Images', 'icon' => 'bi-images'],

Placed after Basic. The Images tab is the second thing a
merchant opens after they've named the product.

The tab body is a new partial
`resources/views/admin/products/_tab_images.php`.

`ProductController::showEdit()` passes two new variables:

  'productImages' => $imageRepo->listForProduct($product->id),
  'mediaLibrary'  => $media->paginateForStore($storeId, [], 1, 200)['items'],

Both are resolved to `MediaItem` instances for the view.

### Decision 4 - Product images save as part of the main form

The product editor is one form. Every tab submits
together. The Images tab follows that convention.

But images are a junction, not a scalar. The pattern from
categories and tags applies: a hidden input or a
`syncImages()` method on the controller that reads a
structured POST payload.

Chosen form: the Images tab posts an array:

    images[<imageId>][sort_order]   = int
    images[<imageId>][alt_text]     = string
    images[<imageId>][is_primary]   = 0|1
    images[<imageId>][variant_id]   = int|null

The controller iterates, updates each row, and then
processes new uploads and deletions separately:

    new_images[<fileId>]            = 1  (files just uploaded)
    delete_images[]                 = <imageId>

Follows the variation editor pattern from 006F.

### Decision 5 - Upload from the Images tab, not the media page

The stage-close summary for 008G.4a.1 documented the rule:
uploads happen at the point of use. The Images tab is the
point of use for product images. Its upload widget is the
same one the Store Settings Branding tab uses
(`resources/views/admin/settings/_upload-widget.php`,
extracted to a shared partial if not already).

Uploads post to
`POST /commerce/ca-admin/media/upload` with
`context=product-image`. The response carries the new
file's id. The Images tab then adds it to the form as a
new image row.

### Decision 6 - Swatch selector replaces the flat select

The current variant picker is a single `<select>` with
concatenated option labels ("Red / M - 45.00"). This stage
replaces it with:

  - One row of choices per variant axis.
  - The first axis renders as color swatches if the
    attribute is named "Color" (or "Colour"), otherwise
    as size chips.
  - Each swatch shows a mini-thumbnail if a variant image
    is assigned to that attribute value.
  - Clicking a swatch updates the hero image (if an image
    is assigned).
  - The combination of selected axis values resolves to a
    variant. Out-of-stock combinations are greyed out.
  - A hidden `<input type="hidden" name="variant_id">`
    carries the resolved variant id to the cart form.
  - The old `<select>` remains as a `<noscript>` fallback.

The controller passes the axis metadata:

  'variantAxes' => [
      ['slug' => 'color', 'name' => 'Color', 'values' => [...]],
      ['slug' => 'size',  'name' => 'Size',  'values' => [...]],
  ]

Each axis's values are the distinct attribute values that
appear in the product's variants. Sourced from
`ProductVariantRepository` combined with the variant list.

### Decision 7 - Storefront image helper

Two helpers, both static-cached:

  product_image_url(?Product $product, string $variant = 'card', string $format = 'webp'): ?string
    Returns null if the product has no images. Callers use
    a fallback.

  category_image_url(?Category $category, string $variant = 'md', string $format = 'webp'): ?string
    Same shape.

Helpers live in `app/Helpers/functions.php`, same pattern
as `store_logo_url()`.

When the helper returns null, the caller renders a
picsum URL. Keeping picsum as the fallback means the
storefront still works for products and categories that
have no images. The CSP keeps the picsum origins until
every product has a real image.

### Decision 8 - Variant image assignment is per-attribute-value

The schema's `variant_id` column is not what this stage
uses for the swatch preview. The variant entity represents
a full combination (Red / M). A swatch preview needs an
image per *attribute value* (Red, M), not per combination.

The cleanest mechanism: assign the image to the
`attribute_value` that the swatch represents. Since the
schema has `variant_id` and not `attribute_value_id`, the
stage adds a new column:

    ALTER TABLE commerce_product_images
      ADD COLUMN attribute_value_id BIGINT UNSIGNED NULL
      AFTER variant_id,
      ADD CONSTRAINT fk_com_pi_attribute_value
        FOREIGN KEY (attribute_value_id)
        REFERENCES commerce_attribute_values (id)
        ON DELETE SET NULL;

Semantics:

  file_id + product_id + no variant_id + no attribute_value_id
    A general product gallery image.

  file_id + product_id + attribute_value_id = 5
    A preview image for attribute value #5 (Red).

  file_id + product_id + variant_id = 12
    A preview image for a specific combination.

The swatch uses attribute_value_id. The variant-specific
variant_id path is reserved for future combination-level
overrides.

### Decision 9 - Category image via the same widget

`commerce_categories.image_file_id` is written by a new
file field on the category editor, using the same
`_upload-widget.php` partial from Store Settings.

`CategoryController::store()` and `::update()` gain:

    'image_file_id' => $fileId ?: null

The form posts a file. The controller uploads it via
`MediaRepository::storeFromUpload()` with
`context=category-image`, then writes the resulting
file id to `image_file_id`.

### Decision 10 - Admin gallery drag-reorder uses a small JS library

The admin gallery grid needs drag-to-reorder. The
codebase has no drag-drop library and refuses to add
Node.js. Two options:

  A. Native HTML5 drag-and-drop API. Browser support
     universal. Small custom JS.
  B. SortableJS (~40 KB) via CDN.

A is the fit. The reorder is one axis (vertical list).
Native drag events are enough. The JS just updates the
hidden `sort_order` inputs on drop.

No library needed.

## Out of Scope

- Video uploads. `commerce_product_videos` exists but
  the video feature is separate.
- 360-degree spin images.
- Image editing (crop, rotate, background removal).
- Automatic alt text generation (AI).
- Multiple categories per image (an image belongs to
  one product).
- Per-storefront locale variants of the same image.
- CDN delivery for product images. The media serve
  controller is the delivery path.
