# Stage 008K.5 - Order Pricing Engine Plan

**Status:** In progress
**Opened:** 2026-10-10
**Depends on:** 008E (checkout), 008K.1 (admin orders),
008K.4 (RBAC), 007B (order schema)
**Blocks:** 008H resumption (the refund arithmetic
shares this stage's source of truth)

---

## Purpose

The order totals computation is the single most
cross-cutting piece of arithmetic in the platform. Every
sale touches it. Every refund reverses it. Every invoice
renders it. Every tax report aggregates it.

Today, three of the four inputs to that computation are
hardcoded to zero:

    $taxTotal      = 0.0;
    $discountTotal = 0.0;
    $grandTotal    = round($subtotal + $taxTotal
                                + $shippingTotal
                                - $discountTotal, 4);

The formula is correct only because `$taxTotal` is zero.
When tax ships, the formula becomes wrong: tax must be
computed on the discounted base, not on the undiscounted
subtotal. If coupons ship first, the code has to be
rewritten when tax ships. If tax ships first, the code
has to be rewritten when coupons ship.

This stage ships all three inputs - coupons, tax,
shipping - as one coherent feature. The computation is
written once, in the right order, and never rewritten.

See the Coupling Principle in `docs/ROADMAP.md`.

---

## The Computation Sequence

The order is fixed and verified against every major
commerce platform. From eBay's PricingSummaryV2:

    total = (priceSubtotal - priceDiscount)
          + deliveryCost
          + tax
          +/- adjustment
          + fee
          + importCharges
          - additionalSavings

From the modmore Commerce docs:

    total_before_tax = subtotal + shipping + discount
    tax = computed on total_before_tax
    total = total_before_tax + tax

From the WooCommerce community docs:

    "By default, coupons are applied before tax is
    applied so in your example above the tax would be
    applied to the subtotal after the coupon is
    applied."

The sequence:

    1. subtotal      = sum of line subtotals
    2. discountTotal = coupon applied to subtotal
    3. taxableBase   = subtotal - discountTotal
    4. taxTotal      = tax computed on taxableBase
    5. shippingTotal = shipping method rate, computed
    6. grandTotal    = taxableBase + taxTotal
                                 + shippingTotal

Locked. Any future stage that adds a total (a fee, a
surcharge, an additional discount) inserts its term
into the sequence at the appropriate position. The
sequence itself does not change.

### What "taxableBase" means

The taxable base is the amount the tax rate applies to.
It is `subtotal - discountTotal`. Shipping is not in
the taxable base by default - most jurisdictions tax
the shipping charge separately, and some do not tax it
at all. Whether shipping is taxable is a per-rate flag
in this stage's design.

For a German store selling consumer goods at 19% with
free shipping above a threshold, the taxable base is
just the discounted subtotal. For a store where
shipping is taxable, the taxable base grows by
`shippingTotal`. The tax config declares which is
which.

to it. This stage populates it with one row per tax
class applied to the order. German VAT invoicing
(§ 14 UStG) requires the invoice to show the VAT amount

and others at 7%, the invoice must show both subtotals
and both tax amounts separately.

renders correctly.

Validation rules, in order:

    1. Code exists and status = 'active'
    2. valid_from is NULL or <= NOW()
    3. valid_to is NULL or >= NOW()
    4. usage_limit is NULL or redemptionCount < usage_limit
    5. per_customer_limit is NULL or customerRedemptionCount
       < per_customer_limit
    6. min_order_subtotal is NULL or subtotal >= min_order_subtotal

The first failure short-circuits and returns a specific
message for that rule. The customer sees "Coupon expired",
"Coupon already used", "Minimum order not met", and so on
- not a generic rejection.

### TaxService

    namespace CorporateAid\Commerce\Services;

    final class TaxService
    {
        public function __construct(
            private TaxClassRepository $classes,
            private TaxRateRepository $rates,
            private StoreContext $storeContext,
        ) {}

        /**
         * Resolve the tax rate that applies to one line.
         * If the product has no tax_class_id, uses the
         * store's default class. If no rate matches the
         * country (and state), uses the country rate with
         * state_code = NULL. If no rate matches at all,
         * returns a zero rate.
         *
         * @return array{class_id:int, rate_id:?int,
         *               label:string, rate_percent:float,
         *               is_inclusive:bool,
         *               is_shipping_taxable:bool}
         */
        public function resolveRateForLine(
            ?int $productTaxClassId,
            string $countryCode,
            ?string $stateCode
        ): array;

        /**
         * Compute tax for the whole order. Returns per-class
         * breakdown and the total.
         *
         * @param array<int,CartLineItem> $lines
         * @return array{
         *   total:float,
         *   classes:array<int,array{
         *     tax_class_id:?int, tax_rate_id:?int,
         *     label:string, rate_percent:float,
         *     taxable_base:float, amount:float
         *   }>
         * }
         */
        public function calculateTax(
            array $lines,
            float $discountedSubtotal,
            float $shippingTotal,
            string $countryCode,
            ?string $stateCode,
            float $discountTotal
        ): array;

        /**
         * Persist the per-class breakdown to
         * commerce_order_taxes. Called inside the checkout
         * transaction.
         */
        public function persistOrderTaxes(
            int $orderId,
            array $classes
        ): void;
    }

Tax computation:

    For each line:
      rate = resolveRateForLine(product.tax_class_id,
                                 country, state)
      if rate.is_inclusive:
        line_net   = line_subtotal / (1 + rate/100)
        line_tax   = line_subtotal - line_net
      else:
        line_net   = line_subtotal
        line_tax   = line_subtotal * rate/100

    The discount reduces the taxable amount in
    proportion to the discounted subtotal:

      proportion = discountedSubtotal / subtotal

    Each line's taxable base = line_net * proportion.

    If rate.is_shipping_taxable and shippingTotal > 0:
      shipping_net = shippingTotal / (1 + rate/100)
      shipping_tax = shippingTotal - shipping_net
      add shipping_net to the class's taxable base and
      shipping_tax to the class's tax amount.

    Sum tax_amount per class into commerce_order_taxes.
    Sum tax amounts across classes = taxTotal.

Rate computation per type:

    flat            config.rate
    free_over       subtotal >= config.threshold
                      ? 0
                      : config.rate
    weight_based    sum(line.weight * line.qty) * config.per_kg
                    max(computed, config.min_charge)
    price_based     subtotal / config.unit_size
                      * config.per_unit
                    max(computed, config.min_charge)
    local_pickup    0.0

Zone resolution: the available methods for a destination
are those with a zone row whose country_code matches and
whose (region IS NULL OR region = destination.region).

If no zone matches, the method is not offered.

### OrderPricingService

The orchestrator. Its job is to compute the six-step
sequence in one place so there is exactly one
implementation of the pricing arithmetic.

    namespace CorporateAid\Commerce\Services;

    final class OrderPricingService
    {
        public function __construct(
            private CouponService $coupons,
            private TaxService $taxes,
            private ShippingService $shipping,
        ) {}

        /**
         * Compute the full pricing breakdown. This is the
         * single source of truth for the six-step sequence.
         *
         * @param array<int,CartLineItem> $lines
         * @param array{
         *   coupon_code:?string,
         *   shipping_method_code:?string,
         *   country_code:string,
         *   state_code:?string,
         *   customer_id:?int,
         *   guest_email:?string
         * } $context
         *
         * @return array{
         *   ok:bool,
         *   reason?:string,
         *   subtotal:float,
         *   discount_total:float,
         *   taxable_base:float,
         *   tax_total:float,
         *   shipping_total:float,
         *   grand_total:float,
         *   coupon:?array,
         *   shipping_method:?array,
         *   tax_classes:array
         * }
         */
        public function compute(array $lines, array $context): array;

        /**
         * The preview used by the cart and checkout views.
         * Never throws. If the coupon or method is invalid,
         * returns the failure in the response and the caller
         * renders a message.
         */
        public function preview(array $lines, array $context): array;

        /**
         * The strict version used inside the checkout
         * transaction. Throws CheckoutException on any
         * failure.
         */
        public function computeOrFail(array $lines, array $context): array;
    }

The compute() method runs the sequence:

    1. subtotal = sum(line.effectiveSubtotal())
    2. if coupon_code:
         validation = coupons.validate(...)
         if !validation.ok: return failure
         discount_total = validation.discount
       else:
         discount_total = 0
    3. taxable_base = subtotal - discount_total
    4. tax_result = taxes.calculateTax(
         lines, taxable_base, shipping_total,
         country, state, discount_total)
       tax_total = tax_result.total
    5. if shipping_method_code:
         method = shipping.resolveForCheckout(...)
         shipping_total = shipping.calculateRate(method, lines, subtotal)
       else:
         shipping_total = 0
    6. grand_total = taxable_base + tax_total + shipping_total

Note the slight reordering in step 4: shipping is
resolved in step 5 for the return value, but its amount
is needed in step 4 for the taxable base when shipping
is taxed. In the implementation, shipping is computed
before tax. The numbers are identical; the sequence
above describes the return value's logical order.

## Integration Points

### CheckoutService::placeOrder()

The totals block (lines 228-236 today) becomes:

    $pricing = $this->pricing->computeOrFail(
        $lines,
        [
            'coupon_code'          => $this->cart->couponCode(),
            'shipping_method_code' => $input['shipping_method_code'] ?? null,
            'country_code'         => $shippingAddress['country_code'] ?? '',
            'state_code'           => $shippingAddress['state_code'] ?? null,
            'customer_id'          => $customer?->id,
            'guest_email'          => $customer === null
                                        ? ($input['guest_email'] ?? null)
                                        : null,
        ]
    );

    $subtotal      = $pricing['subtotal'];
    $discountTotal = $pricing['discount_total'];
    $taxTotal      = $pricing['tax_total'];
    $shippingTotal = $pricing['shipping_total'];
    $grandTotal    = $pricing['grand_total'];

The order header INSERT gains two new keys:

    'coupon_code' => $pricing['coupon'] !== null
                        ? $pricing['coupon']['code']
                        : null,

    'shipping_method_key'   => $pricing['shipping_method']['code'] ?? null,
    'shipping_method_label' => $pricing['shipping_method']['label'] ?? null,

After the order items are inserted and before the
transaction commits:

    if ($pricing['coupon'] !== null) {
        $this->coupons->recordRedemption(
            (int) $pricing['coupon']['id'],
            $orderId,
            $customer?->id,
            $customer === null ? $input['guest_email'] : null,
            $pricing['discount_total']
        );
    }

    $this->taxes->persistOrderTaxes($orderId, $pricing['tax_classes']);

Both writes are inside the existing transaction. If
either fails, the order rolls back. That is the desired
behavior: a redemptive coupon cannot be consumed
without an order, and tax lines cannot be written for
an order that does not exist.

The cart's coupon code is cleared after commit, along
with the cart itself.

Constructor: CheckoutService gains a new dependency,
`OrderPricingService $pricing`. The provider binding
gains one line.

### CartService

Three new methods for coupon state. Coupon state lives
in the session, matching the guest cart pattern. No
schema change to `commerce_carts`.

    public function couponCode(): ?string
        Reads $_SESSION['cart_coupon_code'].
        Returns null if unset or empty.

    public function setCouponCode(string $code): void
        Writes the code. Code is uppercased and trimmed
        before storage.

    public function clearCouponCode(): void
        Removes the key.

The coupon code is stored as a string, not the resolved
coupon. It is re-resolved on every cart render so that
an expiry between pages is caught immediately.

### CartController

Two new actions:

    POST /cart/apply-coupon
        Reads `code` from the POST body.
        Calls CouponService::validate against the current
        cart lines.
        On success: CartService::setCouponCode($code).
        On failure: flash the failure reason.
        Redirects back to /cart.

    POST /cart/remove-coupon
        CartService::clearCouponCode().
        Flash success.
        Redirects back to /cart.

Both actions carry `['store', 'csrf']` middleware.

### Cart and checkout views

The cart page (`resources/views/storefront/cart/index.php`)
gains:

  - A coupon form below the subtotal:
      [ Coupon code ] [Apply]
    With a remove link when a coupon is active.
  - A discount row when a coupon is applied.
  - A VAT line ("inkl. 19% MwSt." for German stores).

The checkout shipping step
(`resources/views/storefront/checkout/shipping.php`)
gains:

  - A shipping method selector: radio buttons with
    label + rate, populated by
    ShippingService::availableMethods.

The checkout payment step
(`resources/views/storefront/checkout/payment.php`)
gains:

  - The full totals breakdown:
      Subtotal
      Discount (if applicable)
      Shipping
      VAT (includes the rate label)
      Grand total

The confirmation page
(`resources/views/storefront/checkout/confirmation.php`)
gains:

  - The same totals breakdown, now reading from the
    order record.
  - The "inkl. MwSt., zzgl. Versandkosten" line for
    German stores (PAngV § 6).

### Controllers that call CheckoutService

`CheckoutController::place()` already passes the input
array to `CheckoutService`. The shipping method code
flows through as `$input['shipping_method_code']`. The
controller needs one change: after a failed place (for
example, a coupon expired between cart and checkout),
it renders the failure with the coupon cleared or
flagged.

## Compliance (Germany)

Three specific requirements this stage addresses.

### § 14 UStG - VAT breakdown on the invoice

The invoice must show the VAT amount broken down by
rate. A store selling some items at 19% and others at
7% must show both. This is why `commerce_order_taxes`
is populated per class.

### PAngV § 6 - Total price disclosure

Every price shown to a consumer must include VAT and
state that it does, and shipping costs must be
separately disclosed. The formula:

    "inkl. 19% MwSt., zzgl. Versandkosten"

This is rendered in the cart footer, the checkout
payment step, the confirmation page, and the customer
order detail.

### PAngV § 4 - Grundpreis (base price)

For products sold by weight, volume, length, or area,
the price per unit must be shown next to the total
price. This requires a Unit of Measure subsystem that
is deferred. Logged in `docs/ROADMAP.md` as a
backlog item. Not in this stage.

## Open Questions

1. Should the applied coupon survive a guest-to-logged-in
   merge? If a guest applies SAVE10 and then logs in,
   should the coupon stay? Recommendation: yes, the
   session key is not tied to the customer record, so
   it survives naturally. The per-customer limit is
   checked at redemption time, not at application time.

2. Should the tax rate be locked at the moment the
   coupon is applied, or at order placement?
   Recommendation: at order placement. Cart is a
   preview; the order is the record.

3. Should a coupon's category scope be enforced
   strictly at order placement? If a customer removes
   all eligible items but keeps the coupon, the
   discount becomes zero. Recommendation: recompute
   at order placement; if the discount drops to zero,
   clear the coupon silently.

4. What happens if a shipping method is disabled
   between the customer choosing it and placing the
   order? Recommendation: `resolveForCheckout` fails
   with a specific message. The customer is sent back
   to the shipping step with a clear explanation.

These are resolved in this document's decisions above
and should be reviewed at Session 1's open.
