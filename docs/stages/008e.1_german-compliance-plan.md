## Purpose

The compliance work that sits alongside checkout. Germany is
the first deployment destination. Several regulatory elements
must be in place before the platform can legally sell.

008E shipped the gates that block checkout (AGB and
Widerrufsbelehrung checkboxes, Impressum link, statutory
Widerrufsbelehrung content). 008E.1 ships the merchant-facing
management UI, the cookie consent banner, and the settings
infrastructure that makes compliance configurable per store.

This stage also builds the general Store Settings page that
the admin sidebar has linked to since Stage 005 but that
never existed. That page is the home for every future
per-store toggle.

## Scope

**In scope:**

- Store Settings page at /commerce/ca-admin/settings with
  tabs. First tab set: General, Compliance, Advanced.
- Dynamic settings form driven by code-declared definitions.
- "Advanced" panel for adding custom key-value settings.
- Legal Pages admin CRUD at /commerce/ca-admin/legal-pages.
- Cookie consent banner (TTDSG-compliant) on the storefront.
- VerpackG registration notice + LUCID number field.
- Country-aware compliance defaults via
  commerce_stores.country_code.

**Out of scope (later):**

- Full feature flag system (core_feature_flags layer).
  The settings table is the storage layer; the flag system
  becomes an API on top later.
- Analytics integration (Stage 010).
- Multi-language cookie banner text (i18n, future stage).
- Grundpreis (Unit of Measure subsystem, future stage).

## Architecture Decision: Option B

Per-store settings live in a new `commerce_store_settings`
key-value table, not as columns on `commerce_stores`.

Why key-value over columns:

  - New toggle = one line in a definitions array. No migration.
  - The table scales to any number of settings without growing
    wide.
  - The shape matches the future Feature Flag System's storage
    layer. Migrating from settings-as-rows to
    flags-with-scopes is a code change, not a schema change.
  - Columns on commerce_stores would require a migration per
    new toggle. At 5 toggles that is overhead. At 20 toggles
    it is a table redesign.

Columns on commerce_stores would be simpler today. The
key-value table is simpler in two years. We chose the
longer-term shape.

Why a dedicated settings table over core_system_settings:

  - core_system_settings is a Platform table shared across
    modules. Commerce-specific keys would pollute it.
  - Commerce controls its own settings table's schema.
  - Platform's naming conventions (key format, scope rules)
    do not necessarily match Commerce's.

## Removing the Human Element

The stage name mentions compliance, but the more interesting
deliverable is the settings infrastructure itself.

The problem with hand-built settings pages:

  Every new toggle needs:
    1. A migration to add the column.
    2. A form field in the view.
    3. Controller validation.
    4. A database write on save.
    5. A read somewhere in the code.

That is five touchpoints per toggle. For a platform that
will accumulate dozens of toggles over its life, that is
untenable.

The design instead:

  1. The developer writes the code that reads a setting:
       $enabled = $settings->bool('my.new.flag', true);

  2. The developer adds one line to the definitions array
     (StoreSettingDefinitions::DEFINITIONS). The entry
     declares the label, type, default, and group.

  3. The admin page reads the definitions array and renders
     the form dynamically. Nothing else changes.

  Total touchpoints: two. And both are code-side. The
  merchant never runs a migration.

This is the "no scripts to run" property. It is what makes
adding toggles a five-minute change rather than a
half-hour one.

The Advanced panel goes further: a merchant can add an
arbitrary key-value setting that the platform does not yet
know about. This is useful for:

  - Merchant-specific flags their workflow depends on.
  - Storing config that a future integration will read.
  - Staging a setting ahead of the code that consumes it.

The Advanced settings are pure data. No code reads them
until the developer writes the code that does. That is
the correct contract.

## The Three Parts

### Part A - Store Settings Page

Route: /commerce/ca-admin/settings

Previously a 404. The sidebar Settings group has linked
here since Stage 005.

Tabs:

  General
    Store name, tagline, contact email, legal name. Fields
    that do not fit in the setup wizard's initial scope.

  Compliance
    All settings with group = 'compliance'. Rendered
    dynamically from StoreSettingDefinitions. First
    entries:
      compliance.cookie_banner.enabled (boolean)
      compliance.verpackg.lucid        (string)
      compliance.legal_pages.required  (boolean, default true)

  Advanced
    Collapsed by default. Lists every setting in
    commerce_store_settings that is NOT in the definitions
    array. Allows adding a new key-value pair by hand.
    Allows deleting a custom key.

The page loads every setting for the current store in one
query. Cached per request.

### Part B - Legal Pages Admin

Route: /commerce/ca-admin/legal-pages

CRUD for the four legal pages seeded in 008E. Not a full
arbitrary-page system - the four slugs are fixed
(impressum, agb, widerruf, datenschutz) because the checkout
gate depends on them. Additional slugs can be added later
if a merchant wants a cookie policy or shipping terms page.

  GET  /                      list (four rows + any custom)
  GET  /{slug}/edit           edit title + body
  POST /{slug}                update

Each row shows: slug, title, published status, last updated,
last updated by.

Edit form: title field, body textarea (HTML), publish toggle,
save. No rich text editor yet - that is a future stage.
Preview button opens /legal/{slug} in a new tab.

The `updated_by` column (already in the schema from 008E)
records the admin who last saved.

### Part C - Cookie Consent Banner

TTDSG-compliant. Renders on every storefront page when:
  - compliance.cookie_banner.enabled is true (default), AND
  - the visitor has no valid consent cookie

Behavior:

  - Banner appears at the bottom of the viewport
  - Two buttons of equal visual weight:
      [Accept all]     [Reject non-essential]
  - No pre-checked anything
  - Decision stored in a cookie: ca_consent
  - Cookie value: JSON { version: 1, essential: true,
    analytics: bool, marketing: bool, timestamp: unix }

Framework provided:

  - window.CAConsent.has('analytics')  -> boolean
  - window.CAConsent.get()             -> full object
  - window.CAConsent.reset()           -> clears the cookie
                                          (for testing)

Stage 010 (payments + shipping deep) will load analytics
scripts conditionally on CAConsent.has('analytics'). 008E.1
ships the framework; the analytics code itself is deferred.

The banner is a partial:
  resources/views/storefront/partials/_cookie-banner.php
Rendered at the bottom of <body> in the storefront layout.

CSS:
  public/assets/css/storefront-cookie-banner.css

JS:
  public/assets/js/cookie-consent.js

The banner is not a modal. It does not block the page. It
sits at the bottom and can be dismissed by either action.
A future preference center can let visitors change their
mind later.

### Part D - Country-Configurable Compliance

The store has commerce_stores.country_code (from Stage 005).
A small config map decides which compliance elements apply:

  'DE' => [
      'cookie_banner'    => true,
      'legal_pages'      => ['impressum', 'agb', 'widerruf', 'datenschutz'],
      'widerruf_required'=> true,
      'verpackg_notice'  => true,
  ],
  'FR' => [
      'cookie_banner'    => true,
      'legal_pages'      => ['mentions-legales', 'cgv', 'retractation', 'confidentialite'],
      'widerruf_required'=> true,  // French 14-day retraction
      'verpackg_notice'  => false,
  ],
  // etc.

For 008E.1, only DE is wired. The map is a placeholder that
other countries fill in over time. The checkout gate already
checks for the German slugs; when the map is in place, the
gate reads from the map instead of hardcoded German slugs.

Country resolution: commerce_stores.country_code, set during
setup. If the country is not in the map, use a safe default
(all compliance elements off, warning in admin).

## Schema

Migration 0304_create_store_settings.sql:

  CREATE TABLE commerce_store_settings (
    id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    store_id   BIGINT UNSIGNED NOT NULL,
    key_name   VARCHAR(120) NOT NULL,
    value      TEXT NULL,
    updated_by INT UNSIGNED NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uniq_com_ss_store_key (store_id, key_name),
    KEY idx_com_ss_store (store_id),
    CONSTRAINT fk_com_ss_store FOREIGN KEY (store_id)
      REFERENCES commerce_stores (id) ON DELETE CASCADE,
    CONSTRAINT fk_com_ss_user FOREIGN KEY (updated_by)
      REFERENCES core_users (id) ON DELETE SET NULL
  ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

The column is named key_name, not key, because key is a
reserved word in MySQL.

No other schema changes. Legal pages already exist from
008E (migration 0302). The commerce_stores.country_code
column exists from Stage 005.

## StoreSettingDefinitions

A single class declaring every known setting. Shape:

  public const DEFINITIONS = [
      'compliance.cookie_banner.enabled' => [
          'label'   => 'Cookie consent banner',
          'type'    => 'boolean',
          'default' => true,
          'group'   => 'compliance',
          'hint'    => 'Show a TTDSG-compliant consent banner. '
                       . 'Required in Germany.',
      ],
      'compliance.verpackg.lucid' => [
          'label'   => 'LUCID registration number',
          'type'    => 'string',
          'default' => '',
          'group'   => 'compliance',
          'hint'    => 'Your VerpackG registration number from the '
                       . 'Zentrale Stelle Verpackungsregister.',
      ],
      'compliance.legal_pages.required' => [
          'label'   => 'Require legal pages before checkout',
          'type'    => 'boolean',
          'default' => true,
          'group'   => 'compliance',
          'hint'    => 'Block checkout until the four German legal '
                       . 'pages are published.',
      ],
      'general.contact_email' => [
          'label'   => 'Contact email',
          'type'    => 'string',
          'default' => '',
          'group'   => 'general',
          'hint'    => 'Displayed on the storefront contact page.',
      ],
      // ... more as the platform grows
  ];

Supported types: boolean, string, text, number, select.

Every read in code goes through a typed accessor on
StoreSettingsRepository:

  $settings->bool('compliance.cookie_banner.enabled', true)
  $settings->string('compliance.verpackg.lucid', '')
  $settings->int('general.page_size', 25)

The default argument is the fallback when the row is missing.
This is what makes "no migration needed" work: the code
declares what it expects, and the DB row appears only when
the merchant changes the value.

  from adding new toggles. Plus three compliance deliverables
  for the German deployment.

  Other countries declare their requirements in the map.

### Architecture decision

  Settings live in a new commerce_store_settings key-value
  table, not as columns on commerce_stores. Adding a toggle
  is one line in a definitions array. The shape matches the
  future Feature Flag System's storage layer, so migrating
  later is a code change, not a schema migration.

  Defaults live in code, values live in the DB. The first time
  a merchant changes a value, a row appears. Before that, the
  declared default applies. No migration. Ever.
