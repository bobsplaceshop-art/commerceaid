# Stage 008G.2 - Recently Viewed

**Status:** In progress
**Opened:** 2026-09-30
**Depends on:** 008F.1 (account shell), 008G.1 (wishlist patterns)

---

## Goal

Track the products a customer views. Show them on
/account/recent. A returning customer can pick up where they
left off.

The feature is write-heavy in a way the wishlist was not. Every
product detail page load triggers a write. The design must be
cheap per write, bounded, and idempotent within a short window.

---

## Deliberate Differences From Wishlist

The wishlist is the direct precedent. Both share:

- Session-vs-DB split (guest state in session, customer state
  in DB)
- Merge on login
- Account shell integration
- A helper for cross-cutting view data
- One page in /account/*

The recently-viewed feature differs in three ways:

| Dimension | Wishlist | Recently Viewed |
|---|---|---|
| When it writes | On customer click | On every product page load |
| Dedup window | Never (idempotent) | 24h (re-visiting within 24h updates the timestamp, not the position) |
| Bound | Unbounded | 50 items (write-time trim) |
| Clearable | Per-item | All-at-once (with a "Clear history" button) |

None of these differences is large. But the write-on-load
pattern is a new integration surface, and the 24h dedup means
the schema needs a `viewed_at` timestamp that updates on
re-view, not just `created_at`.

---

## Decisions Locked

### Decision 1 - Bound on write, not on read

After every successful upsert, trim the customer's rows to the
50 most recent. Two queries per product page load: one upsert,
one delete. Acceptable cost for bounded storage.

The alternative (bound on read, purge in a cron) is more code
and depends on a cron that does not exist. Bound on write is
self-contained and correct on day one.

Guest sessions are naturally bounded by the session's own
lifetime. The session array is capped at 50 too, for symmetry.

### Decision 2 - No bot, prefetch, or crawler filter

Every product detail page load records a view. Including bot
requests, prefetches, and search engine crawlers.

Rationale: the write is cheap. Crawlers have their own session
that never merges into a customer account. A bot that is not
logged in cannot create DB rows - it can only add to its own
session, which dies with the crawler.

Filtering by User-Agent is fragile and high-maintenance. Real
customers have unusual UAs. Bot UAs change weekly. The filter
would need constant updates and would still miss the odd
prefetch.

The cost of recording a view that was not a real visit is one
row that gets trimmed in the next 50 views. The cost of NOT
recording a view that was real is a broken feature.

### Decision 3 - 24h dedup window

Re-viewing the same product within 24 hours updates the
`viewed_at` timestamp but does not create a new row. Re-viewing
after 24 hours also updates the timestamp - but the effect on
ordering is the same: the product moves to the top.

Actually, since the schema has a UNIQUE key on
(store_id, customer_id, product_id), every view is an upsert.
The 24h window is not enforced by the code - it emerges from
the unique key. Every view updates `viewed_at`. The dedup is
implicit.

The "24h" in the plan is a convention, not a constraint. If we
want to enforce it strictly (re-viewing does not update the
timestamp if the last view was within 24h), the code is
different. We do not want that - the customer returning to a
product should bump it to the top of their list. Update
unconditionally.

### Decision 4 - Schema mirrors wishlist, plus viewed_at

commerce_recently_viewed:

    id           BIGINT UNSIGNED PK
    store_id     BIGINT UNSIGNED NOT NULL
    customer_id  BIGINT UNSIGNED NOT NULL
    product_id   BIGINT UNSIGNED NOT NULL
    viewed_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                 ON UPDATE CURRENT_TIMESTAMP

    UNIQUE KEY uniq_com_rv_store_customer_product
        (store_id, customer_id, product_id)
    KEY idx_com_rv_customer
        (store_id, customer_id, viewed_at)

Same shape as commerce_wishlists, plus `viewed_at`.
`viewed_at` is set on first insert and updated on re-view.
There is no separate `created_at` - it would be dead weight.
One timestamp column, one purpose.

The `ON UPDATE CURRENT_TIMESTAMP` handles the re-view bump
automatically. `INSERT ... ON DUPLICATE KEY UPDATE
viewed_at = CURRENT_TIMESTAMP` is not even needed - the
column's own trigger does it.

The idx_com_rv_customer index is declared without `DESC`
even though the primary read is `ORDER BY viewed_at DESC`.
MySQL 8 supports descending indexes, but they only help
when all columns in the index carry the same direction.
For our key (store_id ASC, customer_id ASC, viewed_at
ASC), the read `WHERE store_id = ? AND customer_id = ?
ORDER BY viewed_at DESC` still uses the index efficiently -
MySQL reads it forward and reverses in memory, or reads it
backward. Both are fast at this scale.

### Decision 5 - Session shape for guests

$_SESSION['recently_viewed'] = array of ints, newest first,
capped at 50.

Same shape as $_SESSION['wishlist'] but with the newest item
first. On add: unset the id if present, then unshift to the
front, then trim to 50.

This is a flat array, not a nested items structure. No
timestamps in session - position in the array is the
timestamp.

### Decision 6 - Helper: recently_viewed_product_ids()

Mirrors wishlist_product_ids(). Static-cached, resolves
RecentViewService once per request, returns array of ints,
swallows errors.

Used by:
- The "Clear history" button state (only show when non-empty)
- Future: a "Recently viewed" strip on the product detail page
  (not in scope for 008G.2, but the helper makes it one line
  to add later)

### Decision 7 - Merge guest session history on login

Same pattern as the cart and wishlist. On successful login
or registration, the guest session history is merged into
the customer's DB history, and the session key is cleared.

Same two call sites in AuthController that
mergeGuestCartOnLogin() and mergeGuestWishlistOnLogin()
already use.

Conflict resolution: last-write-wins on `viewed_at`. If the
customer viewed Product A as a guest at 14:00 and as a
logged-in customer at 13:00, the merge keeps the 14:00
timestamp. The repository's upsert
(INSERT ... ON DUPLICATE KEY UPDATE viewed_at =
CURRENT_TIMESTAMP) handles this naturally without special
merge logic - each session ID is upserted, and the DB row's
own ON UPDATE trigger sets the newer timestamp.

After the merge, the session key is cleared regardless of
how many rows were inserted or updated.

## Files To Modify

Every modification carries a cascade note.

### routes/storefront.php

Add one route for the page and one POST for clear:

    GET  /account/recent        index   ['store']
    POST /account/recent/clear  clear   ['store', 'csrf']

No record endpoint. Recording happens inside
ProductController::show(), not via a separate route.

### app/Commerce/CommerceServiceProvider.php

Bind RecentViewRepository and RecentViewService as
singletons. Same shape as the wishlist bindings.

### app/Commerce/Controllers/Storefront/AuthController.php

Two call sites gain mergeGuestRecentViewOnLogin() alongside
the existing mergeGuestCartOnLogin() and
mergeGuestWishlistOnLogin() calls.

### app/Commerce/Controllers/Storefront/ProductController.php

In show(), after the product is confirmed published and
before render, add:

    $this->container
        ->get(RecentViewService::class)
        ->record($product->id);

Defensive: wrap in try/catch so a recording failure does not
break the product page. Recording is a side effect, not a
page requirement.

Cascade: this is the highest-risk change. ProductController
serves every product detail page. The added line runs on
every request. Verify by:
- Walking /products/{slug} for a published product
- Confirming the page renders normally
- Confirming a guest session write happens
- Confirming a customer DB write happens
- Confirming a broken service (simulate by renaming a
  method) does not break the page

### app/Commerce/Support/StorefrontController.php

No change. The helper pattern (Decision 6) means the outer
view scope does not need to carry recently-viewed data. But
inject it anyway for consistency with cartCount and
wishlistProductIds:

    $data['recentlyViewedProductIds'] = $this->resolveRecentlyViewedProductIds();

Hmm - actually, if the helper is available, the injection
is redundant. Skip it. Keep render() unchanged. Add the
helper. The helper is what views call.

### resources/views/storefront/account/_sidebar.php

The "Recently Viewed" group has 'soon' => true and href='#'.
Flip to a real link to /account/recent.

### app/Helpers/functions.php

Add recently_viewed_product_ids(). Mirrors
wishlist_product_ids().

### public/assets/js/wishlist.js OR a new clear-history script

The clear-history button on /account/recent is a plain form
POST. No JS needed. The wishlist JS file is unchanged.

## Test Protocol

Manual, at 375px and 1024px.

    T-1  Guest visits /products/{slug}. A session view is
         recorded.
    T-2  Guest revisits the same product within seconds.
         No duplicate. Order unchanged.
    T-3  Guest visits a second product. Order: newest first.
    T-4  Guest logs in. /account/recent shows both products,
         newest first.
    T-5  Logged-in customer visits a product. A DB row is
         created.
    T-6  Customer revisits a product viewed 1 hour ago. The
         timestamp updates, order moves it to top.
    T-7  Customer views 51 distinct products. Only the 50
         most recent appear on /account/recent.
    T-8  Customer clicks "Clear history". All rows deleted.
    T-9  Direct visit to /account/recent as a guest redirects
         to login.
    T-10 Archived product in history: shows "no longer
         available" state, not a 500.
    T-11 Page load does not slow noticeably. Measure
         /products/{slug} response time before and after.
    T-12 Merge on login: guest views 3 products, logs in
         with 2 already in DB. /account/recent shows 5 (or
         fewer if any overlap).

## Out of Scope

- A "Recently viewed" strip on the product detail page.
  The helper makes it one line to add later, but not in
  008G.2.
- A "Recently viewed" widget on the home page or cart.
- Admin-side visibility into customer view history.
- Analytics or aggregate view counts across customers.
- Bots, prefetch, and crawler filtering (see Decision 2).
- Strict 24h window enforcement (see Decision 3).
