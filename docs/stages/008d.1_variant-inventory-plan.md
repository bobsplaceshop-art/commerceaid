# Stage 008D.1 - Variant-Level Inventory

**Date opened:** 2026-09-28
**Status: Complete (2026-09-28)**
**Depends on:** Stage 008D (cart), Stage 006F (product variations)

---

## Purpose

Fix a foundational data model issue in the inventory layer. As
shipped, inventory has one row per product with `variant_id = 0`.
For variable products, this creates a parent row that is not a
sellable unit and leaves each variant without its own inventory
row. The cart silently skips the stock check when a variant has
no row. This is a correctness bug.

This sub-stage establishes the invariant:

> **Every sellable unit has exactly one inventory row. Nothing
> else does.**

A sellable unit is:
  - A simple product (variant_id = 0)
  - A variant of a variable product (variant_id = variant.id)

A variable product is a marketing container, not a sellable
unit. It gets no inventory row.

---

## The Two Modes

### Simple product

  - One inventory row: (product_id, variant_id = 0)
  - Product edit -> Inventory tab: stock input enabled
  - Inventory page: one row per product
  - Storefront: "only N left" reflects this row
  - Cart: adds with variant_id = 0, checks this row
  - Dashboard "units on hand": counts this row

### Variable product

  - NO parent inventory row (variant_id = 0 must not exist)
  - One inventory row per variant: (product_id, variant_id = V)
  - Product edit -> Inventory tab: stock input disabled with
    a read-only summary line "Total across variants: N units"
    and a link to Manage Variations
  - Variations page: per-variant stock input, writes to that
    variant's row
  - Inventory page: one row per variant, filterable by product
  - Storefront: "In stock" reflects the selected variant's row
  - Cart: adds with variant_id = V, checks that variant's row
  - Dashboard "units on hand": counts variant rows (no parent
    row to double-count)

---

## The Invariant

  Every sellable unit has exactly one inventory row.

  Corollaries:
    - The `variant_id = 0` sentinel means "simple product"
      and nothing else.
    - Variable products have no `variant_id = 0` row.
    - The cart can assume the inventory row exists. If it
      doesn't, that is a bug, and the cart fails loud.

---

## The Bugs This Fixes

### Bug 1 - Silent stock pass-through for variants

`CartService::assertStockAvailable()`:

    $inv = $this->inventory->forUnit($productId, $variantId);
    if ($inv === null) {
        return;  // no row => no check
    }

For every T-Shirt variant:
  - forUnit(3, 5) returns null (variant 5 has no row)
  - assertStockAvailable returns early
  - No stock check happens

The customer can add 10,000 units of a variant that has 0
stock. The parent's 200 units are never consulted.

**Fix:** strict per-variant. If a variant has no inventory row,
throw a RuntimeException (this is a data-integrity issue, not
a customer error). The migration backfills rows so this
condition never occurs post-migration.

### Bug 2 - Parent row for variable products

The T-Shirt has one inventory row with `variant_id = 0,
quantity = 200`. This is a parent row. It's not a sellable
unit. Its 200 units don't belong to any specific variant.

**Fix:** delete parent rows for variable products during
migration. The 200 units are not distributed (test data,
merchant re-enters real stock per variant).

### Bug 3 - Dashboard double-counting

"Units on hand" sums all `commerce_inventory` rows. For a
variable product with a parent row and 12 variant rows, that
is 13 contributions to a single logical product. If variant
rows existed, they'd add to the parent total, overstating
stock.

**Fix:** after backfill, all rows are sellable units. Sum
naturally gives the correct total. No code change needed
once the data model is correct.

## The Migration

File: `database/migrations/0301_variant_inventory_backfill.sql`

Steps:

  1. Create a backup table:
     `commerce_inventory_backup_0301` (full copy of the table).

  2. For every variable product with a `variant_id = 0` row:
     - Delete that row.
     - For each of its variants (from
       `commerce_product_variants` where product_id = X and
       status = 'active'):
         - Insert a new inventory row with
           (product_id, variant_id = V, quantity = 0,
           reserved = 0).

  3. For every variable product with NO `variant_id = 0` row
     but variants that lack their own rows:
     - Insert inventory rows for those variants with
       quantity = 0.

  4. Leave simple products alone. Their `variant_id = 0` rows
     are correct.

  5. Verify: no variable product has a `variant_id = 0` row;
     every active variant has exactly one inventory row.

The 200 units from the T-Shirt's parent row are not
redistributed. For dev data, this is correct - the merchant
re-enters real stock. For a future production migration, the
plan would add a "you have N units to redistribute" warning
before deleting the parent row.

## Application-Layer Changes

### Variant creation must create inventory rows

When a variant is created through:
  - `ProductController::regenerateVariants()`
  - `ProductController::autoGenerate()`
  - `ProductVariantRepository::create()` (the public API)

...an inventory row must be created alongside, with quantity = 0
and reserved = 0. The variant and its inventory row are born
together.

**Cleanest location:** `ProductVariantRepository::create()`.
Every other path goes through it. Add one INSERT after the
existing variant INSERT, inside the same transaction if the
caller is transactional.

### Product creation must not create a parent row for variable products

`ProductController::store()` currently creates a
`variant_id = 0` inventory row when `manage_stock` is on.

Change: skip that INSERT when `product_type = 'variable'`.
The product has no sellable unit yet (no variants exist).
Inventory rows will be created when variants are generated.

### CartService::assertStockAvailable must fail loud on missing row

    $inv = $this->inventory->forUnit($productId, $variantId);
    if ($inv === null) {
        throw new \RuntimeException(
            "Inventory row missing for product {$productId}, " .
            "variant {$variantId}. This is a data-integrity " .
            "issue. Run the 0301 migration if it has not been " .
            "applied."
        );
    }

The exception is RuntimeException, not CartException. It is
not a customer error. It surfaces to the error handler.

Rationale: after the migration, this should never happen. If
it does, we want to know immediately, not silently pass.

## Admin UI Changes

### Product edit -> Inventory tab (`_tab_inventory.php`)

Currently shows the stock input for every product. Change:

  - If `product_type = 'simple'`: input enabled. Existing
    behavior. Writes to the `variant_id = 0` row.
  - If `product_type = 'variable'`:
    - Input disabled (greyed out).
    - Replace the input's value display with a summary line:
      "Total across variants: N units".
    - Add a small link: "Manage per-variant stock" that points
      to the variations page.
    - Add a short note under the input: "Stock is managed per
      variant. Use Manage Variations to set stock for each
      variant individually."

The disabled input stays in the form (with a sentinel value)
so the POST doesn't break. The controller ignores it for
variable products.

### Variations page (`variants.php`)

Already has per-variant stock inputs. Verify:
  - Each input writes to its variant's inventory row (through
    the repository, which already keys on product_id + variant_id).
  - On save, the row is created if it didn't exist.

If the current code assumes the row exists (UPDATE without a
matching INSERT), add an upsert. The migration backfills
existing rows, so the upsert only matters for future variants
- which the repository-level create hook handles.

### Inventory page (`admin/inventory/index.php`)

Currently lists rows from `commerce_inventory`. After the
migration, this naturally becomes "one row per sellable unit":
simple product rows plus variant rows. No code change needed
- verify visually.

Filtering by "product" should group variant rows under their
parent. This may already work; if not, add a product filter.

## Test Protocol

After migration and code changes:

    T-V1  Simple product inventory unchanged. Add to cart
          works. Stock check enforces.

    T-V2  Variable product has NO variant_id = 0 row.
          Verify: SELECT * FROM commerce_inventory
          WHERE product_id = <var product id>;

    T-V3  Every active variant has exactly one inventory row.
          Verify: JOIN variants to inventory, count = variants.

    T-V4  Adding a variant to cart checks that variant's row.
          Set variant A to 5 units. Try adding 10. Rejected.

    T-V5  Variant A has 5, Variant B has 100. Add 10 of
          variant A: rejected. Add 10 of variant B: allowed.

    T-V6  Product edit -> Inventory tab on variable product:
          input is disabled, summary line shows correct total.

    T-V7  Product edit -> Inventory tab on simple product:
          input is enabled. Same behavior as before.

    T-V8  Inventory page lists simple product rows and
          variant rows. Filter by product groups them.

    T-V9  Dashboard "units on hand" equals the sum of all
          sellable-unit rows.

    T-V10 Regenerate variations on a product: old variant
          inventory rows are removed with the variants; new
          variants get fresh inventory rows at 0.

    T-V11 Creating a new variable product with no stock:
          product page shows "Out of stock" per variant
          (or "unavailable" if preferred).
