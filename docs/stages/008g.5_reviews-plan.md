## Purpose

The product detail page renders a Reviews tab that reads
"coming soon" as a placeholder. This stage fills that tab
with real customer reviews, ratings, and moderation.

Reviews are the highest-impact missing storefront feature
for conversion. They were logged as a deferred stage in
four prior documents:

  - docs/stages/008b_extended-visual-plan.md
  - docs/stages/008b_storefront-visual-identity.md
  - docs/stages/008c_customer-auth-plan.md
  - docs/STATUS.md "What Doesn't Work Yet"

This stage delivers them.

## Decisions Locked

### D1 - Any logged-in customer can review

No purchase requirement. Any customer with an account can
submit a review. If they have completed an order containing
the product, the review carries a "Verified Purchase"
badge. If they have not, no badge. Same pattern as Amazon
and Etsy.

Guests cannot review. Reviews are tied to a customer
account so they can be edited and moderated. Anonymous
reviews open the door to spam and make the moderation queue
harder to reason about.

### D2 - One review per customer per product

Enforced by a unique key on
(store_id, customer_id, product_id). A customer can edit
their existing review but cannot submit a second one.

### D3 - Star rating, optional title, required body

Rating: 1-5 (integer, required).
Title: optional, 150 chars max.
Body: required, 5000 chars max.

No review title means the review renders with the
customer's name and the star rating only. No body means
the review is rejected at the form level.

### D4 - Verified purchase from order history

A review is marked verified_purchase = 1 when the customer
has an order in `commerce_orders` with:

  - status IN ('delivered', 'completed')
  - the product_id present in `commerce_order_items`

The check runs once, at submission time. The order_id is
stored for audit. If the order is later refunded, the
badge stays - it recorded that a purchase happened, not
that it stuck.

### D5 - Moderation queue, default status = pending

Every review enters the queue as 'pending'. Only approved
reviews render on the storefront. The administrator
approves or rejects.

Rejections can carry a reason (stored in a future column;
not in v1). The customer can resubmit after editing if
their review was rejected.

The moderation workflow is:
  - `/commerce/ca-admin/reviews` — list of pending
  - Approve / reject buttons per row
  - Bulk approve
  - Rejection without a reason in v1

### D6 - No photos in v1

Review photos are a common feature but they need a media
pipeline context and moderation of image content. Both are
larger scope. Deferred to a future sub-stage.

### D7 - Reviews render inside the Reviews tab on the PDP

The tab structure already exists (008G.4b session 4). The
placeholder panel is replaced with:

  - A summary block: average rating, count, distribution
    bars (5-star, 4-star, ...)
  - A submission form (logged-in customers only)
  - A list of approved reviews with pagination

### D8 - Rating aggregate in the buy box

Average rating and count render under the product title in
the buy box. This is the same info the tab shows in its
summary block, surfaced earlier in the page.

Computing the average on every PDP load would be a query
per view. The aggregate is cached per (store_id, product_id)
with a short TTL. Cache invalidation happens when a review
is approved or deleted.

Alternative: no cache, just a query. Simpler. The count
query is fast with the index
`idx_com_rev_product_rating`. Start with no cache.
Add the cache later if performance data shows a need.

### D9 - Reviews are tied to a customer account

Deleting a customer anonymizes their reviews by nulling
the customer_id and setting the review body to
"[This review was removed at the author's request]".
Deleting a product cascades and removes its reviews.

The customer's display name on a review is their
`fullName()` (or email as fallback). No full address, no
email domain, no other identifying info.

DSGVO Art. 17 compliance. Full policy in the plan's
Compliance section.

### D10 - Moderation queue needs one new permission

`review.moderate`. Seeded in a new seeder
`0008_seed_review_permissions.sql`. Assigned to the
super-admin role via the same INSERT ... SELECT pattern
used by the existing seeder.

## Schema

### Table: commerce_product_reviews

id BIGINT UNSIGNED PK AUTO_INCREMENT
store_id BIGINT UNSIGNED NOT NULL
product_id BIGINT UNSIGNED NOT NULL
customer_id BIGINT UNSIGNED NULL (null after DSGVO anonymization)
order_id BIGINT UNSIGNED NULL (order that qualified the verified badge)
rating TINYINT UNSIGNED NOT NULL (1-5)
title VARCHAR(150) NULL
body TEXT NOT NULL
verified_purchase TINYINT(1) NOT NULL DEFAULT 0
status ENUM('pending','approved','rejected') NOT NULL DEFAULT 'pending'
created_at DATETIME DEFAULT CURRENT_TIMESTAMP
updated_at DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP

### Indexes

  - `uniq_com_rev_store_customer_product` — (store_id, customer_id, product_id) UNIQUE
  - `idx_com_rev_store_product_status` — (store_id, product_id, status, created_at)
  - `idx_com_rev_store_status_created` — (store_id, status, created_at)
  - `idx_com_rev_product_rating` — (store_id, product_id, status, rating)

### Foreign keys

  - fk_com_rev_store -> commerce_stores(id) ON DELETE CASCADE
  - fk_com_rev_product -> commerce_products(id) ON DELETE CASCADE
  - fk_com_rev_customer -> commerce_customers(id) ON DELETE CASCADE
  - fk_com_rev_order -> commerce_orders(id) ON DELETE SET NULL

## Routes

### Storefront

    POST /products/{slug}/review        submit (create or update)
    GET  /products/{slug}/reviews       paginated list (JSON)

The submission route requires a logged-in customer. Guest
attempts redirect to /account/login with a flash.

### Admin

    GET  /commerce/ca-admin/reviews           list pending (default)
    GET  /commerce/ca-admin/reviews?status=approved
    POST /commerce/ca-admin/reviews/{id}/approve
    POST /commerce/ca-admin/reviews/{id}/reject
    POST /commerce/ca-admin/reviews/{id}/delete

All admin routes require the `review.moderate` permission.

## Compliance

### DSGVO Art. 17 (Right to Erasure)

  - Customer deletion anonymizes reviews: customer_id -> NULL,
    body -> "[This review was removed at the author's request]".
  - The review itself is not deleted — the rating remains
    valid for the product's aggregate score.
  - Plan documents the retention rule and the anonymization
    procedure.

### DSGVO Art. 5 (Data Minimisation)

  - Reviews store only: rating, title, body, verified
    flag, timestamps, FKs.
  - No email addresses, no IP addresses, no user agents.
  - The customer's display name renders at query time
    from commerce_customers.fullName(). If the customer
    is later anonymized, no name is stored on the review.

### UWG § 7 (Unfair Competition)

  - Verified purchase badges must not mislead.
  - The badge is generated from order history, not
    manually assigned.
  - Admin moderation ensures no fake reviews.

## Not in Scope

  - Review photos / videos.
  - Helpful / unhelpful voting.
  - Merchant replies.
  - Star distribution charts on the PDP (only aggregate).
  - Review incentives (discount codes, email reminders).
  - Automatic email notifications on review approval.
  - A /account/reviews page for the customer's own reviews.
    Submission and edit happen on the PDP.
