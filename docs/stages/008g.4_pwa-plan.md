# Stage 008G.4 - PWA

**Status:** In progress
**Opened:** 2026-10-02
**Depends on:** Stage 008G (storefront polish), 008A (Store model)

---

## Goal

Activate the storefront as a Progressive Web App. Today the
pieces exist but nothing is wired:

- `public/sw.js` is a real, working service worker,
  committed in the initial repo baseline (`e18e5d3`).
- `/manifest.json` is routed at `routes/commerce.php:20` to
  `ManifestController`, which reads from a static config
  file, not from the Store.
- `/offline` is routed at `routes/storefront.php:61` as an
  inline closure returning hardcoded HTML.
- The `Store` model has four PWA fields
  (`pwaName`, `pwaShortName`, `pwaThemeColor`,
  `pwaBackgroundColor`) added in migration
  `0100_create_commerce_stores.sql` and read by no code.
- No PWA icons exist at `public/assets/img/pwa/`.
- The layout `<head>` has no `<link rel="manifest">`, no
  `<meta name="theme-color">`, no apple-touch-icon.
- No JavaScript registers the service worker.

Nothing works today. Everything has been waiting for this
stage.

---

## What This Stage Is Not

Not a new table. Not a new service. Not a new controller
namespace. The last three sub-stages (008G.1, .2, .3) each
shipped a database table, a repository, a service, a
controller, and views. This one ships none of those.

It ships:

- One controller rewrite (store-aware manifest).
- One closure replacement (offline view).
- Two PNG icon assets.
- Five `<head>` tags.
- One service worker registration script.
- One `PRECACHE_URLS` correction.
- One install-prompt banner.

The whole stage is roughly the size of one of the last
three's single "file 3" commits.

## Deliberate Simplifications

### 1. Config-sourced vs store-sourced branding

The current `ManifestController` reads from
`config('branding')`. That file is deployment-wide. It has
one brand name for the whole platform.

But the storefront is multi-tenant. Each store has its own
`pwaName`, `pwaShortName`, `pwaThemeColor`,
`pwaBackgroundColor` columns.

Decision: the manifest reads from the resolved Store, with
a fallback to `config('branding')` if a Store is not in
scope. This makes the manifest correct for the primary
single-tenant deployment today and correct for the
multi-tenant case when more stores exist.

The route must carry `['store']` middleware so
`StoreContext` is populated. It does not today.

### 2. Static default icons, not per-store uploads

The plan references two PNG files at fixed paths. The
media library (per-store icon upload) lands in a future
stage. For 008G.4, we ship two Anaya Global icons that
every store uses until the store builder exists.

The Store model's `logoFileId` and `faviconFileId` are not
consulted for PWA icons in this stage. That's the store
builder's job in Stage 011.

### 3. One service worker for the whole origin

The existing `sw.js` runs at `/sw.js` (top-level scope),
so it controls the whole origin. It has no concept of
which store it is serving.

That's correct for 008G.4. The cache namespacing is by
version only (`anaya-v1`). If multi-tenant cache isolation
is needed later, it lands with the store builder.

The comment in `sw.js` already anticipates this:
"store namespacing is added when the SW can read the
store id from the URL; Phase 3 will inject it."

### 4. No offline write support

The service worker serves an offline shell when the
network is unavailable. It does not queue failed writes
for later sync. A customer who loses connectivity while
browsing cannot add to cart, checkout, or update their
account. They see the offline page and wait.

Offline write support (Background Sync, IndexedDB queue)
is Stage 011+ territory. It's a real engineering problem
with real complexity.

### 5. Install prompt is a soft banner, not a modal

The `beforeinstallprompt` event is captured and shown as a
small dismissible banner at the bottom of the storefront.
The customer can install or dismiss. Dismissal is stored
in localStorage for 30 days.

No forced modal. No nag. No popup that reappears on every
page.

## Files To Modify

### app/Commerce/Controllers/Pwa/ManifestController.php

Rewrite to read from the resolved Store first, falling
back to `config('branding')`. Read the four PWA fields
from the Store model. Add a maskable 512 icon.

Shape:

    $store = $this->resolveStore();
    if ($store !== null) {
        $name      = $store->pwaName      ?? $store->name;
        $shortName = $store->pwaShortName ?? $name;
        $theme     = $store->pwaThemeColor     ?? $branding['pwa_theme_color'] ?? '#000000';
        $bg        = $store->pwaBackgroundColor ?? '#ffffff';
    } else {
        // fall back to config branding
    }

`resolveStore()` mirrors `StorefrontController::resolveStore()`.
The controller does not extend `StorefrontController`
because that base class renders HTML through the layout —
the manifest is JSON.

Cascade: The route must carry `['store']` middleware or
`StoreContext::has()` returns false and `resolveStore()`
returns null. Without the middleware, this rewrite degrades
to the current behavior.

### routes/commerce.php

Add `['store']` to the manifest route:

    $router->get('/manifest.json',
        [ManifestController::class, '__invoke'],
        ['store']);

Cascade: The `store` middleware is registered in the
Kernel's `$map`. It is already used by every storefront
route. Applying it here is safe.

### routes/storefront.php

Replace the `/offline` closure with a controller call, or
leave the closure and have it delegate to a view:

    $router->get('/offline', function (Request $req, array $params): Response {
        return Response::html(
            view('storefront.offline')
        );
    });

Actually — the cleaner form is to give it a controller
action. But `StorefrontController::render()` requires a
container. A closure can resolve it.

Simplest correct form: keep the closure, resolve the view
service from the container, render the offline view
through the storefront layout.

Cascade: The route has no `['store']` middleware today.
Add it so `$store` is available to the layout when the
offline page renders. The layout uses `$store` for the
header (brand name), and without it the header falls back
to a generic brand.

### resources/views/storefront/layouts/main.php

Add to `<head>`:

    <link rel="manifest" href="/manifest.json">
    <meta name="theme-color" content="<?= e($themeColor) ?>">
    <link rel="apple-touch-icon" href="/assets/img/pwa/icon-192.png">
    <meta name="apple-mobile-web-app-capable" content="yes">
    <meta name="apple-mobile-web-app-status-bar-style" content="default">
    <meta name="apple-mobile-web-app-title" content="<?= e($brandName) ?>">

`$themeColor` comes from the Store, same source the
manifest reads. Resolve it in the layout's PHP block at
the top: if `$store` is set and has `pwaThemeColor`, use
it; else fall back to a design token constant.

The PWA tags go near the top of `<head>`, before the CSS
links, so the browser can process them without waiting for
the stylesheets.

Also add a service worker registration script near the
existing cart JS block:

    if ('serviceWorker' in navigator) {
        window.addEventListener('load', function () {
            navigator.serviceWorker.register('/sw.js', { scope: '/' })
                .catch(function () { /* silent */ });
        });
    }

Silent failure. A browser without service worker support
still gets a fully functional storefront.

Cascade: `main.php` is the storefront layout, rendered on
every storefront page. Adding head tags and one script
block is additive. No existing page breaks.

### public/sw.js

Fix `PRECACHE_URLS`. Currently:

    const PRECACHE_URLS = [
      '/',
      '/assets/css/app.css',
      '/assets/js/app.js',
      '/assets/js/notifications.js',
      '/offline',
    ];

The first three are **admin** assets, not storefront.
The storefront uses `/assets/css/storefront.css`,
`storefront-home.css`, `storefront-catalog.css`, etc.
`/assets/js/notifications.js` is also admin.

Replace with the storefront shell:

    const PRECACHE_URLS = [
      '/',
      '/offline',
      '/assets/css/storefront.css',
      '/assets/css/storefront-home.css',
      '/assets/css/storefront-catalog.css',
      '/assets/css/storefront-product.css',
      '/assets/css/storefront-auth.css',
      '/assets/css/storefront-cart.css',
      '/assets/css/storefront-checkout.css',
      '/assets/css/storefront-search.css',
      '/assets/js/storefront-gallery.js',
      '/assets/js/wishlist.js',
    ];

Bump `CACHE_VERSION` from `v1` to `v2` so the existing
browsers that never registered the SW (all of them) do not
have a stale cache. The `activate` handler already cleans
up old cache names.

Note: `storefront-cookie-banner.css` and
`storefront-cookie-banner.js` are conditionally loaded.
They are not precached. If a customer is offline and the
banner is enabled, the banner loads from network and fails.
That is acceptable - the offline page does not need the
cookie banner.

Cascade: The service worker only runs after the customer
registers it. Since nothing registers it today, there are
no existing users of this SW. The version bump is
belt-and-suspenders.

### public/assets/img/pwa/icon-192.png and icon-512.png

New PNG icons. Anaya Global monogram on a warm background,
centered, with padding for the maskable variant.

The monogram is the SVG from
`resources/views/storefront/partials/header.php` (the
A+globe mark). Render it at 192×192 and 512×512 with a
warm cream background.

Icon files are binary and cannot be generated by a PHP
script in this session. The customer supplies them, or we
generate them separately before running the migration and
test pass.

Until the icons exist, the manifest references paths that
return 404 and the browser silently rejects the PWA
install prompt. The rest of the stage (offline page, head
tags, SW registration) works without them.

## Install Prompt Banner

A small dismissible banner that appears at the bottom of
the storefront when the browser fires
`beforeinstallprompt`.

Context in the view (a partial or inline):

    A banner with:
      - Small app icon (32x32)
      - "Install Anaya Global" text
      - Install button
      - Dismiss button

The banner is shown only when:
  - The browser fired beforeinstallprompt.
  - The customer has not dismissed it in the last 30 days.

Dismissal is stored in localStorage under
`sf-pwa-install-dismissed-until` as a timestamp.

The banner is a `<div>` inserted at the bottom of the
`<body>` from JavaScript. It is not in the layout markup -
it is created dynamically so it does not appear in the
DOM unless the browser signals installability.

New JS file: `public/assets/js/pwa-install.js`. Loaded
with `defer` from the layout.

New CSS: a small block in `storefront.css` for the banner.

## Test Protocol

    T-1  Visit / in a browser. DevTools Application tab
         shows the manifest loaded with the store's name.
    T-2  DevTools Application tab shows the service worker
         as "activated and running".
    T-3  DevTools Application tab shows installability
         criteria met (if the icons are present).
    T-4  Disconnect network. Reload any storefront page.
         The offline page renders with the storefront
         shell.
    T-5  Disconnect network. Reload /cart. The offline page
         renders (the cart is excluded from the SW cache
         because it is a navigation request that hits the
         network-first branch).
    T-6  Reconnect. Reload. Normal page.
    T-7  On Android Chrome, visit the site. The install
         prompt banner appears (if installed icons exist
         and installability criteria are met).
    T-8  Dismiss the banner. Reload. It does not appear.
    T-9  Clear localStorage. Reload. The banner appears
         again.
    T-10 Confirm /account/* routes are never cached by the
         SW (open DevTools Network tab; navigate to
         /account/orders; check the request was served
         from network, not ServiceWorker).
    T-11 Confirm /api/* routes are never cached (same
         technique).

## Out of Scope

- Per-store icon uploads (Store Builder, Stage 011).
- Offline write support / Background Sync (Stage 011+).
- Push notifications (Stage 011+).
- Real-time SW update prompts. The SW uses the default
  browser behavior: install the new version, activate on
  next navigation.
- Cache-first for HTML. Only static assets are cached.
  Navigations are network-first with an offline fallback.
- Prefetching product pages on hover or viewport entry.
- Custom offline HTML for specific pages. All navigations
  fall back to the same /offline page.
