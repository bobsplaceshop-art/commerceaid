## A Correction To The Session Handoff

The session file for 2026-09-30 described 008G.3 as "the
first cross-layer integration in the storefront build -
reads from core_notifications, writes to
NotificationRuleService."

Reading the schema before designing disproved that
description.

`core_notifications` targets `core_users`, not
`commerce_customers`:

    `user_id` INT UNSIGNED NOT NULL
    CONSTRAINT fk_core_notif_user
        FOREIGN KEY (`user_id`) REFERENCES `core_users` (`id`)

`core_users` is the admin identity table. `commerce_customers`
is a different table with a different ID space. Today, the
notification system has no concept of "customer."

`core_notification_rules` confirms the same: its
`recipient_type` enum (`role`, `permission`, `user`,
`assigned_recruiter`, `engagement_member`,
`organisation_client_admin`, `organisation_client_user`,
`hiring_manager`, `owner`, `actor_except`) is a set of
Recruit Aid leftovers. None of them map to a storefront
customer.

So 008G.3 is not a cross-layer integration. It is a
self-contained Commerce feature. The message center owns its
own table, its own service, its own preferences. Platform
stays unaware.

This correction is the plan's first decision, and the reason
the plan exists before the code.

---

## Goal

A customer-facing notification surface. Three tabs:

  System Messages   - welcome, password change confirmation,
                      policy updates, admin announcements
  Order Updates     - order placed, and (once producers
                      exist) order shipped, order delivered,
                      refund issued
  Promotions        - opt-in marketing. Deferred producer.

An unread count badge in the account sidebar. A preferences
page where the customer controls which categories arrive
in-app vs by email.

---

## Deliberate Simplifications

Two things the session handoff proposed, and we are not
doing:

### 1. No writes to NotificationRuleService

`NotificationRuleService` is Platform-owned and its
`recipient_type` enum does not include customers. Using it
would require extending the enum, which puts "customer" into
Platform - forbidden by docs/ARCHITECTURE.md.

Customer notification preferences are Commerce-owned. A
small preferences table (or columns on commerce_customers)
holds them. No cross-layer call.

### 2. No order status producer from OrderRepository

Order status changes today happen in exactly two places:

  OrderRepository::update()       (admin-initiated, no UI yet)
  OrderRepository::claimOrders()  (customer guest-order claim)

Neither is a status transition in the sense the message
center wants (shipped, delivered, refunded). They are
internal state updates with no customer-visible meaning yet.

The message center's Order Updates tab producer is
CheckoutService, at the single stable point where an order
is created. One line:

    $this->customerNotifications->orderPlaced(
        $customerId,
        $orderNumber,
        $orderId
    );

When 008H (returns) or 010 (payments deep) introduces real
order lifecycle events, they add producers at their own
call sites. The message center reads whatever rows exist.
No coupling to OrderRepository now.

## Decisions Locked

### Decision 1 - Commerce-owned table

`commerce_customer_notifications`. Parallel to
`core_notifications` but scoped to customers and stores.

Shape:

    id           BIGINT UNSIGNED PK
    store_id     BIGINT UNSIGNED FK -> commerce_stores
    customer_id  BIGINT UNSIGNED FK -> commerce_customers
    category     ENUM('system','order','promotion')
    title        VARCHAR(255)
    body         TEXT NULL
    link         VARCHAR(500) NULL
    read_at      DATETIME NULL
    created_at   DATETIME DEFAULT CURRENT_TIMESTAMP

    KEY idx_com_cn_customer_unread
        (store_id, customer_id, read_at, created_at)
    KEY idx_com_cn_customer_category
        (store_id, customer_id, category, created_at)

FK to store and customer, both ON DELETE CASCADE. A deleted
customer takes their notifications.

No FK to orders. The link column carries the URL for
"view this order" - no hard dependency.

### Decision 2 - CustomerNotificationService is the only producer

No code outside the service writes to the table. Same
discipline as `NotificationService` in Platform: the
service is the sole writer.

Public API:

    notify(customerId, category, title, body, link)
        - generic. Used by admin-authored messages.

    systemMessage(customerId, title, body, link)
        - shorthand for category='system'

    orderPlaced(customerId, orderNumber, orderId)
        - the checkout hook. Formats the message and link.

    welcome(customerId)
        - called on registration. Fires a system message.

The service does NOT touch core_notifications. It does NOT
call NotificationService. It writes only to
commerce_customer_notifications.

### Decision 3 - Preferences stored as columns on the customer

Two booleans on `commerce_customers`:

    notify_order_updates   TINYINT(1) DEFAULT 1
    notify_promotions      TINYINT(1) DEFAULT 0

A new `commerce_customer_notification_prefs` table is
overkill for two booleans. Adding columns is one migration
and no join. If preferences grow beyond two or three
booleans, we extract a table then.

The existing `accepts_marketing` boolean stays as-is. It
predates this stage and is used by the registration form.
It is not removed or repurposed.

### Decision 4 - Sidebar badge uses unread count

The account sidebar already supports a `badge` field per nav
item. The wishlist and recent pages never used it. The
message center nav item carries:

    'badge' => $unreadCount

Populated from `CustomerNotificationService::unreadCount()`.
Same mechanism as the Claims badge from 008E.2.

No new badge infrastructure. No AJAX. The badge updates on
each page load.

### Decision 5 - Email channel is a stub

The preferences page offers a per-category channel toggle
(in-app vs email). The email side is a stub - no code sends
anything. The preference is stored. When 010 ships an email
digest worker, it reads the preferences and sends.

The UI is honest about this: a small note on the preferences
page says "Email delivery is not yet active."

### Decision 6 - Order Updates tab may be empty

The tab exists from day one. Its producer (CheckoutService)
writes one row per order placed. If the customer has not
placed an order since 008G.3 shipped, the tab shows an
empty state with a link to /account/orders.

No fake data. No placeholder rows.

Adds two boolean columns to `commerce_customers`:

    notify_promotions     TINYINT(1) NOT NULL DEFAULT 0

Separate migration from the table creation. Two

### routes/storefront.php

Three routes:

    GET  /account/messages                    index
    POST /account/messages/mark-read          markRead
    POST /account/messages/mark-all-read      markAllRead
    GET  /account/messages/preferences        preferences
    POST /account/messages/preferences        savePreferences

Five routes. All require login (enforced in controller).
POST routes carry CSRF middleware.

### app/Commerce/CommerceServiceProvider.php

Bind CustomerNotificationRepository and
CustomerNotificationService. The service takes no session
dependency - notifications are per-customer, not
per-session. Guests do not have a message center.

### app/Commerce/Controllers/Storefront/AuthController.php

Two call sites (registration and login) gain a call to
CustomerNotificationService::welcome($customerId). Only on
registration - the login path skips it. A customer who
registers gets a welcome message. A customer who logs in
does not.

Actually - only the registration path. Move the call to
inside the registration method, not the shared merge
section. One call site.

### app/Commerce/Services/CheckoutService.php

After the order is created and the status history is
appended, add:

    $this->customerNotifications->orderPlaced(
        $customerId,
        $orderNumber,
        $orderId
    );

Constructor injection: CheckoutService gains
CustomerNotificationService as a dependency.

Cascade: CheckoutService is the checkout entry point.
The added call runs once per successful order placement.
The service swallows failures so a broken notifier cannot
break checkout - same pattern as the recently-viewed
record hook.

### resources/views/storefront/account/_sidebar.php

Flip the Messages group from 'soon' => true to a real link
to /account/messages. Populate the badge from the unread
count passed through from the shell.

The shell needs to pass $unreadMessageCount to the
sidebar partial. That is one more key on the array.

### resources/views/storefront/account/_shell.php

Add `$unreadMessageCount` to the sidebar partial context.

The shell already does this for `$claimableCount` (the
Claims badge from 008E.2). The same pattern applies: the
shell reads the count, passes it to the sidebar partial,
and the sidebar renders it if greater than zero.

`$claimableCount` is passed to the shell by each account
controller that needs it. `$unreadMessageCount` is the
same shape. Controllers that load the shell pass the
count. In practice every account page loads the shell, so
every account controller passes it.

Implementation choice: resolve `$unreadMessageCount` inside
the shell itself, not in each controller. The shell has
container access via the standard render pipeline and can
call `CustomerNotificationService::unreadCount()` once per
request. This is the same pattern the shell uses for
breadcrumbs - one place, resolved once.

### app/Commerce/Support/StorefrontController.php

No change. The unread count is resolved by the shell, not
by render(). render() is already responsible for cartCount
and wishlistProductIds. Keeping the message-center count
out of that method avoids touching the highest-cascade file
in the codebase for a value only the sidebar needs.

## Test Protocol

    T-1  Register a new customer. /account/messages shows
         one unread "Welcome" system message.
    T-2  Sidebar badge shows "1" next to Messages.
    T-3  Click the message. read_at is set. Badge clears.
    T-4  Place an order. Order Updates tab shows one
         "Order placed" message with a link to the order.
    T-5  Preferences: toggle order_updates off. Place
         another order. No new message appears in the tab.
    T-6  Preferences: toggle promotions on. No messages
         appear until a promotions producer exists (none
         today).
    T-7  Mark-all-read clears the badge.
    T-8  Guest visits /account/messages. Redirected to
         login.
    T-9  Customer with 0 notifications sees the empty
         state on each tab.
    T-10 Archived/deleted product linked from an order
         notification: the link still resolves (order
         page), no 500.

## Out of Scope

- Email delivery. The preferences are stored, the send is
  a stub.
- Admin UI for authoring customer notifications. The
  service method exists. A UI lands when there is a reason
  to send a bulk message.
- Push notifications. PWA in 008G.4.
- Order shipped / delivered / refunded producers. Those
  arrive when 008H (returns) and 010 (payments deep)
  introduce the events.
- Real-time badge updates. The badge updates on page load.
- Reading core_notifications from the customer side. Two
  separate systems by design.

### Bugs found and fixed during the build

**Bug 1 - Undefined variable $customerId in CheckoutService.**
Caught by PHPStan immediately after the wiring patch landed.
The orderPlaced() call was written with a $customerId
variable that did not exist in placeOrder()'s scope. The
method's variable is $customer, typed Customer|null. Fixed
by guarding the call on `$customer instanceof Customer` and
passing $customer->id. The guard also correctly skips the
notification for guests.

**Bug 2 - CheckoutService constructor argument count mismatch.**
Also caught by PHPStan. The provider binding was not updated
when the constructor gained its 15th dependency. Fixed by
adding `$c->get(CustomerNotificationService::class)` to the
binding.

These two are why the wiring step exists as its own commit.
Both were caught before the smoke test. Both would have
surfaced as runtime fatals otherwise.

**Bug 3 - Header partial silently vanished.**
The header restructure patch removed the block at the top of
the partial that resolves $__customer and $__unread. The bell
conditional still referenced $__unread. Every storefront page
threw "Undefined variable $__unread", view_partial() caught
it, logged it, and returned an empty string. The entire
header disappeared from every page.

Caught by the app log:
  ERROR: view_partial(storefront/partials/header) failed:
  Undefined variable $__unread

Fixed by restoring the resolution block. Documented as
Pattern 30 in docs/REMEMBER.md.

This bug is why Pattern 30 exists. Before this, we had
Pattern 26 (a shared partial's guard fails silently) and
Pattern 28 (a partial does not inherit outer scope). Pattern
30 completes the triangle: a partial references a variable
that was removed by a patch.

### Enhancements not in the original plan

Three additions requested during the build:

**A. Header bell dropdown.**
The original plan called for an unread count badge in the
account sidebar. During the build, the customer asked for a
bell in the storefront header that previews the top unread
messages inline. Added as customer_recent_messages() helper
plus a bell panel with the top 5 unread items and a "View
all messages" footer.

**B. Header action cluster reorder.**
Cart first, bell second, account last. Search stays leftmost.
More-used controls move left.

**C. Guest "Sign in" label.**
The bare person icon did not communicate "click here to log
in." Guests now see a "Sign in" text label next to the icon.
Collapses to icon-only below 640px.

None of these were in the plan. All three were UX
improvements identified when the plan's outputs were in
front of the customer.

### Patterns

One new pattern: Pattern 30 (view_partial swallows PHP
fatals). Documented in docs/REMEMBER.md.

The build also applied the lessons of Patterns 26 and 28
proactively - no shared-partial-guard bugs, no view-scope
leaks. Pattern 30 was the exception: it is a new failure
class that neither Pattern 26 nor Pattern 28 covered.
