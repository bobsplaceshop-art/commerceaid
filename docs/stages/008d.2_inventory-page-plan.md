# Stage 008D.2 - Per-Product Inventory Page

**Date opened:** 2026-09-28
**Status:** Planned
**Depends on:** Stage 008D.1 (variant inventory model)

---

## Purpose

The inventory list was designed for a world where each product
was one sellable unit. The 008D.1 sub-stage made variants the
sellable unit. Now a variable product with 12 variants produces
12 rows in the inventory list, and one product's stock is
scattered across a long page.

This sub-stage restructures the inventory UI around a
product-centric model:

  - The inventory list shows one row per product with a
    summary (variant count, total units).
  - Clicking a product opens a dedicated per-product page.
  - The per-product page shows every variant in a table with
    inline adjust controls and a sticky save bar.
  - Simple products get the same detail page (one row, same
    layout).
  - The modal stays for simple-product quick adjust from the
    list.

---

## The Two List Views

### Inventory list (`/commerce/ca-admin/inventory`)

Before:

  One row per sellable unit.
  A T-Shirt with 12 variants = 12 rows.
  A store with 20 variable products averaging 10 variants
  each = 220 rows.

After:

  One row per product.
  Simple products = one row.
  Variable products = one row, showing variant count and
  aggregate stock.
  Same store = 20 rows for the variable products + simple
  products.

Columns:

  Product         Image + name (link to detail page)
  Type            "Simple" or "12 variants"
  SKU             Product-level SKU (simple) or blank
  Units           Total across all sellable units
  Status          In Stock / Low Stock / Out of Stock (worst
                  case across the product)
  Actions         Adjust (modal for simple, link for variable)

Filters:

  Same as today (search, status, category, brand).
  "Status" applies to the aggregate product status.

Summary tiles (unchanged):

  Low Stock      count of products with any low-stock unit
  Out of Stock   count of products with all units out of stock
  Units on Hand  sum across all sellable units

### Per-product page (`/commerce/ca-admin/inventory/item/{id}`)

Breadcrumb: Inventory / Product Name

Header:

  Product name + type ("Variable product, 12 variants")
  Aggregate stats: Total units, Low stock variants count
  Status badge (In Stock / Low Stock / Out of Stock)

Body:

  A table with one row per sellable unit:

    Variant         Attribute summary or "—" for simple
    SKU             SKU or "—"
    On Hand         Editable number input
    Reserved        Read-only
    Available       Read-only (computed)
    Status          In Stock / Low Stock / Out of Stock

  Save all changes bar at the bottom (sticky).

Below the table:

  Movement history for this product (last 20 entries).
  "View full history" link to the filtered movements page.

### Simple products

Same detail page. One row (the product itself with "—" for
variant). Same layout. Same behavior.

## Why Two Entry Points for Simple Products

Simple products are common and often adjusted in quick
bursts ("bump stock on 5 products, one after the other"). The
modal is faster for that: click pencil, adjust, save, close.
No page navigation.

Variable products are different. Adjusting one variant without
seeing the others is rarely what the merchant wants. The
detail page is the right shape.

Rule:

  Simple: modal from the list, OR click name to detail page
  Variable: click name to detail page (no modal for the
    parent; the modal is still used per-variant on the detail
    page if we add it later)

---

## The Invariant Preserved

Every sellable unit still has exactly one inventory row. The
detail page is a view over those rows. No data model change.

The inventory list becomes a view over products, aggregating
their sellable-unit rows. Still no data model change - just a
different query.

## Query Shape

The new list query groups inventory rows by product:

  SELECT
      p.id, p.name, p.slug, p.product_type, p.sku,
      COUNT(DISTINCT i.id) AS unit_count,
      SUM(i.quantity)      AS total_quantity,
      SUM(i.reserved)      AS total_reserved,
      MIN(CASE WHEN i.available <= 0 THEN 1 ELSE 0 END)
          AS any_out_of_stock,
      MIN(CASE WHEN i.available > 0
                AND i.available <= COALESCE(i.low_stock_threshold,
                    :default_threshold)
           THEN 1 ELSE 0 END) AS any_low_stock
  FROM commerce_products p
  LEFT JOIN commerce_inventory i
    ON i.product_id = p.id AND i.store_id = p.store_id
  WHERE p.store_id = ?
    AND p.deleted_at IS NULL
    AND (filters)
  GROUP BY p.id
  ORDER BY p.name

For simple products, this produces one row with unit_count = 1.
For variable products, one row with unit_count = N (number of
variants).

Status computed in PHP from `any_out_of_stock` and
`any_low_stock`:

  both 0              -> In Stock
  any_low_stock = 1   -> Low Stock (unless all are out)
  any_out_of_stock=1
    AND all out       -> Out of Stock
  any_out_of_stock=1
    but some in stock -> Low Stock

## The Per-Product Detail Query

For a single product:

  SELECT
      i.id, i.product_id, i.variant_id,
      i.quantity, i.reserved, i.available,
      i.low_stock_threshold,
      v.sku AS variant_sku, v.attribute_summary,
      p.name AS product_name, p.sku AS product_sku,
      p.product_type
  FROM commerce_inventory i
  INNER JOIN commerce_products p
    ON p.id = i.product_id
  LEFT JOIN commerce_product_variants v
    ON v.id = i.variant_id AND i.variant_id > 0
  WHERE i.store_id = ?
    AND i.product_id = ?
  ORDER BY v.sort_order ASC, i.variant_id ASC

For a simple product, this returns one row with
`variant_id = 0` and `attribute_summary = NULL`.

## Save Behavior on the Detail Page

The detail page has one form per product. Submitting posts:

  adjustments[<inventory_id>] = <new_quantity>
  movement_type[<inventory_id>] = 'adjustment' | 'stocktake' | ...
  reason[<inventory_id>] = "..."

Server-side:

  For each inventory_id posted:
    - Load the current row.
    - Compute delta = new_qty - current_qty.
    - If delta == 0, skip (no movement logged).
    - Call InventoryRepository::adjust(product_id, variant_id,
      delta, movement_type, {reason, created_by}).
    - If delta would push quantity below zero, reject that row
      with an error.

All adjustments run in the same request. Each is its own
transaction (via adjust()). If one fails, we still process the
others and report failures per-row.

Response: flash success with count of rows updated.

## Movement History on the Detail Page

Below the variant table, show the last 20 movements for this
product (all its variants combined).

  SELECT m.*, p.name, v.attribute_summary
  FROM commerce_inventory_movements m
  INNER JOIN commerce_products p ON p.id = m.product_id
  LEFT JOIN commerce_product_variants v ON v.id = m.variant_id
  WHERE m.store_id = ? AND m.product_id = ?
  ORDER BY m.id DESC
  LIMIT 20

Reuses the existing movement row rendering style from the
full movements page.

"View full history" links to
`/commerce/ca-admin/inventory/movements?product_id={id}`.
