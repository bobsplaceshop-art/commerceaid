# Stage 008G.1 - Wishlist

**Status:** Complete
**Opened:** 2026-09-29
**Closed:** 2026-09-29
**Depends on:** 008F.1 (account shell), 008D (cart patterns)

---

## Goal

Customers can save products for later. Per-customer for
logged-in customers, per-session for guests. Merge on login,
same pattern as the cart.

---

## Deliberate Reductions vs the Cart

Wishlist mirrors the cart's integration pattern but is
simpler in every other dimension. Reductions:

| Cart has | Wishlist has | Why |
|---|---|---|
| quantity per row | no quantity | One product, one row. Quantity is not meaningful for save-for-later. |
| unit_price snapshot | no snapshot | Wishlist is not a purchase intent. Price is read live at render time. |
| product_name, sku, variant_label snapshots | none | The live product is the source of truth. No drift concept. |
| CartLineItem view-model (pair with live state) | none | No drift warnings, no stale-price badges. |
| status enum (active/converted/abandoned) | none | No conversion lifecycle. A wishlist row is either there or not. |
| markConverted lifecycle | none | Nothing converts. |
| variant_id in the unique key | product only | Customer saves a product, not a variant. See Decision 1. |

The wishlist is a bookmark list, not a cart-shaped
mini-transaction.

## Decisions Locked

### Decision 1 - Track products only, not variants

A wishlist row is `(store_id, customer_id, product_id)`.
The heart icon on a product card adds the product, not a
specific variant.

Rationale: a customer browsing a category does not know
which variant (Color × Size) they want. The heart says
"I like this product, come back to it." Saving a specific
variant would force a decision the customer has not made.

The schema carries a nullable `variant_id` column from day
one, set to 0 or NULL and unused by any code path. This
keeps the option open without a future migration. Cost: one
column. Benefit: no ALTER later if the decision reverses.

### Decision 2 - Inject `$wishlistProductIds` in `render()`

`StorefrontController::render()` already injects `$cartCount`
into every storefront view. Add a parallel
`$wishlistProductIds` — an array of product IDs the current
viewer has wishlisted.

The alternative (AJAX on page load to fill the hearts) was
rejected because it produces a visible unfilled → filled
flash on every page load and adds a network round-trip. The
`render()` injection is one indexed read on a small table.

The change is one new private method `resolveWishlistProductIds()`,
mirroring `resolveCartCount()`, and one line in `render()`.
Any view that does not use the array ignores it. The
method is defensive: if the read fails, it returns an empty
array. A broken wishlist should not break the storefront.

### Decision 3 - Guest state lives in the session

`$_SESSION['wishlist']` holds an array of product IDs for
guests. No `session_id` column in the database. Merge on
login clears the session key and inserts rows.

Same shape as `$_SESSION['cart']` from 008D.

### Decision 4 - One wishlist row per customer per product

UNIQUE on `(store_id, customer_id, product_id)`. Clicking
the heart twice is idempotent — the second click does not
create a duplicate row. The heart's filled state reflects
membership.

## Schema

One new table. One migration. Same naming conventions as
the cart.

    database/migrations/0310_create_wishlists.sql

Table `commerce_wishlists`:

    id           BIGINT UNSIGNED AUTO_INCREMENT PK
    store_id     BIGINT UNSIGNED NOT NULL  FK -> commerce_stores
    customer_id  BIGINT UNSIGNED NOT NULL  FK -> commerce_customers
    product_id   BIGINT UNSIGNED NOT NULL  FK -> commerce_products
    variant_id   BIGINT UNSIGNED NOT NULL DEFAULT 0  (reserved, unused)
    created_at   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP

    UNIQUE KEY uniq_com_wl_store_customer_product (store_id, customer_id, product_id)
    KEY idx_com_wl_customer (store_id, customer_id, created_at)

    FK store_id    -> commerce_stores    ON DELETE CASCADE
    FK customer_id -> commerce_customers ON DELETE CASCADE
    FK product_id  -> commerce_products  ON DELETE CASCADE

Design notes:

- No `updated_at`. A wishlist row is insert-once or
  delete. Nothing updates in place.
- No soft delete. A removed wishlist item is gone. The
  audit trail lives in the audit log, not in the wishlist.
- `ON DELETE CASCADE` from all three parents. A deleted
  customer takes their wishlist. A deleted product takes
  its wishlist entries. A deleted store takes everything.
- `idx_com_wl_customer` on `(store_id, customer_id, created_at)`
  supports the "newest first" ordering on the wishlist page.

## Test Protocol

Manual, at 375px and 1024px, on `/products`, a product
detail page, and `/account/wishlist`.

    T-1   Guest on /products clicks heart on any product.
          Heart fills. No login required.
    T-2   Guest reloads /products. Heart is still filled.
          (Session persisted.)
    T-3   Guest clicks heart again. Heart empties. Reload
          confirms empty.
    T-4   Guest logs in. /products shows filled hearts for
          products they wishlisted as a guest.
    T-5   Logged-in customer on /products clicks heart.
          Fills. Reload confirms filled.
    T-6   /account/wishlist lists all wishlisted products,
          newest first.
    T-7   /account/wishlist "Remove" button removes the row
          and the heart on /products empties on next load.
    T-8   Logged-in customer clicks heart twice quickly.
          One row in DB. No duplicate. Heart stays filled.
    T-9   Product that is archived after wishlisting: the
          wishlist page shows a "no longer available" state,
          not a 500.
    T-10  Product that is deleted after wishlisting: same.
    T-11  Customer who has never used wishlist loads
          /account/wishlist. Empty state renders.
    T-12  Add all to cart (optional): all available
          wishlist items go to the cart; unavailable items
          are skipped with a notice.

### Bugs found and fixed during the build

1. **Shared partial guard** (Pattern 26) - the wishlist
   partial was the first time we had this class in a new
   feature, but we designed around it by using a helper.

2. **CSRF token not available on pages with no forms.**
   The catalog page has no <form>, so no
   input[name="_csrf"]. wishlist.js sent an empty token and
   got 403. Fixed by reading the meta tag the layout already
   provided. Broader lesson: AJAX endpoints should never
   assume a form is present on the page.

3. **View scope leak.** $wishlistProductIds was injected by
   StorefrontController::render() into the outer view, but
   view_partial() does not propagate outer scope. The
   product card partial's `?? []` silently returned empty.
   Fixed with a static-cached global helper mirroring
   csrf_token(). This is worth documenting as a pattern -
   the codebase's view_partial() convention is explicit
   data passing, and any cross-cutting data must come
   through a helper or explicit passing.

### Deferred (as designed)

- Variant-level wishlisting (the schema reserved a column,
  no code path uses it).
- "Add all to cart" button on the wishlist page (noted in
  the plan as optional; not built).
- Email notifications when a wishlisted product goes on sale
  (out of scope).

### Patterns to document

Two new patterns surfaced that are not in REMEMBER.md yet:
